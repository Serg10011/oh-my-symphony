# Хуки конвейера

Здесь восемь программ на Python ≥ 3.11 (только стандартная библиотека, POSIX). Все они вызываются из `WORKFLOW.md`, который собирается из общего шаблона `ours/templates/WORKFLOW.md.tmpl` командой `ours/bin/project-render` — руками строки в `WORKFLOW.md` не вписываются. `$SYMPHONY_WORKFLOW_DIR` для них — папка доски проекта (`~/symphony-projects/<имя>/`), настройки — её `project.toml`.

| Файл | Где вызывается | Что делает |
|---|---|---|
| `worktree.py create` | `hooks.after_create` | рабочая копия карточки `symphony/<ID>` от базовой ветки, ссылки в папку доски, запись базы, `setup.sh` |
| `worktree.py remove` | `hooks.before_remove` | убирает ссылки в папку доски, затем штатная уборка `_worktree_cleanup` |
| `integrate.py ensure-branch <ЗАДАЧА>` | вручную; её же вызывает `plan.py hook` | создаёт интеграционную ветку задачи `integration/<ЗАДАЧА>` от базовой, если её нет; существующую не трогает. Как библиотека — для `worktree.py` (S4-11) |
| `integrate.py hook` | последняя строка `hooks.after_run` | вливает готовую подзадачу в интеграционную ветку задачи и ставит ей `Done` (S4-12), дописывает ход задачи в её карточку и, если подзадача была последней, начинает итоговую проверку (S4-21); всегда код 0 |
| `integrate.py finish-task <ЗАДАЧА>` | вручную | итоговая проверка задачи (S4-21): слияние `integration/<ЗАДАЧА>` с базовой веткой, рабочая копия, дифф для Verify, `Subtasks` → `Verify`; код 0 — переведена, 1 — нет (причина в выводе) |
| `plan.py hook` | вторая строка `hooks.after_run` | проверяет план `plan.toml`, сданный руководителем переводом карточки в `Subtasks`, и создаёт карточки подзадач; ошибка плана — возврат в `Plan` (S4-19); всегда код 0 |
| `plan.py brief` | последняя строка `hooks.before_run` | для карточки руководителя в `Plan` кладёт сводку лимитов `limits.md` (S4-19); всегда код 0 |
| `check.py hook` | первая строка `hooks.after_run` | механические проверки, если карточка в `Done` / `Human Review`; при провале — откат; при успехе пишет отметку `<ID>.pass.json` |
| `check.py gate` | `agent.done_gate_command` | те же проверки при приёмке Done; код 0 — пропуск; тесты не гоняет повторно, если дерево то же, что уже прошло `hook` и было влито (S4-13) |
| `deliver.py` (`ours/bin/deliver push <ID>`, `merged <ID>`) | команды очереди `<ID>.deliver` и `<ID>.merge` для `deliver/<ID>` | доставка результата карточки на GitHub: проверяет зелёную проверку, пушит ветку `deliver/<ID>`, открывает PR; после слияния PR пишет запись «влито» для шлюза (S4-27); коды 0 / 1 (отказ) / 2 (ошибка) |
| `summarize.py <junit.xml>` | последняя строка `test.sh` | печатает строку итогов `PIPELINE_TESTS passed=… skipped=… failed=…` по отчёту JUnit XML |
| `project_config.py` | библиотека | разбор `project.toml`, раскладка папки доски, сборка `WORKFLOW.md`, строка итогов и замер базы, правка `[timeouts]` |

## `worktree.py`

**create.** ID карточки — имя рабочей папки; он обязан начинаться с `<id_prefix>-` из `project.toml`, иначе отказ. Проверяется, что папка доски не лежит внутри git-репозитория (иначе git молча взял бы чужой репозиторий, REPORT-09, п. 17).

- Если папка уже рабочая копия репозитория кода на ветке `symphony/<ID>` (ядро повторно вызвало хук на той же папке) — режим **«обновить»**: восстанавливаются только ссылки, исключения и отсутствующая запись базы. Ветка не переименовывается, `setup.sh` не запускается — иначе пропала бы работа карточки.
- Иначе — **чистый старт** под блокировкой `<git-common-dir кода>/symphony-worktree.lock` (тот же файл, что у штатного скрипта; `fcntl`, команда `flock` не нужна): штатная подготовка `_worktree_cleanup --prepare-setup`; прежняя ветка `symphony/<ID>` переименовывается в `attempts/<ID>-<UTC>`, прежние артефакты `artifacts/<ID>` — в `artifacts/.attempts/<ID>-<UTC>` (иначе старые файлы прошли бы контракты новой попытки); `git worktree add … -b symphony/<ID> refs/heads/<база>`; настройки рабочей копии (`symphony.basesha`, `symphony.basebranch`, `symphony.mergetargetbranch`, `symphony.autocommitExclude`, `core.excludesFile = <доска>/worktree-exclude`); запись базы `<доска>/.ours-state/<ID>.base.json`; ссылки `kanban`, `docs/<ID>` и `docs/llm-wiki` в папку доски; затем `/bin/bash <доска>/setup.sh` в рабочей папке.
- **База подзадачи (S4-11).** Только при `[integration] enabled = true` в `project.toml`. Тогда в чистом старте читается шапка карточки `<доска>/kanban/<ID>.md` (нет файла — отказ; при `enabled = false` карточка не читается вовсе). Карточка с меткой `worker_label` (по умолчанию `role:worker`) и полем `request: <ЗАДАЧА>` — подзадача: рабочая копия берётся не от `refs/heads/<база>`, а от конца ветки `<branch_prefix><ЗАДАЧА>` (`integration/<ЗАДАЧА>`), и `symphony.basebranch` с `symphony.mergetargetbranch` получают это имя. Если ветки ещё нет, `worktree.py` создаёт её от базовой — под той же блокировкой, после штатной подготовки и до переименования старой ветки, чтобы две подзадачи не создали её вразнобой; существующая ветка никогда не пересоздаётся и не сдвигается. Неверный `request` (не по шаблону ID, чужой префикс, сама карточка) — отказ, код 1: лучше остановить, чем молча стартовать от базовой. Обычная карточка (нет метки или `request`) стартует от базовой, как раньше. В запись базы добавлены поля `start_branch` (откуда взята копия: `our-main` или `integration/<ЗАДАЧА>`) и `task` (`null` для обычной карточки); `base_branch` остаётся веткой проекта, на которой снят `baseline.json`. `check.py` читает из записи только `base_sha`. При откате созданная интеграционная ветка не удаляется: на неё могла встать другая подзадача.
- Если `setup.sh` упал (или не уложился в `hooks_ms` − 30 с), рабочая копия и новая ветка убираются, старая ветка, артефакты и запись базы возвращаются на место, код выхода 1.
- Если `docs/llm-wiki` уже есть в репозитории кода, ссылка не создаётся (предупреждение в выводе хука).

**remove.** Удаляет только те ссылки, что ведут в папку доски, потом вызывает штатный `_worktree_cleanup` с `SYMPHONY_WORKFLOW_DIR = <репозиторий кода>`. Ветки не трогает.

В репозитории кода от хуков меняется только содержимое `.git`: ветки `symphony/*` и `attempts/*`, регистрация рабочих копий, `extensions.worktreeConfig` и файл блокировки. `.git/info/exclude` не трогается.

## `check.py`

Проверки по порядку (подробно — REPORT-07):

1. Конфиг — `<доска>/project.toml`: базовая ветка из `[project]`, путь к `symphony` из `[tools]`, правила из `[checks]` (в том числе `allow_paths`: открывает агенту отдельные пути в `ours/`, но не контур `ours/hooks/**`, `ours/bin/**`, `ours/templates/**` и не другие запреты), таймауты из `[timeouts]`. Неизвестный раздел или ключ — отказ (опечатка не должна отключить проверку); старый `[checks] test_timeout_s` — отказ с подсказкой перенести в `[timeouts] tests_s`. Замеры базы (пишет `project-doctor`): история `<доска>/.ours-state/baselines.json` (S4-25) и последний замер `baseline.json`. Есть `baselines.json` — сравнение идёт по нему (п. 6); файл повреждён, неизвестной версии, запись без нужных полей или с неверным `base_sha`, или нет ни одной записи для `base_branch` — отказ «перезапусти project-doctor», к `baseline.json` не откатываемся, тесты не запускаются. Нет `baselines.json` — режим `legacy`, как было до S4-25: по одному `baseline.json` (нет файла, он повреждён или снят на другой ветке — отказ «запусти project-doctor»). Файлы из рабочей папки агента не читаются никогда.
2. База — `base_sha` из `.ours-state/<ID>.base.json` (её пишет `worktree.py` при создании рабочей копии). Нет записи — отказ; `base_sha` не предок `HEAD` — отказ («ветка переписана относительно базы»). Слияние с подвижной веткой больше не используется: после вливания ветки в целевую проверки ослепли бы.
3. Запрещённые пути, 4. неизменность существующих тестов, 5. разделы карточки — как в K05. К быстрым проверкам (вместе с запрещёнными путями, до тестов) добавлена **проверка «ключ в диффе» (E1b)**: в **добавленных** строках изменений относительно базы — закоммиченных, в индексе, не в индексе и в неотслеживаемых файлах (те же пути и исключения, что у `changed_paths`: без `kanban` и `.symphony`) — ищется `sk-ant-[A-Za-z0-9_-]{20,}` (шаблон `project_config.API_KEY_PATTERN`, одна функция `check.diff_key_hits` на `check.py` и `deliver.py`). Найдено — отказ: «в добавленных строках найден ключ API Anthropic (sk-ant-…): <путь>:<номер строки>; сама строка не выводится» (до 10 мест, дальше «и ещё N»). Текст строки не попадает ни в отчёт, ни в `## Check Failure`, ни в `check.log`, ни в счётчик. Удалённая строка и текст вроде `sk-ant-…` отказа не дают; двоичные файлы (в добавленных строках есть байт NUL) пропускаются. Проверка работает на всех досках и в любом режиме оплаты. Для **подзадачи** (S4-16: `[integration] enabled = true`, у карточки метка `worker_label` и поле `request:` — то же определение, что у `integrate.py`, функция `integrate.is_subtask`) вместо `required_sections` требуются `[checks] worker_required_sections` (по умолчанию `## QA Evidence` и `## Merge Status`: их пишет Verify). У подзадачи нет своего этапа Document: wiki, Learnings и отчёт As-Is → To-Be пишет карточка задачи, поэтому `## Wiki Updates` и `## As-Is -> To-Be Report` с неё не требуются. Карточка без метки или без `request:`, а также любая карточка при выключенной интеграции — обычные разделы. Форма заголовков проверяется одинаково. Если шапка карточки не читается, карточка считается обычной (требования строже).
6. Тесты проекта — всегда `/bin/bash <доска>/test.sh` в рабочей папке (без login-оболочки: полные пути пишутся в самом `test.sh`), в своей группе процессов; по таймауту убивается вся группа. Таймаут — `[timeouts] tests_s` (по умолчанию 900 с, заполняет `project-doctor`). Код не 0 — отказ. Код 0 — ищется последняя строка `PIPELINE_TESTS passed=<n> skipped=<n> failed=<n>` во всём выводе: нет строки, `failed` > 0, `passed` меньше замера или `skipped` больше замера — отказ.

   **С чем сравнивается (S4-25, режим истории).** Не с последним замером, а с замером **точки ответвления** ветки карточки: `git merge-base HEAD refs/heads/<base_branch>` (`base_branch` из `project.toml`; у подзадачи это тоже `our-main`, а не интеграционная ветка, то есть `our-main` момента плана). Ошибка `git` — отказ с причиной, не пропуск. Так карточка, начатая до того, как `our-main` получил новые тесты, не получает ложного «passed меньше базы» (случай OMS-8), а тест, выпавший относительно её точки, по-прежнему ловится. Действующий замер — строго:
   1. запись с `base_sha`, равным точке (`baseline_match: exact`);
   2. иначе ближайшая запись-предок точки, если между ней и точкой (`git diff --name-only --no-renames`) нет файла по правилу **этой доски** — файла, который меняет то, что измеряют тесты (`ancestor`). Правило доски: `[baseline] paths` из её `project.toml` (E2; заменяет правило целиком; шаблоны того же вида, что `forbidden_paths`; `Config.baseline_paths`, функция `project_config.paths_rule`), а без раздела — прежнее питоновское `project_config.affects_baseline` (`tests/`, `ours/tests/`, `test_*.py`, `*_test.py`, `conftest.py` на любом уровне, `pyproject.toml`, `uv.lock` и т. п.). Синтаксис шаблонов путей (`compile_glob`) живёт в `project_config.py`, `check.py` берёт его оттуда. Причина: `post-merge` перемеряет базу только когда слияние меняет такие файлы, поэтому после слияния одних документов конец `our-main` не замерян, и запись-предок для него так же верна, как собственная. Запись, коммита которой нет в репозитории, пропускается. Правило одно на двоих: его же использует `post_merge.py`;
   3. иначе замера нет (`unknown`): тесты идут, отказ только при коде не 0, без строки итогов или при `failed` > 0; в `check.log` отдельное событие `baseline_unknown` (`baseline_point`, `base_branch`, `reason`: «нет записи» или «между записью <sha> и точкой менялись файлы тестов: <до 5 путей>»). Событие пишется, только когда тесты действительно прогнаны (при пропуске по `doc_paths` и по записи «влито» его нет).

   В событиях `pass` / `fail` (`hook` и `gate`; у отката хука — в событии `rollback:*`) поля `baseline_match` (`exact` / `ancestor` / `unknown` / `legacy`), `baseline_sha` (пусто при `unknown`) и `baseline_point` (нет при `legacy`). Текст отказа «passed меньше базы» называет действующий замер: обе тройки чисел, ветку, коммит замера и точку ответвления; в режиме `legacy` текст прежний (обе тройки и подсказка перезапустить `project-doctor`).

**Лёгкий путь: правка только документов (S4-16).** Ключ `[checks] doc_paths` — список шаблонов путей (тот же синтаксис, что у `forbidden_paths`, без учёта регистра); по умолчанию пустой, и тогда ничего не меняется. Если множество изменённых путей (закоммиченные, в индексе, не в индексе, неотслеживаемые — то же, что видят проверки 3–4) **не пустое** и **каждый** путь совпадает с одним из шаблонов, `test.sh` не запускается: результат `ok`, в отчёте строка `tests skipped: only doc paths changed (N files)`, в журнале событие `pass` (`hook` и `gate` одинаково) с `reason` того же содержания и полем `tests: skipped-docs` (у пропуска по записи «влито» — `tests: skipped`). Пустое множество изменений — полный прогон, как раньше. Условия безопасности:

- **Быстрые проверки идут всегда** — конфиг, база, запрещённые пути, изменённые тесты, разделы карточки; пропускаются только тесты. Достаточно одного пути вне списка (файл кода в папке документов, если шаблон не ограничен расширением), и идёт полный прогон.
- В режиме `hook` при пропуске отметка `<ID>.pass.json` **пишется так же**, как после успешных тестов, иначе `integrate.py` не влил бы подзадачу.
- Порядок в `gate`: запись `.merged.json` забирается и удаляется первой; совпало дерево — пропуск по записи (`tests: skipped`); не совпало — проверяется `doc_paths` (`tests: skipped-docs`, `tests_reason` сохраняется); иначе полный прогон.
- Включать в список только то, что тесты точно не читают, и лучше с расширением `.md`. Решает код по фактически изменённым путям; агент на это не влияет (поля «класс карточки» нет, см. `docs/our/DECISIONS.md`, «Отступление: поле `class`»).
- Итоговая проверка задачи перед доставкой (шаг 7 дорожной карты, `.deliver`) обязана гонять полный набор независимо от `doc_paths`. `deliver.py` (S4-27) поэтому не считает проверку лёгким путём зелёной: смотрит поле `tests` события `hook pass` (см. ниже) и при `skipped-docs` отказывает; полный прогон во временной копии — S4-28.

**Одна проверка карточки за раз** — блокировка `.ours-state/<ID>.lock`. Второй `after_run` той же карточки (REPORT-10, «Риски», п. 1) при занятой блокировке пишет `skipped` и выходит. Шлюз ждёт освобождения не дольше `gate_ms/1000 − таймаут тестов − 30 с`, потом отказывает (с умолчаниями 960 000 мс и 900 с это 30 с).

**Карточка-задача (S4-21).** Для карточки с меткой `role:manager-plan` и разделом `## Plan Accepted` (`integrate.is_task_card`): (1) пропуска тестов по `[checks] doc_paths` нет ни в `hook`, ни в `gate` — всегда полный прогон, в отчёте и событии причина `task card: full suite (S4-16 п. 4)`; запись «влито» (`.merged.json`) шлюз для неё принимает **только** с `source` = `deliver/<её ID>` (её пишет `deliver.py merged` после слияния PR доставки, S4-27); запись подзадачи (`source` = `symphony/<ID>@<sha>`), запись без `source` и любая другая забираются и ничего не пропускают — полный прогон; (2) провал `hook` сразу уводит карточку в `needs_human`, а не в `In Progress` (в `In Progress` она получила бы промпт работника и чинила бы код сама, мимо подзадач; разбор — человек, позже `role:manager-diagnose`); раздел `## Check Failure` пишется как обычно; (3) обязательные разделы — обычные (`required_sections`: `## Wiki Updates`, `## As-Is -> To-Be Report`, их пишет Document).

**Событие `hook pass` (S4-27).** Рядом с отметкой `.pass.json` (её не меняли) в журнал `check.log` событие `pass` режима `hook` несёт поля `tree` и `head` (те же, что в отметке; нет их — полей нет) и `tests`: `full`, если `test.sh` действительно прогнан, `skipped-docs` — лёгкий путь. По ним `deliver.py` находит зелёную проверку: последнее **решающее** событие карточки (`hook pass`, `hook rollback:*`, `gate fail`) — `pass` с `tree` = дереву конца ветки и `tests` = `full`. Событие `gate` не менялось (у полного прогона поля `tests` в нём нет). Раздел `## Delivery` дописывается в конец существующего раздела (`APPEND_TO_SECTION`), как `## Subtask Progress`.

**Отметка «проверка пройдена» (S4-12).** Сразу после взятия блокировки, до прогона тестов, `check.py hook` считает **дерево содержимого** рабочей копии (`tree`): во временном индексе (`GIT_INDEX_FILE`) — `git read-tree HEAD`, `git add -A` с теми же исключениями, что у штатного блока (`kanban`, `.symphony`), `git write-tree`; настоящий индекс не трогается. Если проверка прошла, пишется `<доска>/.ours-state/<ID>.pass.json`: `{"ppid", "tree", "head", "at"}`. `ppid` — процесс оболочки хука (общий родитель `check.py` и `integrate.py`), `tree` — какое именно содержимое прошло тесты. Отметка одноразовая: `integrate.py hook` читает её и удаляет; она нужна ему, чтобы вливать только проверенное в этом же `after_run`. Старая отметка просто перезаписывается следующей успешной проверкой, а чужой `ppid` `integrate.py` не принимает. При провале проверки и в `check.py gate` отметка не пишется. Побочное следствие: если `test.sh` создаёт в рабочей копии файлы, не перечисленные в `.gitignore` проекта, дерево после тестов (оно попадёт в коммит штатного блока) отличается от проверенного, и вливание пропускается — такие файлы нужно игнорировать.

**Шлюз без повторного прогона тестов (S4-13).** После программного `Done` (S4-12) ядро само запускает `check.py gate` в той же рабочей копии. Содержимое то же, что только что прошло `check.py hook` и было влито, и второй прогон `test.sh` (5–10 минут) ничего бы не дал, а нестабильный тест мог бы отказать уже после вливания. Поэтому `integrate.py hook` после успешного `Done` пишет `<доска>/.ours-state/<ID>.merged.json` (`{"tree", "commit", "task", "branch", "source", "at"}`; `tree` — дерево из отметки `.pass.json`, `commit` — sha коммита в интеграционной ветке или `null`, если слияние ничего не изменило). Шлюз (только `gate`; `hook` запись не читает и не трогает) делает так:

- **Быстрые проверки идут всегда** — конфиг, база, запрещённые пути, изменённые тесты, разделы карточки. Они дешёвые, и запись их не отменяет: при их провале шлюз отказывает, как и раньше.
- Если они прошли, а запись есть, считается `worktree_tree` рабочей копии (та же функция, что в хуке: содержимое диска, временный индекс) и сравнивается с `tree` из записи. **Совпало** — тесты не запускаются; в отчёте строка `tests skipped: tree <12 знаков> passed check.py hook and was merged into <ветка> (<коммит|no changes>)`, в журнале событие `gate` `pass` с `tests: skipped`. **Не совпало** (файл правили после вливания) — полный прогон, как раньше; в событии `tests: full` и `tests_reason: tree differs from the merged one`.
- **Запись одноразовая.** Шлюз удаляет её, как только прочитал, — и при пропуске, и при несовпадении, и при провале быстрых проверок: второго шанса у неё нет. Нет записи (карточку к `Done` привели руками, `Done` после вливания не поставился) — полный прогон.

Дерево — это содержимое, а не история: схлопывание коммитов ядром (`finalize_delivery_history`: soft reset к базе и один коммит) дерево не меняет, поэтому сравнение остаётся верным. Пропуск касается только тестов.

Правила подключения, которые шаблон уже соблюдает: `check.py hook` — первой строкой `after_run` (у штатного блока есть ранний выход «нет изменений») и с `|| true` (иначе `bash` подменит себя скриптом, и при таймауте хука тесты останутся жить, REPORT-07, Q3); таймауты хука и шлюза больше таймаута тестов. `integrate.py hook` — последней строкой и тоже с `|| true`; штатный блок (коммит `wip: …`) завёрнут в подоболочку `( … )`, чтобы его `exit 0` при «нет изменений» не обрывал `after_run` до `integrate.py`.

## `integrate.py`

`ensure-branch <ЗАДАЧА>` — см. таблицу выше и раздел «Интеграционная ветка задачи» в `ours/README.md`. Здесь — подкоманда `hook`.

**`integrate.py hook`** запускается последней строкой `after_run` (рабочая папка — рабочая копия карточки; окружение `SYMPHONY_WORKFLOW_DIR`, `SYMPHONY_ISSUE_ID`, `SYMPHONY_PYTHON`, как у `check.py`). Код выхода всегда 0; любая ошибка — событие `error` в журнале и строка в stderr.

Условия (любое несовпадение — событие `skipped` с причиной, карточка и ветка не трогаются; при `[integration] enabled = false` хук выходит молча, без события):

1. карточка в состоянии `Human Review` — агент на этапе Document ставит его сам;
2. карточка — подзадача: метка `worker_label` и `request: <ЗАДАЧА>`; запись базы `<ID>.base.json` существует и её `task` равен этой задаче (то есть карточка стартовала от интеграционной ветки);
3. блокировка карточки взята (ждём до 5 с, чтобы не пересечься со шлюзом);
4. есть отметка `<ID>.pass.json` с `ppid`, равным родителю `integrate.py`, а `git rev-parse HEAD^{tree}` равно её полю `tree` (`commit --amend` штатного блока дерево не меняет, любая правка файла после проверки — меняет); отметка удаляется в любом случае;
5. рабочая копия чиста относительно `HEAD` (`git status --porcelain` с учётом `core.excludesFile`) — иначе штатный блок не закоммитил, а вливать незакоммиченное нельзя.

Вливание — в репозитории кода (`[project] repo`), ветка `integration/<ЗАДАЧА>`: `git merge-tree --write-tree` старого конца ветки и `HEAD` рабочей копии → `git commit-tree` с **одним родителем** (старый конец; сообщение `<ID>: <заголовок>` и строки `Task:`, `Source: symphony/<ID>@<sha>`; автор и коммитер `symphony <symphony@local>`) → `git update-ref` с проверкой старого значения. Ветку сдвинули за это время — одна повторная попытка от нового конца, вторая неудача считается конфликтом. Дерево слияния совпало с деревом ветки — коммит не создаётся.

Исходы:

- **влито / без изменений** → `symphony board mv <ID> Done` (путь — `[tools] symphony`), затем проверка, что состояние стало `Done`; в карточке раздел `## Integration` (`task`, `branch`, `source`, `commit` — sha или `no changes`, `check`, `moved to`); событие `done`. Если карточка не передвинулась — событие `error` и `moved to: Done FAILED`: код при этом уже влит, статус поправляет человек.
- **конфликт** → ветка не меняется; карточка в `needs_human`; в `## Integration` — `result: conflict`, причина, список файлов; событие `conflict`.
- **ошибка** (git упал, нет `symphony`, ветки нет, нет записи базы) → ничего не двигается; событие `error`, строка в stderr.

Карточка не в `Human Review` — выход **молча**, без события `skipped`: хук запускается после каждого хода каждой карточки, и иначе `check.log` рос бы по строке на ход. Остальные `skipped` (не подзадача, запись базы без `task`, блокировка, нет отметки, дерево не совпало, грязная копия) пишутся как раньше. «Грязная копия» считается по тем же путям, что у штатного блока и `worktree_tree` (без `kanban` и `.symphony`).

**Запись «влито» (S4-13).** После успешного `Done` (проверка состояния карточки прошла) пишется `<доска>/.ours-state/<ID>.merged.json` — см. «Шлюз без повторного прогона тестов» в разделе `check.py`; в событии `done` поле `merged_record: written`. Если `Done` не поставился, записи нет (`merged_record: not written`), и шлюз, придя позже, прогонит тесты полностью.

`Done` подзадаче ставит только `integrate.py` и только здесь; агент маршруты не вызывает, `allowed_bash` не расширялся. `Done` самой задачи ставит только человек.

**Ход задачи (S4-21).** После успешного `Done` хук дописывает в карточку-задачу (`request` подзадачи) строку `- <ПОДЗАДАЧА> merged (k of N)` в **один** раздел `## Subtask Progress` (S4-25: строка идёт в конец существующего раздела — до следующего заголовка `#` / `##`; если таких разделов несколько, как у карточек до S4-25, — в последний; нет раздела — создаётся; первую строку `0 of N merged` пишет `plan.py`): `N` — число подзадач в `## Plan Accepted`, `k` — сколько из них сейчас в `Done`. Правка карточки сбрасывает отсчёт автоархива ядра (30 дней). Запись идёт через трекер (частный метод ядра `FileBoardTracker._mutate_ticket`: под блокировкой карточки и с проверкой `updated_at`; запасной путь — то же преобразование текста файла под той же блокировкой `.locks/<ID>.lock`) под блокировкой карточки-**задачи** (не подзадачи); остальные разделы (`## Check Failure`, `## Integration` и др.) по-прежнему каждый раз новым; ошибка записи — только событие `error` (`progress` — удачная запись). Нет карточки задачи на доске или в ней нет `## Plan Accepted` (подзадача сделана вручную) — молча, ничего не пишется.

**Сигнал «все подзадачи готовы» (S4-21).** После строки прогресса, **вне всех блокировок вливания** (flock не вкладывается: повторное открытие того же файла блокировки в том же процессе ждёт само себя, а `finish_task` берёт свои блокировки заново), хук проверяет: карточка-задача в `Subtasks` и все ID из `## Plan Accepted` в `Done`. Тогда вызывается `finish_task`. Любая ошибка — событие `error` и строка в stderr, `Done` подзадачи уже стоит. Одна подзадача в `needs_human` — задача остаётся в `Subtasks`.

**Итоговая проверка: `finish_task` / `integrate.py finish-task <ЗАДАЧА> [--board <папка доски>]`.** «Карточка-задача» — метка `role:manager-plan` и раздел `## Plan Accepted` (`integrate.is_task_card`, одно определение для хука, `check.py` и команды). Рабочая копия — `<корень рабочих копий>/<ЗАДАЧА>` (`$SYMPHONY_WORKSPACE_ROOT`, который служба выдаёт хукам; руками — `~/symphony_workspaces/<имя проекта>`). Под блокировкой карточки-задачи и общей блокировкой рабочих копий:

1. *Не время* (не карточка-задача, не в `Subtasks`, не все подзадачи в `Done`): отказ с причиной, событие `final:refused`, ничего не меняется, код 1. Раннюю ручную команду не наказываем переводом в `needs_human`.
2. *Условия* (рабочая копия есть, это копия репозитория кода на `symphony/<ЗАДАЧА>`, чистая, в ветке руководителя нет правок относительно записи базы, ветки есть): иначе `needs_human`, `## Final Check` с причинами, событие `final:needs_human`, ветки не тронуты.
3. *Слияние.* `main` — предок конца `integration/<ЗАДАЧА>` — слияния нет. Иначе `git merge-tree --write-tree` → конфликт: `needs_human` со списком файлов, ветка не меняется; нет конфликта: `git commit-tree -p <int> -p <main>` (два родителя, сообщение `<ЗАДАЧА>: merge <база> for the final check`) → `git update-ref` с проверкой старого значения (сдвинули — один повтор с начала, вторая неудача — `needs_human`).
4. *Рабочая копия на цель:* `git reset --keep <цель>` (ветка `symphony/<ЗАДАЧА>` встаёт на тот же коммит, что `integration/<ЗАДАЧА>`).
5. *Дифф для Verify:* `<доска>/artifacts/<ЗАДАЧА>/work/final-diff.md` (`--name-status` и `--stat`, какие коммиты сравниваются) и `final-diff.patch` (полный дифф `main..цель`, до 200 КБ, дальше обрезка по границе строки и строка `обрезано, N КБ всего, полный дифф: git diff <main> <цель>`); запись не идёт сквозь ссылку. Их готовит программа, потому что `git diff` агенту не разрешён, а права мы не расширяем.
6. *Запись базы:* `base_sha` в `<ЗАДАЧА>.base.json` = использованный `main` (`final_from` — прежняя), `git config --worktree symphony.basesha`; `symphony.mergetargetbranch` и `symphony.basebranch` должны быть базовой веткой (`worktree.py` даёт их карточке-задаче сам, при расхождении `finish_task` исправляет): `## Merge Status` в Verify проверит слияние именно в неё. Теперь `check.py` видит правки `our-main` не как правки задачи.
7. `<ЗАДАЧА>.final.json`: `{"task", "branch", "integration_commit", "our_main", "merged", "at"}` — для будущей доставки (шаг 7), которая сравнит `our_main` с текущим.
8. Раздел `## Final Check` (ветка, концы веток, коммит слияния или `no merge needed`, строка «итоговая проверка: Verify → Document → Human Review, полный test.sh»), `board mv <ЗАДАЧА> Verify` с проверкой, событие `final:started`.

Ошибка на шагах 4–8 после сдвига веток — `needs_human`, а в `## Final Check` в разделе «Сдвинуто в ветках» сказано, что уже изменилось.

Где смотреть: `<доска>/.ours-state/check.log` (записи с `"mode": "integrate"`), раздел `## Integration` в карточке подзадачи, `## Subtask Progress` и `## Final Check` в карточке задачи, файл `<ЗАДАЧА>.final.json`, отметка `<доска>/.ours-state/<ID>.pass.json` (существует только между `check.py hook` и `integrate.py hook` одного хода), запись `<ID>.merged.json` (между `integrate.py hook` и следующим `check.py gate`).

## `deliver.py`

Ветка уже есть на GitHub — отказ. Локальные ветки клона и рабочая копия карточки не меняются никогда.
5а. **Ключ в диффе (E1b).** Перед пушем та же проверка, что в `check.py` (`check.diff_key_hits`), по добавленным строкам `git diff <base>..<D>`, а также по заголовку и описанию PR (описание собирается из карточки, её пишет агент). Найдено — отказ «в добавленных строках найден ключ API Anthropic (sk-ant-…): <путь>:<номер строки>» или «в заголовке или описании PR найден ключ…»; ничего не пушится и не открывается, сама строка нигде не печатается.
6. Сразу после пуша — запись `.delivered.json` (`id`, `kind`, `source`, `source_commit`, `source_tree`, `commit`, `our_main`, `recheck: false`, `repo`, `base`, `branch`, `pr`, `at`). Потом `gh pr list --head deliver/<ID>` (PR уже есть — записать, второй не создавать), иначе `gh pr create --repo --base --head --title --body-file`. Описание — отчёт As-Is → To-Be, у карточки-задачи — список подзадач, итог проверки; не больше 60 000 знаков. Потом раздел `## Delivery` в карточке, событие `delivered`, `git fetch origin` в основной папке (только если её `origin` — тот же репозиторий).
7. Сбой `gh pr create` после пуша: запись остаётся с `pr: null`, код 2; повторный `push` пропускает пуш (ветка на GitHub указывает ровно на `commit` записи), находит или создаёт PR.

**`deliver merged <ID>`** — вызывает очередь после успешного `gh pr merge` ветки `deliver/<ID>`. Пишет `<ID>.merged.json` (формат S4-13; `source` = `deliver/<ID>`, `commit` = D, `tree` = дерево D, `task: null`, `branch` = `base`) — для **обоих** видов карточек: шлюз при `Done` увидит то же дерево и не будет гонять тесты повторно (дерево доставки уже прошло полный прогон). Дописывает в `## Delivery` строку «PR влит», событие `merged`, в `.delivered.json` — `merged_at`. Повторно слияние не отмечается.

Где смотреть: `check.log` (`"mode": "deliver"`), раздел `## Delivery` в карточке, `<доска>/.ours-state/<ID>.delivered.json`, отчёты `tmp_workspaces/outbox/<ID>.deliver.log` и `<ID>.merge.log`.

## Где смотреть результат

- `<доска>/.ours-state/check.log` — журнал проверок (JSON-строки: время, ID, режим, исход, причина).
- `<доска>/.ours-state/<ID>.json` — счётчик провалов (сам не сбрасывается).
- `<доска>/.ours-state/<ID>.base.json` — база карточки.
- `<доска>/.ours-state/<ЗАДАЧА>.plan.json` — счётчик провалов плана (S4-19); после принятого плана файла нет.
- `<доска>/.ours-state/<ID>.pass.json` — одноразовая отметка «проверка этого хода пройдена» (S4-12); обычно её нет.
- `<доска>/.ours-state/<ID>.merged.json` — одноразовая запись «это дерево влито в интеграционную ветку» (S4-13): `tree`, `commit`, `task`, `branch`, `source`, `at`. Её читает и удаляет `check.py gate`; пока шлюз не пришёл, лежит. Обычно её нет.
- `<доска>/.ours-state/<ID>.delivered.json` — запись доставки (S4-27): ветка `deliver/<ID>`, коммит D, источник, PR (`null`, пока PR не создан), `merged_at` после слияния. Обычно есть у доставленных карточек; чтобы доставить заново, её удаляет человек.
- `<доска>/.ours-state/baseline.json` — последний замер базовой ветки (`project-doctor`): `base_branch`, `base_sha`, `passed`, `skipped`, `failed`, `setup_s`, `tests_s`, `measured_at`.
- `<доска>/.ours-state/baselines.json` — история замеров (S4-25): `{"version": 1, "records": [...]}`, записи (те же поля) от старых к новым, одна на коммит ветки, последние 50. С неё `check.py` берёт замер точки ответвления карточки.
- Разделы `## Check Failure`, `## Integration`, `## Plan Accepted`, `## Plan Failure` и `## Subtask Progress` в карточке; вывод хуков — в `.symphony-workspace-hook-output/<ID>/` рядом с рабочими папками.
