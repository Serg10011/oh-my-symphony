# Хуки конвейера

Здесь четыре программы на Python ≥ 3.11 (только стандартная библиотека, POSIX). Все они вызываются из `WORKFLOW.md`, который собирается из общего шаблона `ours/templates/WORKFLOW.md.tmpl` командой `ours/bin/project-render` — руками строки в `WORKFLOW.md` не вписываются. `$SYMPHONY_WORKFLOW_DIR` для них — папка доски проекта (`~/symphony-projects/<имя>/`), настройки — её `project.toml`.

| Файл | Где вызывается | Что делает |
|---|---|---|
| `worktree.py create` | `hooks.after_create` | рабочая копия карточки `symphony/<ID>` от базовой ветки, ссылки в папку доски, запись базы, `setup.sh` |
| `worktree.py remove` | `hooks.before_remove` | убирает ссылки в папку доски, затем штатная уборка `_worktree_cleanup` |
| `check.py hook` | первая строка `hooks.after_run` | механические проверки, если карточка в `Done` / `Human Review`; при провале — откат |
| `check.py gate` | `agent.done_gate_command` | те же проверки при приёмке Done; код 0 — пропуск |
| `summarize.py <junit.xml>` | последняя строка `test.sh` | печатает строку итогов `PIPELINE_TESTS passed=… skipped=… failed=…` по отчёту JUnit XML |
| `project_config.py` | библиотека | разбор `project.toml`, раскладка папки доски, сборка `WORKFLOW.md`, строка итогов и замер базы, правка `[timeouts]` |

## `worktree.py`

**create.** ID карточки — имя рабочей папки; он обязан начинаться с `<id_prefix>-` из `project.toml`, иначе отказ. Проверяется, что папка доски не лежит внутри git-репозитория (иначе git молча взял бы чужой репозиторий, REPORT-09, п. 17).

- Если папка уже рабочая копия репозитория кода на ветке `symphony/<ID>` (ядро повторно вызвало хук на той же папке) — режим **«обновить»**: восстанавливаются только ссылки, исключения и отсутствующая запись базы. Ветка не переименовывается, `setup.sh` не запускается — иначе пропала бы работа карточки.
- Иначе — **чистый старт** под блокировкой `<git-common-dir кода>/symphony-worktree.lock` (тот же файл, что у штатного скрипта; `fcntl`, команда `flock` не нужна): штатная подготовка `_worktree_cleanup --prepare-setup`; прежняя ветка `symphony/<ID>` переименовывается в `attempts/<ID>-<UTC>`, прежние артефакты `artifacts/<ID>` — в `artifacts/.attempts/<ID>-<UTC>` (иначе старые файлы прошли бы контракты новой попытки); `git worktree add … -b symphony/<ID> refs/heads/<база>`; настройки рабочей копии (`symphony.basesha`, `symphony.basebranch`, `symphony.mergetargetbranch`, `symphony.autocommitExclude`, `core.excludesFile = <доска>/worktree-exclude`); запись базы `<доска>/.ours-state/<ID>.base.json`; ссылки `kanban`, `docs/<ID>` и `docs/llm-wiki` в папку доски; затем `/bin/bash <доска>/setup.sh` в рабочей папке.
- Если `setup.sh` упал (или не уложился в `hooks_ms` − 30 с), рабочая копия и новая ветка убираются, старая ветка, артефакты и запись базы возвращаются на место, код выхода 1.
- Если `docs/llm-wiki` уже есть в репозитории кода, ссылка не создаётся (предупреждение в выводе хука).

**remove.** Удаляет только те ссылки, что ведут в папку доски, потом вызывает штатный `_worktree_cleanup` с `SYMPHONY_WORKFLOW_DIR = <репозиторий кода>`. Ветки не трогает.

В репозитории кода от хуков меняется только содержимое `.git`: ветки `symphony/*` и `attempts/*`, регистрация рабочих копий, `extensions.worktreeConfig` и файл блокировки. `.git/info/exclude` не трогается.

## `check.py`

Проверки по порядку (подробно — REPORT-07):

1. Конфиг — `<доска>/project.toml`: базовая ветка из `[project]`, путь к `symphony` из `[tools]`, правила из `[checks]` (в том числе `allow_paths`: открывает агенту отдельные пути в `ours/`, но не контур `ours/hooks/**`, `ours/bin/**`, `ours/templates/**` и не другие запреты), таймауты из `[timeouts]`. Неизвестный раздел или ключ — отказ (опечатка не должна отключить проверку); старый `[checks] test_timeout_s` — отказ с подсказкой перенести в `[timeouts] tests_s`. Замер базы — `<доска>/.ours-state/baseline.json` (пишет `project-doctor`): нет файла, он повреждён или снят на другой ветке — отказ «запусти project-doctor», тесты не запускаются. Файлы из рабочей папки агента не читаются никогда.
2. База — `base_sha` из `.ours-state/<ID>.base.json` (её пишет `worktree.py` при создании рабочей копии). Нет записи — отказ; `base_sha` не предок `HEAD` — отказ («ветка переписана относительно базы»). Слияние с подвижной веткой больше не используется: после вливания ветки в целевую проверки ослепли бы.
3. Запрещённые пути, 4. неизменность существующих тестов, 5. разделы карточки — как в K05.
6. Тесты проекта — всегда `/bin/bash <доска>/test.sh` в рабочей папке (без login-оболочки: полные пути пишутся в самом `test.sh`), в своей группе процессов; по таймауту убивается вся группа. Таймаут — `[timeouts] tests_s` (по умолчанию 900 с, заполняет `project-doctor`). Код не 0 — отказ. Код 0 — ищется последняя строка `PIPELINE_TESTS passed=<n> skipped=<n> failed=<n>` во всём выводе: нет строки, `failed` > 0, `passed` меньше базы или `skipped` больше базы — отказ; в тексте отказа обе тройки чисел и подсказка перезапустить `project-doctor`, если базовая ветка менялась.

**Одна проверка карточки за раз** — блокировка `.ours-state/<ID>.lock`. Второй `after_run` той же карточки (REPORT-10, «Риски», п. 1) при занятой блокировке пишет `skipped` и выходит. Шлюз ждёт освобождения не дольше `gate_ms/1000 − таймаут тестов − 30 с`, потом отказывает (с умолчаниями 960 000 мс и 900 с это 30 с).

Правила подключения, которые шаблон уже соблюдает: `check.py hook` — первой строкой `after_run` (у штатного блока есть ранний выход «нет изменений») и с `|| true` (иначе `bash` подменит себя скриптом, и при таймауте хука тесты останутся жить, REPORT-07, Q3); таймауты хука и шлюза больше таймаута тестов.

## Где смотреть результат

- `<доска>/.ours-state/check.log` — журнал проверок (JSON-строки: время, ID, режим, исход, причина).
- `<доска>/.ours-state/<ID>.json` — счётчик провалов (сам не сбрасывается).
- `<доска>/.ours-state/<ID>.base.json` — база карточки.
- `<доска>/.ours-state/baseline.json` — замер базовой ветки (`project-doctor`): `base_branch`, `base_sha`, `passed`, `skipped`, `failed`, `setup_s`, `tests_s`, `measured_at`.
- Раздел `## Check Failure` в карточке; вывод хуков — в `.symphony-workspace-hook-output/<ID>/` рядом с рабочими папками.
