# Хуки конвейера

Здесь шесть программ на Python ≥ 3.11 (только стандартная библиотека, POSIX). Все они вызываются из `WORKFLOW.md`, который собирается из общего шаблона `ours/templates/WORKFLOW.md.tmpl` командой `ours/bin/project-render` — руками строки в `WORKFLOW.md` не вписываются. `$SYMPHONY_WORKFLOW_DIR` для них — папка доски проекта (`~/symphony-projects/<имя>/`), настройки — её `project.toml`.

| Файл | Где вызывается | Что делает |
|---|---|---|
| `worktree.py create` | `hooks.after_create` | рабочая копия карточки `symphony/<ID>` от базовой ветки, ссылки в папку доски, запись базы, `setup.sh` |
| `worktree.py remove` | `hooks.before_remove` | убирает ссылки в папку доски, затем штатная уборка `_worktree_cleanup` |
| `integrate.py ensure-branch <ЗАДАЧА>` | вручную; позже — хук нарезки | создаёт интеграционную ветку задачи `integration/<ЗАДАЧА>` от базовой, если её нет; существующую не трогает. Как библиотека — для `worktree.py` (S4-11) |
| `integrate.py hook` | последняя строка `hooks.after_run` | вливает готовую подзадачу в интеграционную ветку задачи и ставит ей `Done` (S4-12); всегда код 0 |
| `check.py hook` | первая строка `hooks.after_run` | механические проверки, если карточка в `Done` / `Human Review`; при провале — откат; при успехе пишет отметку `<ID>.pass.json` |
| `check.py gate` | `agent.done_gate_command` | те же проверки при приёмке Done; код 0 — пропуск |
| `summarize.py <junit.xml>` | последняя строка `test.sh` | печатает строку итогов `PIPELINE_TESTS passed=… skipped=… failed=…` по отчёту JUnit XML |
| `project_config.py` | библиотека | разбор `project.toml`, раскладка папки доски, сборка `WORKFLOW.md`, строка итогов и замер базы, правка `[timeouts]` |

## `worktree.py`

**create.** ID карточки — имя рабочей папки; он обязан начинаться с `<id_prefix>-` из `project.toml`, иначе отказ. Проверяется, что папка доски не лежит внутри git-репозитория (иначе git молча взял бы чужой репозиторий, REPORT-09, п. 17).

- Если папка уже рабочая копия репозитория кода на ветке `symphony/<ID>` (ядро повторно вызвало хук на той же папке) — режим **«обновить»**: восстанавливаются только ссылки, исключения и отсутствующая запись базы. Ветка не переименовывается, `setup.sh` не запускается — иначе пропала бы работа карточки.
- Иначе — **чистый старт** под блокировкой `<git-common-dir кода>/symphony-worktree.lock` (тот же файл, что у штатного скрипта; `fcntl`, команда `flock` не нужна): штатная подготовка `_worktree_cleanup --prepare-setup`; прежняя ветка `symphony/<ID>` переименовывается в `attempts/<ID>-<UTC>`, прежние артефакты `artifacts/<ID>` — в `artifacts/.attempts/<ID>-<UTC>` (иначе старые файлы прошли бы контракты новой попытки); `git worktree add … -b symphony/<ID> refs/heads/<база>`; настройки рабочей копии (`symphony.basesha`, `symphony.basebranch`, `symphony.mergetargetbranch`, `symphony.autocommitExclude`, `core.excludesFile = <доска>/worktree-exclude`); запись базы `<доска>/.ours-state/<ID>.base.json`; ссылки `kanban`, `docs/<ID>` и `docs/llm-wiki` в папку доски; затем `/bin/bash <доска>/setup.sh` в рабочей папке.
- **База подзадачи (S4-11).** Только при `[integration] enabled = true` в `project.toml`. Тогда в чистом старте читается шапка карточки `<доска>/kanban/<ID>.md` (нет файла — отказ; при `enabled = false` карточка не читается вовсе). Карточка с меткой `worker_label` (по умолчанию `role:worker`) и полем `request: <ЗАДАЧА>` — подзадача: рабочая копия берётся не от `refs/heads/<база>`, а от конца ветки `<branch_prefix><ЗАДАЧА>` (`integration/<ЗАДАЧА>`), и `symphony.basebranch` с `symphony.mergetargetbranch` получают это имя. Если ветки ещё нет, `worktree.py` создаёт её от базовой — под той же блокировкой, после штатной подготовки и до переименования старой ветки, чтобы две подзадачи не создали её вразнобой; существующая ветка никогда не пересоздаётся и не сдвигается. Неверный `request` (не по шаблону ID, чужой префикс, сама карточка) — отказ, код 1: лучше остановить, чем молча стартовать от базовой. Обычная карточка (нет метки или `request`) стартует от базовой, как раньше. В запись базы добавлены поля `start_branch` (откуда взята копия: `our-main` или `integration/<ЗАДАЧА>`) и `task` (`null` для обычной карточки); `base_branch` остаётся веткой проекта, на которой снят `baseline.json`. `check.py` читает из записи только `base_sha`. При откате созданная интеграционная ветка не удаляется: на неё могла встать другая подзадача.
- Если `setup.sh` упал (или не уложился в `hooks_ms` − 30 с), рабочая копия и новая ветка убираются, старая ветка, артефакты и запись базы возвращаются на место, код выхода 1.
- Если `docs/llm-wiki` уже есть в репозитории кода, ссылка не создаётся (предупреждение в выводе хука).

**remove.** Удаляет только те ссылки, что ведут в папку доски, потом вызывает штатный `_worktree_cleanup` с `SYMPHONY_WORKFLOW_DIR = <репозиторий кода>`. Ветки не трогает.

В репозитории кода от хуков меняется только содержимое `.git`: ветки `symphony/*` и `attempts/*`, регистрация рабочих копий, `extensions.worktreeConfig` и файл блокировки. `.git/info/exclude` не трогается.

## `check.py`

Проверки по порядку (подробно — REPORT-07):

1. Конфиг — `<доска>/project.toml`: базовая ветка из `[project]`, путь к `symphony` из `[tools]`, правила из `[checks]` (в том числе `allow_paths`: открывает агенту отдельные пути в `ours/`, но не контур `ours/hooks/**`, `ours/bin/**`, `ours/templates/**` и не другие запреты), таймауты из `[timeouts]`. Неизвестный раздел или ключ — отказ (опечатка не должна отключить проверку); старый `[checks] test_timeout_s` — отказ с подсказкой перенести в `[timeouts] tests_s`. Замер базы — `<доска>/.ours-state/baseline.json` (пишет `project-doctor`): нет файла, он повреждён или снят на другой ветке — отказ «запусти project-doctor», тесты не запускаются. Файлы из рабочей папки агента не читаются никогда.
2. База — `base_sha` из `.ours-state/<ID>.base.json` (её пишет `worktree.py` при создании рабочей копии). Нет записи — отказ; `base_sha` не предок `HEAD` — отказ («ветка переписана относительно базы»). Слияние с подвижной веткой больше не используется: после вливания ветки в целевую проверки ослепли бы.
3. Запрещённые пути, 4. неизменность существующих тестов, 5. разделы карточки — как в K05.
6. Тесты проекта — всегда `/bin/bash <доска>/test.sh` в рабочей папке (без login-оболочки: полные пути пишутся в самом `test.sh`), в своей группе процессов; по таймауту убивается вся группа. Таймаут — `[timeouts] tests_s` (по умолчанию 900 с, заполняет `project-doctor`). Код не 0 — отказ. Код 0 — ищется последняя строка `PIPELINE_TESTS passed=<n> skipped=<n> failed=<n>` во всём выводе: нет строки, `failed` > 0, `passed` меньше базы или `skipped` больше базы — отказ; в тексте отказа обе тройки чисел и подсказка перезапустить `project-doctor`, если базовая ветка менялась.

**Одна проверка карточки за раз** — блокировка `.ours-state/<ID>.lock`. Второй `after_run` той же карточки (REPORT-10, «Риски», п. 1) при занятой блокировке пишет `skipped` и выходит. Шлюз ждёт освобождения не дольше `gate_ms/1000 − таймаут тестов − 30 с`, потом отказывает (с умолчаниями 960 000 мс и 900 с это 30 с).

**Отметка «проверка пройдена» (S4-12).** Сразу после взятия блокировки, до прогона тестов, `check.py hook` считает **дерево содержимого** рабочей копии (`tree`): во временном индексе (`GIT_INDEX_FILE`) — `git read-tree HEAD`, `git add -A` с теми же исключениями, что у штатного блока (`kanban`, `.symphony`), `git write-tree`; настоящий индекс не трогается. Если проверка прошла, пишется `<доска>/.ours-state/<ID>.pass.json`: `{"ppid", "tree", "head", "at"}`. `ppid` — процесс оболочки хука (общий родитель `check.py` и `integrate.py`), `tree` — какое именно содержимое прошло тесты. Отметка одноразовая: `integrate.py hook` читает её и удаляет; она нужна ему, чтобы вливать только проверенное в этом же `after_run`. Старая отметка просто перезаписывается следующей успешной проверкой, а чужой `ppid` `integrate.py` не принимает. При провале проверки и в `check.py gate` отметка не пишется. Побочное следствие: если `test.sh` создаёт в рабочей копии файлы, не перечисленные в `.gitignore` проекта, дерево после тестов (оно попадёт в коммит штатного блока) отличается от проверенного, и вливание пропускается — такие файлы нужно игнорировать.

Правила подключения, которые шаблон уже соблюдает: `check.py hook` — первой строкой `after_run` (у штатного блока есть ранний выход «нет изменений») и с `|| true` (иначе `bash` подменит себя скриптом, и при таймауте хука тесты останутся жить, REPORT-07, Q3); таймауты хука и шлюза больше таймаута тестов. `integrate.py hook` — последней строкой и тоже с `|| true`; штатный блок (коммит `wip: …`) завёрнут в подоболочку `( … )`, чтобы его `exit 0` при «нет изменений» не обрывал `after_run` до `integrate.py`.

## `integrate.py`

`ensure-branch <ЗАДАЧА>` — см. таблицу выше и раздел «Интеграционная ветка задачи» в `ours/README.md`. Здесь — подкоманда `hook`.

**`integrate.py hook`** запускается последней строкой `after_run` (рабочая папка — рабочая копия карточки; окружение `SYMPHONY_WORKFLOW_DIR`, `SYMPHONY_ISSUE_ID`, `SYMPHONY_PYTHON`, как у `check.py`). Код выхода всегда 0; любая ошибка — событие `error` в журнале и строка в stderr.

Условия (любое несовпадение — событие `skipped` с причиной, карточка и ветка не трогаются; при `[integration] enabled = false` хук выходит молча, без события):

1. карточка в состоянии `Human Review` — агент на этапе Document ставит его сам;
2. карточка — подзадача: метка `worker_label` и `request: <ЗАДАЧА>`; запись базы `<ID>.base.json` существует и её `task` равен этой задаче (то есть карточка стартовала от интеграционной ветки);
3. блокировка карточки взята (ждём до 5 с, чтобы не пересечься со шлюзом);
4. есть отметка `<ID>.pass.json` с `ppid`, равным родителю `integrate.py`, а `git rev-parse HEAD^{tree}` равно её полю `tree` (`commit --amend` штатного блока дерево не меняет, любая правка файла после проверки — меняет); отметка удаляется в любом случае;
5. рабочая копия чиста относительно `HEAD` (`git status --porcelain` с учётом `core.excludesFile`) — иначе штатный блок не закоммитил, а вливать незакоммиченное нельзя.

Вливание — в репозитории кода (`[project] repo`), ветка `integration/<ЗАДАЧА>`: `git merge-tree --write-tree` старого конца ветки и `HEAD` рабочей копии → `git commit-tree` с **одним родителем** (старый конец; сообщение `<ID>: <заголовок>` и строки `Task:`, `Source: symphony/<ID>@<sha>`; автор и коммитер `symphony <symphony@local>`) → `git update-ref` с проверкой старого значения. Ветку сдвинули за это время — одна повторная попытка от нового конца, вторая неудача считается конфликтом. Дерево слияния совпало с деревом ветки — коммит не создаётся.

Исходы:

- **влито / без изменений** → `symphony board mv <ID> Done` (путь — `[tools] symphony`), затем проверка, что состояние стало `Done`; в карточке раздел `## Integration` (`task`, `branch`, `source`, `commit` — sha или `no changes`, `check`, `moved to`); событие `done`. Если карточка не передвинулась — событие `error` и `moved to: Done FAILED`: код при этом уже влит, статус поправляет человек.
- **конфликт** → ветка не меняется; карточка в `needs_human`; в `## Integration` — `result: conflict`, причина, список файлов; событие `conflict`.
- **ошибка** (git упал, нет `symphony`, ветки нет, нет записи базы) → ничего не двигается; событие `error`, строка в stderr.

`Done` подзадаче ставит только `integrate.py` и только здесь; агент маршруты не вызывает, `allowed_bash` не расширялся. `Done` самой задачи ставит только человек.

Где смотреть: `<доска>/.ours-state/check.log` (записи с `"mode": "integrate"`), раздел `## Integration` в карточке, отметка `<доска>/.ours-state/<ID>.pass.json` (существует только между `check.py hook` и `integrate.py hook` одного хода).

## Где смотреть результат

- `<доска>/.ours-state/check.log` — журнал проверок (JSON-строки: время, ID, режим, исход, причина).
- `<доска>/.ours-state/<ID>.json` — счётчик провалов (сам не сбрасывается).
- `<доска>/.ours-state/<ID>.base.json` — база карточки.
- `<доска>/.ours-state/<ID>.pass.json` — одноразовая отметка «проверка этого хода пройдена» (S4-12); обычно её нет.
- `<доска>/.ours-state/baseline.json` — замер базовой ветки (`project-doctor`): `base_branch`, `base_sha`, `passed`, `skipped`, `failed`, `setup_s`, `tests_s`, `measured_at`.
- Разделы `## Check Failure` и `## Integration` в карточке; вывод хуков — в `.symphony-workspace-hook-output/<ID>/` рядом с рабочими папками.
