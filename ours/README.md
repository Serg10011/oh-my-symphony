# Наши скрипты, хуки и шаблоны

Термины — в [docs/our/GLOSSARY.md](../docs/our/GLOSSARY.md)

Здесь всё, что мы добавляем к oh-my-symphony снаружи ядра. Каждый проект подключается одинаково: у него есть **папка доски** вне репозитория кода, а в самом репозитории кода ничего нашего не появляется.

| Папка | Что внутри |
|---|---|
| `bin/` | `project-new` (создать папку доски), `project-doctor` (проверить готовность и замерить базу), `project-render` (пересобрать `WORKFLOW.md`), `project-launchd` (записать `launchd.plist` для автозапуска на Mac) |
| `hooks/` | `worktree.py` (рабочие копии карточек), `check.py` (механические проверки), `integrate.py` (вливание подзадач, итоговая проверка задачи), `plan.py` (план-файл руководителя → карточки подзадач, сводка лимитов), `summarize.py` (строка итогов тестов из одного или нескольких отчётов JUnit XML), `project_config.py` (общая библиотека); подробности — `hooks/README.md` |
| `templates/` | `WORKFLOW.md.tmpl` — общий шаблон, в нём собраны все решения из `docs/our/DECISIONS.md` |
| `prompts/` | копия штатных промптов с нашими правками; список правок — `prompts/CHANGES.md` |
| `tests/` | тесты на временных git-репозиториях и сквозной прогон `tests/e2e/run.sh` |

## Термины

- **Репозиторий кода** — git-репозиторий проекта, с которым работает агент.
- **Папка доски** — `~/symphony-projects/<имя>/`, в ней настройки и доска проекта. Сама она не git-репозиторий и не должна лежать внутри него.
- **Рабочая копия** (worktree) — отдельная папка карточки `~/symphony_workspaces/<имя>/<ID>`, привязанная к репозиторию кода, на ветке `symphony/<ID>`.

## Что лежит в папке доски

| Файл | Зачем |
|---|---|
| `project.toml` | единственный файл настроек: путь к репозиторию, базовая ветка, префикс ID, порт, пути к программам, правила проверок, права агента (`[agent]`), модель службы (`[service]`), уровни задач (`[levels]`), таймауты, лимиты ходов |
| `setup.sh` | готовит свежую рабочую копию (установка зависимостей) |
| `test.sh` | полный прогон тестов; код 0 = зелено, в конце — строка итогов (ниже) |
| `WORKFLOW.md` | собирается из шаблона; **руками не правится**: `project-render` и `project-doctor` пересоздают его по шаблону и `project.toml`, ручные правки живут только до их следующего запуска |
| `launchd.plist`, `log/` | автозапуск через launchd (`project-launchd`) и лог службы `log/symphony.log` |
| `card-template.md` | образец карточки с подсказками: строка `level:` и строка «Уровень: … — почему такой» (в доску не попадает, копируешь вручную) |
| `kanban/` | доска с карточками |
| `artifacts/<ID>/`, `wiki/` | артефакты агента; в рабочей копии видны как `docs/<ID>/` и `docs/llm-wiki/`, в git не попадают |
| `worktree-exclude` | что git в рабочих копиях не должен видеть |
| `.ours-state/` | состояние наших скриптов: база каждой карточки, замеры базовой ветки (`baseline.json` — последний, `baselines.json` — история), журнал проверок, счётчики |

## Как подключить проект

Все команды запускать тем Python, в который установлен оркестратор (тот же, что `symphony`): его путь попадёт в настройки. Порядок проверен пробой на Mac (K13).

1. **Создать папку доски.**
   ```bash
   /путь/к/python ~/oh-my-symphony/ours/bin/project-new eve \
     --repo ~/code/eve --base dev --prefix EVE --port 9971
   ```
   Команда откажет и ничего не создаст, если: папка уже есть; путь — не корень git-репозитория; нет ветки `dev`; папка доски оказалась бы внутри git-репозитория; имя или префикс в неверном формате (имя — строчные буквы, цифры и `-`; префикс — 2–10 заглавных букв и цифр); порт или префикс уже заняты другим проектом в той же папке; не найден `claude`, `python` или `symphony`.
2. **Заполнить `setup.sh` и `test.sh`.** Обе заготовки выходят с кодом 1 «не настроено» и содержат строку-метку `OURS-STUB` — её надо удалить вместе с двумя последними строками (`echo`, `exit 1`), иначе `project-doctor` не пропустит. В скриптах — полные пути к программам (login-оболочка не используется). Контракт `test.sh` — ниже; подсказки про бедное окружение службы, лимит файлов и тесты с таймингом — в комментариях заготовок и в разделе «Окружение службы».
3. **Заполнить `project.toml`.**
   - `[checks]`: запрещённые пути `forbidden_paths` (сюда же — файлы запуска тестов: `package.json`, конфиг раннера), `allow_paths` (какие пути в `ours/` открыть агенту; контур не открывается — см. выше), шаблоны файлов тестов `test_globs`, исключения `allow_modified_tests`, `required_sections`, `worker_required_sections` (разделы для подзадачи, по умолчанию `## QA Evidence` и `## Merge Status`: у подзадачи нет этапа Document, wiki и отчёт пишет задача; кто подзадача — см. «Интеграционная ветка задачи»), `doc_paths` (шаблоны путей, правка только которых не требует полного прогона тестов: быстрые проверки идут всегда; включать лишь то, что тесты точно не читают, лучше с расширением `.md`; по умолчанию пусто; перед доставкой задачи полный прогон всё равно будет), `max_check_failures`. Неизвестный ключ — ошибка.
   - **`[agent] allowed_bash`** — права агента; **заполнить до первой карточки** (раздел «Права агента»).
   - `[service] model` — только если службе нужна своя модель (раздел «Запуск через launchd»). Модель уровня (`[levels]`) важнее неё.
   - `[levels]` — модель и усилие по уровням задач; в заготовке уже конфигурация B, значения стартовые (раздел «Уровни задач»).
   - `[limits]` — лимиты ходов; в заготовке уже строгие, для облачных моделей (раздел «Ходы, попытки и лимиты»).
   - `[integration]` — интеграционная ветка задачи (раздел «Интеграционная ветка задачи»); три необязательных ключа: `enabled` (по умолчанию `false`), `branch_prefix` (по умолчанию `"integration/"`; должен кончаться на `/`, не `symphony/` и не `attempts/`), `worker_label` (по умолчанию `"role:worker"`, без учёта регистра). В заготовке — закомментированным блоком. Включать, когда подзадачам одной задачи нужно видеть код друг друга. При `enabled = true` ключ `[agent] max_concurrent_agents` должен быть 1 (умолчание): вливание и `Done` подзадачи рассчитаны на одного агента, одно вливание за раз; иначе `project.toml` не принимается. Оставь `false`, если интеграция не нужна.
4. **Остановить службу проекта (если была запущена), проверить и замерить: `project-doctor`.**
   ```bash
   /путь/к/python ~/oh-my-symphony/ours/bin/project-doctor eve
   ```
   Печатает список PASS / FAIL / WARN, код 0 — только без FAIL. Проверяет `project.toml`, программы из `[tools]` (`claude --version`), репозиторий и базовую ветку, что папка доски не внутри git, что порт и префикс не заняты соседним проектом, что `setup.sh` и `test.sh` — не заготовки. Затем делает **пробную рабочую копию** базовой ветки (временная папка вне доски и кода, без новых веток, всегда удаляется), гоняет в ней `setup.sh` и `test.sh` (предел — час на каждый) и требует: код 0, строка итогов, `failed=0`. Числа и время пишет в `.ours-state/baseline.json` (последний замер) и добавляет в историю `.ours-state/baselines.json` (одна запись на коммит базовой ветки, последние 50; если истории ещё нет, первой записью становится прежний `baseline.json`; неудачный замер не меняет ни один из файлов), по замеру заполняет `[timeouts]` (правится только этот раздел, остальной текст файла не меняется), пересобирает `WORKFLOW.md` и запускает `symphony doctor`. Два WARN ядра ожидаемы и помечены «известно»: `git history writable` (папка доски — не git) и `agent git grant` (абсолютный путь к `claude`). **Пока служба этого проекта запущена, `symphony doctor` пожалуется на занятый порт — поэтому службу перед `project-doctor` останавливают.**
   **`project-doctor` перезапускает `post-merge`, когда слияние в базовую ветку меняло тесты** (добавили, убрали, пропустили; правило — `project_config.affects_baseline`), вручную — после правок вне слияния. Историю замеров ведёт сам `project-doctor`; `check.py` сравнивает карточку не с последним замером, а с замером **точки ответвления** её ветки (ближайшая запись-предок подходит, если между ней и точкой не менялись файлы тестов; иначе замера нет — тесты идут, отказ только при падении, в журнале `baseline_unknown`). Поэтому слияние новых тестов в `our-main` во время работы карточек не даёт ложного «passed меньше базы».
   Недетерминированные падения при первом прогоне (на пробе — 113 падений, в одном воспроизведении sqlite «unable to open database file») — повод проверить лимит открытых файлов, см. «Окружение службы».
5. **Пересобрать `WORKFLOW.md`**, если менялся `project.toml` без `project-doctor`: `ours/bin/project-render eve` — покажет разницу и запишет новый файл. Эта же команда разносит правку общего шаблона по проекту. **Ручные правки `WORKFLOW.md` не живут:** и `project-render`, и `project-doctor` перезаписывают файл по шаблону и `project.toml`. Нужна другая настройка — меняй `project.toml` или шаблон.
6. **Запустить службу** одним из двух способов (не обоими сразу — один порт, одна доска):
   - из Терминала: `symphony service start ~/symphony-projects/eve/WORKFLOW.md`;
   - через launchd (автозапуск на Mac): `ours/bin/project-launchd eve`, затем `launchctl bootstrap …` (раздел «Запуск через launchd»).
   После запуска проверь окружение службы: `ps eww -p <pid>`.
7. **Первая карточка — маленькая** (одна правка, один тест). Бери за образец `card-template.md` из папки доски: в нём уже есть подсказка «Тесты только через `/bin/bash <папка доски>/test.sh`, по одной команде на вызов Bash, без `&&`, `;`, `|`.» с настоящим путём — так агент не тратит ходы на отклонённые команды — и строки про уровень задачи (раздел «Уровни задач»).

### Права агента: `[agent] allowed_bash`

Агент запускается как `claude -p --permission-mode acceptEdits`. В этом режиме команды Bash вне списка разрешённых **отклоняются**, и агент может крутиться до `max_turns` (на пробе так и вышло: `budget_exhausted` и `needs_human`). Поэтому шаблон добавляет в команду `claude` ключ `--allowedTools` с такими правилами (по ним прошла проба на Mac):

| Встроенная база | Зачем |
|---|---|
| `/bin/bash <папка доски>/test.sh` | единственный способ гонять тесты |
| `git merge-tree` | проверка слияния в Verify (нужен ещё доступ к `.git` — его служба выдаёт сама, в логе `claude_git_roots_granted`) |
| `test`, `echo`, `cat`, `wc`, `head`, `tail` | мелкие проверки и чтение |

Свои разрешения проекта — в `project.toml`, они добавляются к базе:

```toml
[agent]
allowed_bash = [".venv/bin/python -m ruff"]
```

Запись — начало команды без обёртки `Bash(...)`; шаблон сам делает из неё правило `Bash(<запись>:*)`. Правила работы:

- **Составные команды** (`&&`, `;`, `|`) отклоняются, если хоть одна часть не разрешена. Поэтому в подсказке карточки — «по одной команде на вызов».
- `project_config.py` отказывает с понятным текстом на: пустые записи, одиночный `*`, `Bash(*)` и любые записи с `Bash(...)`, голые `bash` / `sh` / `zsh` / `env` / `sudo` / `eval` / `exec` (они разрешают что угодно), суффикс `:*` (его добавляет шаблон), и всё, что похоже на отключение проверок разрешений (`dangerously`, `bypass`, `skip-permissions`, `--permission-mode`, `--allowedTools` внутри записи).
- Флаги, отключающие проверки разрешений агента, в наши конфигурации не добавляются никогда (правило проекта).
- Изменил список — `project-render`, затем перезапусти службу.

### Сторож зависания (`stall_timeout_ms`)

Ядро отменяет воркера, если он молчит дольше `stall_timeout_ms`. «Молчит» — не было ни ответа модели (кадры `assistant`), ни событий жизненного цикла, ни прироста выходных токенов; **эхо результата инструмента прогрессом не считается**. Значит, один долгий вызов Bash (агент гоняет `test.sh` 3–5 минут) — это тишина на всё время вызова. На пробе при жёстких 300 с это давало паузу `paused for operator inspection`.

Шаблон теперь считает значение сам: `max(300 с, tests_s + 120 с)`, где `tests_s` — из `[timeouts]` (его по замеру пишет `project-doctor`, он вдвое больше времени тестов). Запас 120 с — на ответ модели вокруг долгого вызова. `project-doctor` после пересчёта таймаутов пересобирает `WORKFLOW.md` и печатает получившееся значение. Если пауза всё же случилась — `POST /api/v1/<ID>/resume`.

Что формула не покрывает: собственный предел времени одного вызова Bash у `claude` (он задаётся в самом `claude`, а не здесь) — на пробе не проверялся. Сам хук `check.py hook` под сторож не попадает: пока идёт `after_run`, ядро зависание не проверяет (по коду).

### Запуск через launchd

```bash
/путь/к/python ~/oh-my-symphony/ours/bin/project-launchd eve
launchctl bootstrap gui/$(id -u) ~/symphony-projects/eve/launchd.plist   # запустить
launchctl bootout gui/$(id -u) ~/symphony-projects/eve/launchd.plist     # остановить
```

Команда читает `project.toml` и пишет `launchd.plist` в папку доски (как `project-render` пишет `WORKFLOW.md`; перед записью показывает разницу). В файле: метка `local.symphony.<имя>`; та же команда, что строит `symphony service start` (`<python> -m symphony.cli <WORKFLOW.md> --host 127.0.0.1 --port <порт>`) в переднем плане; рабочая папка — папка доски; лог — `log/symphony.log`; `RunAtLoad` включён, `KeepAlive` выключен (сама служба после падения не перезапускается). Окружение: `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `HOME`, `PYTHONUNBUFFERED=1`, `SYMPHONY_PYTHON` из `[tools] python`.

Необязательный ключ `[service] model` (например `model = "haiku"`) добавляет `ANTHROPIC_MODEL`: процесс `claude` наследует переменную от службы. Без ключа переменная не задаётся.

**Служба из Терминала и служба из launchd — одно вместо другого, не обе сразу** (один порт, одна доска). Перед `project-doctor` службу останови (`launchctl bootout …`).

Проверка окружения работающей службы: `ps eww -p <pid>` (pid — из `launchctl print gui/$(id -u)/local.symphony.<имя>` или `ps`).

Не проверено на Mac: автозапуск после перезагрузки и поведение службы при закрытой крышке и сне.

### Окружение службы (замер на Mac под launchd)

- `PATH` — ровно то, что задано в plist (`/usr/bin:/bin:/usr/sbin:/sbin`); Node из Homebrew (`/opt/homebrew/bin`) и `~/.local/bin` в нём нет — скрипты задают пути сами.
- Есть `HOME`, `USER`, `LOGNAME`, `SHELL=/bin/zsh` и `TMPDIR=/var/folders/…/T/` (его выдаёт launchd, не мы). **`LANG` и `LC_ALL` не заданы** — тесты, зависящие от локали, задают её сами.
- **Лимит открытых файлов 256** (`launchctl limit maxfiles`; на macOS так по умолчанию). Большому набору тестов этого мало; на пробе `project-doctor` дал FAIL, зелёным стал после `ulimit -n 10240` в начале `test.sh`. Что причина именно в лимите — предположение (один зелёный прогон не доказательство).
- У агента и хуков в окружении есть переменные `SYMPHONY_*` службы; прямой `pytest` на пробе дал 9 падений, а `test.sh` с очисткой этих переменных — 0. Поэтому агент гоняет **только `test.sh`**, а в `test.sh` проекта убирают `SYMPHONY_*` (кроме `SYMPHONY_PYTHON` и `SYMPHONY_WORKFLOW_DIR`).
- Тесты, проверяющие время, под нагрузкой флейкают: их гонят отдельным последовательным проходом после основного. Оба отчёта JUnit отдают в `summarize.py` одним вызовом — он сложит счётчики.

### Интеграционная ветка задачи

Подзадачи одной задачи должны видеть код друг друга. Для этого у задачи есть общая ветка `integration/<ЗАДАЧА>` (например `integration/OMS-7`): подзадачи стартуют от её **текущего конца**, а не от базовой ветки проекта. Работает только при `[integration] enabled = true`; пока `false` (умолчание), всё как раньше и карточка не читается.

- **Имя — не `symphony/<ЗАДАЧА>`.** Карточку-задачу (`role:manager-plan`) сама выполняет агент в рабочей копии на ветке `symphony/<ЗАДАЧА>`, а при чистом старте той же карточки `worktree.py` переименовывает эту ветку в `attempts/…`. Интеграционная ветка с таким именем пропала бы. Префикс задаёт `[integration] branch_prefix`; будущая доставка (`.deliver`) будет пушить именно эту ветку.
- **Привязка подзадачи.** Метка `role:worker` (ключ `worker_label`) и поле `request: <ЗАДАЧА>` в шапке карточки. Нет метки или нет `request` — обычная карточка, старт от базовой ветки. Неверный `request` — старт отказывает.
- **Создание ветки.** Явно: `ours/hooks/integrate.py ensure-branch <ЗАДАЧА> [--board <папка доски>]` (без `--board` берётся `$SYMPHONY_WORKFLOW_DIR`); страховка — `worktree.py` создаёт ветку сам, если при старте первой подзадачи её ещё нет. Оба пути безопасны для повторов: существующая ветка не пересоздаётся и не двигается.
- **Вливание и программное `Done` (S4-12).** Когда агент подзадачи заканчивает этап Document и ставит карточке `Human Review`, ядро запускает `hooks.after_run`: `check.py hook` (проверки и полный `test.sh`), штатный блок (коммит `wip: …`) и последней строкой — `integrate.py hook`. Он вливает **ровно то содержимое, что прошло тесты** (сверка дерева с отметкой `check.py`), в `integration/<ЗАДАЧА>` одним плоским коммитом `<ID>: <заголовок>` (строки `Task:` и `Source: symphony/<ID>@<sha>`; история `wip`-коммитов остаётся в ветке `symphony/<ID>`) и сам ставит подзадаче `Done`. Следующая подзадача (`blocked_by`) стартует только после этого `Done` — уже от сдвинутого конца ветки. `Done` подзадаче ставит программа, `Done` самой задаче — только Сергей. Подробности, условия и исходы — `ours/hooks/README.md`, раздел `integrate.py`.
- **Без этапа Document (S4-16).** Подзадача идёт Verify → Human Review: Verify после чистой проверки пишет `## Document Skipped` (одна строка «Subtask: documentation is written by the task card») и ставит `Human Review`. Wiki, Learnings и отчёт As-Is → To-Be пишет карточка задачи целиком. `check.py` для подзадачи требует `[checks] worker_required_sections` (по умолчанию `## QA Evidence`, `## Merge Status`) вместо `## Wiki Updates` и `## As-Is -> To-Be Report`. Подзадачу определяет код (интеграция включена, метка `worker_label`, поле `request:`); ветка в `verify.md` только экономит ход: ошибка агента ведёт либо к отказу шлюза (нет `## Wiki Updates`), либо к лишнему ходу Document.
- **Конфликт.** Если слияние подзадачи с веткой даёт конфликт (или ветку дважды сдвинули за время слияния), интеграционная ветка **не меняется**, а карточка уходит в `needs_human` с разделом `## Integration` (файлы, причина). Разбор — человек.
- **Шлюз после `Done` (S4-13).** После `Done` ядро само вызывает шлюз `check.py gate`: он проверит быстрые правила и пропустит тесты, если дерево то же; иначе прогонит полностью. Для этого `integrate.py` оставляет одноразовую запись `<доска>/.ours-state/<ID>.merged.json` с деревом (подробности — `ours/hooks/README.md`, раздел `check.py`).
- **Включение.** Теперь `[integration] enabled = true` можно включать на доске (включает Сергей; условие — `max_concurrent_agents = 1`).

### Нарезка задачи на подзадачи (S4-19)

Руководитель (карточка с меткой `role:manager-plan`, статус `Plan`) пишет план в `docs/<ЗАДАЧА>/work/plan.toml` и сдаёт его, переводя карточку в `Subtasks`. Карточки подзадач создаёт не агент, а хук `ours/hooks/plan.py hook`, и только если весь план прошёл проверку («всё или ничего»): подзадачи получают номера `<ЗАДАЧА>-1`, `-2`, …, метку `role:worker`, поле `request: <ЗАДАЧА>`, уровень не выше уровня задачи и стартуют в `In Progress`. Ошибка плана возвращает карточку в `Plan` с разделом `## Plan Failure` (после `[plan] max_failures` — в `needs_human`). Перед ходом руководителя `plan.py brief` кладёт ему сводку лимитов `limits.md`. Настройки — раздел `[plan]` в `project.toml` (`max_subtasks`, `max_failures`). Подробности — `ours/hooks/README.md`, раздел `plan.py`, и `docs/our/DECISIONS.md`, запись «S4-19».

### Итоговая проверка задачи (S4-21)

Когда `Done` получает последняя подзадача, `integrate.py hook` сам (или человек командой `ours/hooks/integrate.py finish-task <ЗАДАЧА> [--board <папка доски>]`) начинает итоговую проверку: вливает свежий `our-main` в `integration/<ЗАДАЧА>` настоящим коммитом слияния, ставит рабочую копию карточки-задачи на результат, пишет для Verify дифф (`docs/<ЗАДАЧА>/work/final-diff.md` и `.patch`), записывает `<доска>/.ours-state/<ЗАДАЧА>.final.json` и переводит карточку-задачу из `Subtasks` в `Verify`. Дальше `Verify` → `Document` → `Human Review` с полным `test.sh` (для карточки-задачи пропуска по `doc_paths` нет; провал `check.py hook` ведёт сразу в `needs_human`). В ходе работы карточка-задача получает строки в один раздел `## Subtask Progress`. Любая проблема (грязная рабочая копия, конфликт с `our-main`, правки в ветке руководителя) — `needs_human` с разделом `## Final Check`, ветки не тронуты. Подробности — `ours/hooks/README.md`, раздел `integrate.py`.

### Карточки: что помнить

- **Исчерпанный бюджет не оживает.** Если карточка упёрлась в `max_turns` / `max_total_turns` (`budget_exhausted`; со строгими лимитами это случается чаще), флаг хранится в `state.db` и штатно не снимается. Перенеси карточку в `Archive` и заведи новую (с подсказкой про тесты). Решение, нужен ли штатный сброс, — открытый вопрос (`docs/our/DECISIONS.md`).
- Пауза `paused for operator inspection` снимается `POST /api/v1/<ID>/resume`.
- Подтверждение `Done` идёт через шлюз `check.py gate` (повторно прогоняет тесты).
- **`needs_human` после конфликта вливания** (раздел `## Integration` в карточке, событие `conflict` в `.ours-state/check.log`): интеграционная ветка цела. Разобрать можно руками: `git merge-tree --write-tree --name-only integration/<ЗАДАЧА> symphony/<ID>` покажет конфликтные файлы; поправить их в ветке `symphony/<ID>` и вернуть карточку в `Human Review` — но хук сработает снова только после нового хода агента. Проще: Сергей вливает подзадачу в `integration/<ЗАДАЧА>` руками и ставит карточке `Done`.
- **`Done` не поставился после вливания** (в `## Integration` — `moved to: Done FAILED`): код уже в интеграционной ветке, статус поправляет Сергей.

### Если проект — сам этот форк

Так подключён проект `oms` на пробе. Три ловушки:

0. **Основная папка ≠ клон.** Это два разных каталога одного репозитория, и после слияния PR обновлять надо оба; про это не надо помнить — это делает `ours/bin/post-merge` (раздел «После слияния»).
1. **Отдельный клон, не основная папка.** В `[project] repo` — отдельный клон форка (на пробе `~/dev/oms-pipeline`), а не папка `~/dev/oh-my-symphony`, из которой запускается оркестратор: конвейер создаёт в репозитории ветки `symphony/<ID>` и рабочие копии, и не должен делить их с живой установкой.
2. **Своя venv в каждой рабочей копии.** `setup.sh` создаёт `.venv` в рабочей копии и ставит пакет из неё; после установки проверь, что `symphony` импортируется из этой копии: `.venv/bin/python -c "import symphony; print(symphony.__file__)"` — путь должен вести в рабочую копию карточки, а не в основную установку. Иначе тесты проверят чужой код.
3. **`CLAUDE.md` с разделом «Если ты агент конвейера»** должен быть в базовой ветке: агент читает правила оттуда (не коммитит, не пушит, гоняет только `test.sh`).

**Запрет `ours/**` и что агент может менять в `ours/`.** По умолчанию `check.py` запрещает агенту любые правки в `ours/` (шаблон `ours/**` в встроенном списке; из `project.toml` он не отключается, `forbidden_paths` только добавляет). Снять запрет можно точечно ключом `[checks] allow_paths` — списком шаблонов, каждый из которых начинается с `ours/` (иначе ошибка конфигурации). Путь, подходящий под `allow_paths`, освобождается **только от `ours/**`**; от остальных запретов (`WORKFLOW.md`, `.github/**`, `.git/**`, `.env`, `*.pem`, `*.key`, свой `forbidden_paths` проекта) освободить нельзя.

**Неснимаемый контур контроля** — файлы, которые проверяют работу агента и задают его права: `ours/hooks/**`, `ours/bin/**`, `ours/templates/**`. Они запрещены всегда, даже если подходят под `allow_paths` (например, при ошибке `allow_paths = ["ours/**"]`). Новые файлы в этих папках защищены автоматически. Контур и права меняют только задачи, запущенные человеком (локальный Claude Code), не карточки конвейера.

Для проекта `oms` Сергей прописывает в его `project.toml` (вне репозитория):

```toml
[checks]
allow_paths = ["ours/prompts/**", "ours/README.md", "ours/tests/**"]
```

Тогда агент конвейера может править промпты (`ours/prompts/`), `ours/README.md` и добавлять **новые** тесты в `ours/tests/` (менять существующие по-прежнему нельзя — это проверка «существующие тесты»). Всё остальное в `ours/` — хуки, скрипты `bin/`, шаблон — ему запрещено. Пока `allow_paths` не прописан, запрет прежний.

### Уровни задач (`level`)

**Уровень** описывает **сложность задачи**. Какая модель и с каким усилием её выполнит — это перевод уровня для бэкенда: у каждого бэкенда своя шкала (`[levels.<имя>.claude]`, `[levels.<имя>.codex]`). Уровни описаны в `project.toml`, раздел `[levels]`, а не в коде; там же, если нужно, свои лимиты ходов. В заготовке `project-new` — конфигурация B из спецификации (значения стартовые, уточняются по статистике); перевод для claude:

| Уровень | По-русски | Модель | Усилие | Когда |
|---|---|---|---|---|
| `simple` | простая | haiku | medium | понятная небольшая задача (**по умолчанию**) |
| `standard` | обычная | haiku | high | обычная задача, та же модель думает дольше |
| `complex` | сложная | sonnet | high | сложная или пограничная задача |
| `critical` | критическая | sonnet | max | самая трудная, цена ошибки высока |

Старые имена L1/L2/S1/S2 → simple/standard/complex/critical (26.10.2026).

`default_level = "simple"` в `[levels]` — уровень карточек без собственного `level`. Усилие для claude: `low`, `medium`, `high`, `xhigh`, `max` (список из `claude --help`, версия 2.1.310); другое значение — ошибка в `project.toml`, потому что сам `claude` при неизвестном значении только пишет предупреждение и молча берёт усилие по умолчанию. Имена моделей проект не проверяет — это делает `claude`.

**Как назначить уровень карточке.** Строкой во frontmatter: `level: complex`. Рядом, в тексте карточки, — строка «Уровень: complex — почему такой» (одна фраза). Уровень и обоснование пишет тот, кто нарезает задачу: сейчас — архитектор (Claude в чате), в этапе 4 для подзадач работника — руководитель. Пустая строка `level:` или её отсутствие — действует `default_level`. Образец — `card-template.md` в папке доски.

**Что делает ядро.** При запуске хода берёт уровень карточки (иначе `default_level`) и вставляет в команду `claude` сразу после программы `--model <модель> --effort <усилие>`; если такие флаги в команде уже были, они заменяются, а не дублируются. Для `codex` подставляются `codex.model` и `codex.reasoning_effort`. Порядок: уровень карточки → `default_level` → как раньше (без `level`/`default_level` ничего не меняется). Уровень без своих `max_turns` / `max_state_turns` оставляет общие лимиты; с ними — подменяет их для своих карточек (раздел «Ходы, попытки и лимиты»).

**Связь с `[service] model`.** `[service] model` задаёт переменную `ANTHROPIC_MODEL` службы — модель, когда флага `--model` нет. Флаг `--model` из уровня важнее: проверено запуском (claude 2.1.310, `ANTHROPIC_MODEL=haiku` и `--model sonnet` дали sonnet). Для карточек без уровня (если `default_level` не задан) работает `[service] model`.

**Неизвестный уровень.** Если у карточки `level: expert`, а такого уровня нет, ход не запускается: перед выдачей агенту карточка переводится в `Blocked`, в её текст добавляется раздел `## Level` с причиной (и списком существующих уровней), в журнале службы — запись `level_rejected`. Молча на модель по умолчанию карточка не уходит. Исправь `level` в карточке и верни её в `Todo`. Так же блокируется карточка, если уровень задаёт модель claude, а `claude.command` запускает не `claude` (скрипт-обёртка), — флаги в него вставить нельзя. Ошибка в самом разделе `[levels]` ловится ещё при чтении `WORKFLOW.md`.

**Смена уровня.** Карточка перечитывается при каждой выдаче агенту и при каждой смене этапа, поэтому новый `level` вступает в силу со следующей попытки (или со следующего этапа внутри текущего захода). Продолжение сессии `claude` при смене модели работает: проверено запуском (`--resume <сессия> --model sonnet` в сессии, начатой на haiku, ответило по содержимому сессии). Новая сессия при смене уровня не нужна. По коду продолжение сессии вообще используется только внутри одного этапа (одна модель) и при восстановлении после аварии службы.

**Учёт.** Каждый ход пишет в журнал службы строку `worker_turn_started` с полями `task_level`, `model`, `effort`; те же поля лежат в событии `turn_started` записи запуска (`runs`). Стоимость хода (`cost_usd`, K07) берётся из того же запуска. Вместе это даёт цену задач по уровням: исходные данные для расчёта лестницы (этап 4). Поле называется `task_level`, а не `level`, потому что `level` занят уровнем важности записи в журнале.

### Ходы, попытки и лимиты

- **Ход** — один запуск агента с заданием этапа; внутри хода агент делает много действий (читает файлы, правит код, запускает тесты). Нормальной карточке нужен примерно 1 ход на этап.
- **Заход** — период от выдачи карточки агенту до выхода воркера; в нём несколько этапов подряд. **Попытка** — заход на задачу, который заканчивается проверкой: если проверка не прошла, карточка возвращается назад и начинается следующая попытка.
- **Памятка для задач:** как писать карточки, статусы и роли — см. [docs/our/HOWTO-TASKS.md](../docs/our/HOWTO-TASKS.md).
- **Путь карточки:** `Todo` (разбор) → `In Progress` (работа) → `Verify` (проверка) → `Document` (документация) → `Human Review` (человек) → `Done`. Карточка-задача с меткой `role:manager-plan` идёт иначе: `Plan` (руководитель нарезает задачу на подзадачи) → `Subtasks` (ждёт подзадачи, агент на ней не работает) → `Verify` → `Document` → `Human Review` (S4-18; выход из `Subtasks` — S4-21, см. «Итоговая проверка задачи»). Возвраты назад:
  1. `Verify` → `In Progress`: проверяющий нашёл замечания уровня CRITICAL/HIGH/MEDIUM (`## Review Findings`) или не прошёл QA (`## QA Failure`). Считается в `max_attempts`.
  2. Откат `check.py` из `Human Review` в `In Progress`: механическая проверка не прошла (тесты, запрещённые пути, изменённые тесты, нет разделов). Причина — в разделе `## Check Failure`. Считается в `[checks] max_check_failures`; на последнем провале карточка идёт не в `In Progress`, а в `needs_human`. В `max_attempts` не входит.
  3. Повтор этапа при провале контракта: этап закончил, но обязательных разделов или свидетельств в карточке нет — ядро возвращает карточку в этот же этап. Считается в `max_attempts`.

Лимиты ходов (`project.toml`, `[limits]`), значения по умолчанию в заготовке — строгие, для облачных моделей: нормальной карточке нужно ~4 хода (по одному на этап), всё сверх этого — признак проблемы, а деньги уходят на каждый ход.

| Лимит | Что считает | Заготовка | Что будет при превышении (по коду ядра) |
|---|---|---|---|
| `max_state_turns` | ходов подряд на одном этапе без перехода дальше | 2 | после 2-го хода карточка → `needs_human` + пауза (`paused`, снимается `POST /api/v1/<ID>/resume`), заметка «Budget Exceeded»; третьего хода нет |
| `max_turns` | ходов за один заход | 12 (4 этапа на самом длинном пути × (1 + `max_attempts`); и не меньше числа активных статусов доски — 5) | карточка → `needs_human`, заметка «Budget Exceeded», флаг `budget_exhausted` |
| `max_total_turns` | ходов по карточке за всё время работы службы | 20 | то же, что у `max_turns` |
| `max_attempts` | возвратов назад по этапам (пункты 1 и 3 выше) | 2 | возврат №3 → `Blocked`; флага нет |
| `max_check_failures` | провалов `check.py` | 2 | второй провал → `needs_human` |

**Согласованность лимитов.** `max_turns` должен быть не меньше `4 × (1 + max_attempts)`: 4 активных этапа и до `max_attempts` возвратов, каждый возврат заставляет пройти этапы заново. Иначе карточка с положенными возвратами упрётся в `max_turns` раньше, чем дойдёт до `Human Review` (так OMS-6 остановилась по `max_turns = 8` при `max_attempts = 2`). Формулу проверяет загрузчик `project.toml` (`ours/hooks/project_config.py`): противоречивый `[limits]` — отказ с объяснением; та же формула действует для `max_turns` уровня (с `max_attempts` проекта). Зацикливание на одном этапе по-прежнему держит `max_state_turns`.

Счётчики ядра хранятся в памяти службы: перезапуск службы их обнуляет. Флаг `budget_exhausted` хранится в `state.db`; снимается он `POST /api/v1/<ID>/reset-budget` (S4-09). Пока лестница (этап 4) не включена, остановленную по лимиту карточку разбирает человек.

**Как продолжить карточку из `needs_human`.** (1) `POST /api/v1/<ID>/reset-budget` — сбрасывает счётчики ходов и флаг `budget_exhausted`; (2) при необходимости поправь `level:` в карточке (например, `complex` вместо `standard`); (3) перенеси карточку в `Todo`. Рабочая копия карточки при этом сохраняется: `needs_human` входит в `agent.preserve_workspace_states` шаблона `WORKFLOW.md`, так что ядро не удаляет её ни при смене статуса, ни при перезапуске службы (для доски, отрисованной `project-render` после S4-15). Агент продолжает работу в той же копии. Счётчик провалов `check.py` лежит в `.ours-state` папки доски, и `reset-budget` его не трогает.

Счётчик `max_state_turns` не сбрасывается, если карточку вернули в тот же этап (сбрасывается при смене этапа): после `resume` в том же этапе она получит один ход. Подробно — `docs/our/reports/REPORT-16.md`.

**Свои лимиты у уровня.** У уровня можно задать `max_turns` и/или `max_state_turns` — они подменяют общие для карточек этого уровня (общий `max_state_turns_by_state` для этапа важнее). `max_total_turns` и `max_attempts` общие. Зачем: у облачных уровней лимиты строгие, а у будущей локальной модели — свои, щедрее: она бесплатная, её ограничивает только время. Пример (в заготовке закомментирован):

```toml
[levels.LOCAL]
max_turns = 40         # не меньше 4 × (1 + max_attempts)
max_state_turns = 6
```

Общий потолок `max_total_turns` действует и для таких уровней: если он меньше `max_turns` уровня (в заготовке 20 против 40 в примере), карточка остановится по нему — для щедрого уровня поднимай и `[limits] max_total_turns`.

### Контракт `test.sh`: строка итогов

`test.sh` в конце печатает строку `PIPELINE_TESTS passed=<n> skipped=<n> failed=<n>` (с начала строки; если таких строк несколько, считается последняя). Печатает её `ours/hooks/summarize.py` по отчёту JUnit XML, который умеют писать все распространённые раннеры. Отчёт — во временный файл вне рабочей папки (`mktemp`), чтобы он не попал в git:

```bash
report="$(mktemp -t ours-junit.XXXXXX)"; trap 'rm -f "$report"' EXIT
/полный/путь/node_modules/.bin/vitest run --reporter=junit --outputFile="$report"   # Vitest
# .venv/bin/python -m pytest -q --junitxml="$report"                               # pytest
rc=$?
"$SYMPHONY_PYTHON" ~/oh-my-symphony/ours/hooks/summarize.py "$report" || exit $(( rc ? rc : 1 ))
exit $rc
```

Если тесты идут в несколько проходов (например, основной и отдельный последовательный для тестов с таймингом), `summarize.py` принимает несколько отчётов и печатает одну общую строку: `summarize.py "$report" "$report_timing"` (суммы `passed` / `skipped` / `failed`). Любой нечитаемый отчёт — отказ без строки. С одним отчётом поведение прежнее.

`check.py` при коде 0 требует эту строку и отказывает, если: строки нет; `failed` больше нуля; `passed` меньше, чем в замере базы **на точке ответвления ветки карточки** (S4-25; история — `.ours-state/baselines.json`); `skipped` больше, чем в замере. Так ловится агент, который убрал тест из запуска, не трогая сам файл теста (например, через конфиг раннера). Нет `baselines.json` и `baseline.json` — отказ «запусти project-doctor»; повреждённая история — отказ «перезапусти project-doctor». Если для точки нет действующего замера, сравнивать не с чем: отказ только при `failed` больше нуля, в журнале событие `baseline_unknown`.

### Таймауты и лимиты

- `[timeouts]` заполняет `project-doctor`: `tests_s` = max(300, удвоенное время тестов, округлённое вверх до минуты) — таймаут `test.sh` в `check.py`; `gate_ms` = (`tests_s` + 60) × 1000 — шлюз Done; `hooks_ms` = (max(1,5 × время `setup.sh`, `tests_s`) + 60) × 1000 — хуки. `fixed = true` в разделе — не перезаписывать (только показать рекомендацию). Старый ключ `[checks] test_timeout_s` убран: его наличие — ошибка с подсказкой.
- `[limits]` — лимиты ядра, попадают в раздел `agent` `WORKFLOW.md`: `max_state_turns`, `max_turns`, `max_total_turns`, `max_attempts`. Без раздела (старые проекты) действуют прежние значения: `max_turns` 30, `max_total_turns` 60, `max_attempts` 3, `max_state_turns` 30 (умолчание ядра). Заготовка `project-new` пишет строгие: 2 / 12 / 20 / 2, и `[checks] max_check_failures = 2` (раздел «Ходы, попытки и лимиты» выше). Существующий проект заготовка не обновляет — строки переносят вручную.

Карточки заводятся с ID `<ПРЕФИКС>-<номер>` (например `EVE-1`); карточку с чужим префиксом хук рабочей копии не возьмёт.

## После слияния

```bash
/Users/helloworld10011/dev/oh-my-symphony/ours/bin/post-merge [--project ИМЯ ...] [--dry-run] [--root DIR] [--main DIR]
```

Одна команда вместо ручных `git pull` в основной папке и в клонах проектов. Запускать **сразу после слияния PR**. Она:

1. проверяет, что основная папка и клоны стоят на `our-main` и в них нет незакоммиченных изменений отслеживаемых файлов (иначе отказ, `stash` не делается);
2. делает `git fetch` и `git pull --ff-only` (без `rebase` и без слияний);
3. смотрит, какие файлы изменились с **последнего обработанного коммита** (он хранится в `tmp_workspaces/post-merge-state.json` основной папки) и решает по таблице, что нужно каждому проекту;
4. перед остановкой или перезапуском спрашивает службу (`GET /api/v1/state`): если есть карточки `running` или `retrying`, ничего не трогает;
5. делает действия и убирает за собой.

Подходят проекты из `--root` (по умолчанию `~/symphony-projects`), у которых `[project] repo` — клон того же репозитория, что и основная папка (совпадает `origin`).

| Что изменилось | Что делает |
|---|---|
| `src/**` основной папки | перезапуск службы (`launchctl kickstart -k`) |
| в клоне проекта: `tests/**`, `ours/tests/**`, `conftest.py` на любом уровне, `pytest.ini`, `pyproject.toml`, `uv.lock`, `package.json`, `package-lock.json`, `test_*.py`, `*_test.py` | `project-doctor`: службу останавливает (`bootout`), после doctor всегда запускает обратно (`bootstrap`), даже если doctor упал |
| `ours/templates/**`, `ours/prompts/**`, `ours/hooks/project_config.py` | `project-render`, без перезапуска |
| только `docs/**`, `*.md`, прочее | ничего |

Если нужны и doctor, и перезапуск — только остановка → doctor → запуск. Render вместе с перезапуском — сначала render, потом перезапуск. Render вместе с doctor — только doctor (он сам вызывает render). Остальные `ours/hooks/*`, `ours/bin/**` основной папки действий не требуют (`ours/tests/**` — только как файлы клона проекта, строка про doctor): хуки запускаются отдельным процессом на каждый вызов и подхватываются сами.

**Почему перезапуск нужен только для `src/`.** Служба перечитывает `WORKFLOW.md` и файлы промптов на каждом такте (`_on_tick` → `workflow_state.reload()`), поэтому после `project-render` и правки `ours/prompts/*` перезапуск не нужен. А код `src/` загружен в память процесса (editable-установка из основной папки) — его заменит только новый процесс.

**Код возврата.** `0` — всё сделано или нечего делать; `1` — отказ или ошибка (смотрите вывод; повторный запуск безопасен); `2` — часть действий **отложена**, потому что в проекте есть карточки в работе.

**Что делать при коде 2.** Команда в таком случае ничего не трогает в этом проекте и не запоминает коммит как обработанный. Дождитесь, когда карточки выйдут из работы (или остановите службу сами), и запустите `ours/bin/post-merge` ещё раз — отложенное выполнится. Если служба не отвечает, перезапускать нечего: команда напечатает, как её запустить (`project-launchd`, затем `launchctl bootstrap`).

**`--dry-run`.** Только `git fetch` и печать плана: что подтянется, что изменится, какие действия потребуются, что будет убрано. Ничего не меняет.

**Уборка** (не при `--dry-run`): `git worktree prune`; рабочие копии `dev/<код>`, ветка которых уже влита в `our-main`, удаляются (`git worktree remove` без `--force`, затем `git branch -d`) вместе с `tmp_workspaces/inbox/<код>.md` — но только если в копии нет незакоммиченных и неотслеживаемых файлов и у ветки есть собственные коммиты. Остальное пропускается с пояснением. Основная папка и клоны проектов не удаляются никогда.

Защита от двух запусков одновременно — файл-замок рядом с файлом состояния. Поведение на настоящем `launchctl` проверяется при первом боевом запуске.

## Очередь команд

**Зачем.** Помощник в чате не может набирать текст в Терминале, поэтому раньше запуск Claude Code и слияние PR набирал Сергей вручную. Теперь помощник кладёт в папку маленький файл-команду, а фоновая служба `ours/bin/inbox-runner` выполняет ровно три вещи. Всё остальное запрещено устройством службы.

Папка команд — `tmp_workspaces/inbox/` основной папки форка (вне git). Имя файла — `<код>.<команда>`; код — буквы, цифры и дефис (до 31 знака), команда — строго строчными.

| Файл | Содержимое | Что делает служба |
|---|---|---|
| `S4-03.run` | пусто или одна строка слов через один пробел: `model=…` (`sonnet` по умолчанию, ещё `opus`, `haiku`) и/или `effort=…` (`low`, `medium`, `high`, `xhigh`, `max`); каждый ключ не более раза, в любом порядке, например `model=sonnet effort=high`; без `effort` флаг `--effort` не передаётся — усилие Claude Code по умолчанию; в отчёте строка `Запуск: model=… effort=…` (или `effort=по умолчанию`) | рядом должен лежать `S4-03.md` (задание). Если ветки `dev/S4-03` и папки `oms-dev/S4-03` ещё нет: `git fetch origin our-main`, `git worktree add --no-track -b dev/S4-03 … origin/our-main`, затем открывает окно Терминала с Claude Code внутри этой копии |
| `S4-03.test` | пусто | гоняет в рабочей копии зашитый набор: `ruff check ours` и `pytest ours/tests -q`; если ветка меняет `src/` или `tests/` — ещё `ruff check src tests` и полный `pytest -q`. Для ветки с правками `src/` создаётся своё `.venv` в копии |
| `S4-03.merge` | одна строка — имя ветки, например `dev/S4-03` | проверяет, что есть ровно один открытый PR из этой ветки этого же репозитория в `our-main`; вливает (`gh pr merge … --merge`), затем запускает `ours/bin/post-merge` |

**Окно Claude Code.** `.run` запоминает открытое окно Терминала (номер окна и `tty`) в `tmp_workspaces/outbox/<код>.terminal.json`. После успешного `.merge` — после строки «PR влит.» и до `post-merge` — служба проверяет, что это то самое окно, останавливает Claude Code этой задачи вместе с его дочерними процессами (`SIGTERM`, через 10 с `SIGKILL` оставшимся из этого же дерева) и закрывает окно; если не вышло (Терминал спросил подтверждение, окна нет), в отчёте строка с причиной, слияние и `post-merge` не страдают. После `.test` окно остаётся: после проверки могут понадобиться правки.

**Порядок приёмки.** Claude Code закончил → чат кладёт `<код>.test` → читает `outbox/<код>.test.log` (в конце `ТЕСТЫ: PASS` или `ТЕСТЫ: FAIL`) → заключение → после «добро» Сергея чат кладёт `<код>.merge`. `.test` можно повторять после каждой доработки: прежний отчёт переименуется в `<код>.test.<метка времени>.log`, ничего не затирается.

**Куда что уходит.**
- обработанный файл сразу забирается в `tmp_workspaces/inbox/done/` (с меткой времени) и только потом выполняется: если служба упала посередине, команда не повторится;
- отчёт о каждой команде — `tmp_workspaces/outbox/<код>.<команда>.log` (шаги, вывод `git`/`gh`/`post-merge` как есть, коды возврата);
- всё пропущенное (неизвестный файл, неверное содержимое, нет задания `.md`, повтор) — одной строкой в `tmp_workspaces/outbox/_skipped.log`, один раз на файл. Файлы `<код>.md` и каталог `done/` служба не трогает и не упоминает.

**Лимит открытых файлов.** При старте служба поднимает мягкий лимит открытых файлов до 10240 (у `launchd` он 256, а полному `pytest` ядра этого мало); проверки наследуют его, а отчёт `.test` показывает значение строкой `Лимит открытых файлов`.

**Внутренняя ошибка.** Если служба споткнулась внутри команды, в отчёте есть строка `ВНУТРЕННЯЯ ОШИБКА` и полная трассировка.

**Повтор команды.** `.run` и `.merge` с тем же кодом второй раз не выполняются, пока лежит их отчёт (`повтор` в `_skipped.log`). Чтобы повторить неудачную попытку, нужен новый код: чат кладёт копию задания под новым кодом (например `S4-01b.md`) и пишет `S4-01b.run`. Прежние рабочая копия и ветка остаются.

**Установка** (один раз; служба сама не загружается):

```bash
ours/bin/inbox-runner-launchd          # пишет tmp_workspaces/launchd/local.symphony.inbox-runner.plist, печатает команды
launchctl bootstrap gui/$(id -u) <путь к plist из вывода>
```

Остановка: `launchctl bootout gui/$(id -u) <путь к plist>`. Служба — агент пользователя (`gui/<uid>`), иначе она не сможет открыть окно Терминала. Лог самой службы — `tmp_workspaces/outbox/_launchd.log`. Вторая копия службы не стартует (файл-замок `tmp_workspaces/inbox-runner.lock`). После `.merge` служба сравнивает свои файлы с теми, что были при старте, и если они изменились — завершается; `launchd` (`KeepAlive`) поднимает новую версию.

**Разрешение macOS.** При первом открытии окна система спросит, можно ли этой программе управлять «Терминалом» (Автоматизация). Подтвердите один раз. Если окно пропустили: Системные настройки → Конфиденциальность и безопасность → Автоматизация.

**Доступ к GitHub.** Служба сама делает `git fetch origin our-main`, а у `launchd` короткое окружение (`PATH=/usr/bin:/bin:/usr/sbin:/sbin`). Если доступ к GitHub держится на настройках терминала (ssh-агент, переменные), `fetch` может не пройти. Текст ошибки попадёт в `outbox/<код>.run.log`; тогда доступ настраивается один раз (службе передаются только `SSH_AUTH_SOCK`, `GH_TOKEN`, `GITHUB_TOKEN`, если они есть).

**Уборка.** `post-merge` убирает только влитые рабочие копии. Копии неудачных и невлитых попыток остаются — их удаляет Сергей: `git worktree remove <папка>` и `git branch -D dev/<код>`.

**Предупреждение о безопасности.** Всё, что может писать в `tmp_workspaces/inbox/`, может запустить эти три команды. Поэтому: жёсткие шаблоны имён, кода, ветки и модели; файл не выполняется и не вставляется в оболочку; PR проверяется (один, открытый, из этого репозитория, база `our-main`); `gh pr merge` без `--admin`; сессии Claude Code в `inbox/` не пишут. Репозиторий, базовая ветка, список команд, набор проверок и модели — константы в `ours/hooks/inbox_runner.py`, не настройки.

## Что гарантирует шаблон

Агент заканчивает работу в `Human Review`; `Done` ставит только человек (Confirm done), и перед этим `check.py gate` ещё раз проверяет ветку (вместе с прогоном тестов и сравнением с замером базы). Автослияние и пуш выключены, `auto_recover_blocked` выключен, лестница бюджета ведёт в `needs_human`. Проверки разрешений агента не отключаются.
