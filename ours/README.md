# Наши скрипты, хуки и шаблоны

Здесь всё, что мы добавляем к oh-my-symphony снаружи ядра. Каждый проект подключается одинаково: у него есть **папка доски** вне репозитория кода, а в самом репозитории кода ничего нашего не появляется.

| Папка | Что внутри |
|---|---|
| `bin/` | `project-new` (создать папку доски), `project-doctor` (проверить готовность и замерить базу), `project-render` (пересобрать `WORKFLOW.md`) |
| `hooks/` | `worktree.py` (рабочие копии карточек), `check.py` (механические проверки), `summarize.py` (строка итогов тестов из JUnit XML), `project_config.py` (общая библиотека); подробности — `hooks/README.md` |
| `templates/` | `WORKFLOW.md.tmpl` — общий шаблон, в нём собраны все решения из `docs/our/DECISIONS.md` |
| `prompts/` | копия штатных промптов с нашими правками; список правок — `prompts/CHANGES.md` |
| `tests/` | тесты на временных git-репозиториях и сквозной прогон `tests/e2e/run.sh` |

## Термины

- **Репозиторий кода** — git-репозиторий проекта, с которым работает агент.
- **Папка доски** — `~/symphony-projects/<имя>/`, в ней настройки и доска проекта. Сама она не git-репозиторий и не должна лежать внутри него.
- **Рабочая копия** (worktree) — отдельная папка карточки `~/symphony_workspaces/<имя>/<ID>`, привязанная к репозиторию кода, на ветке `symphony/<ID>`.

## Что лежит в папке доски

| Файл | Зачем |
|---|---|
| `project.toml` | единственный файл настроек: путь к репозиторию, базовая ветка, префикс ID, порт, пути к программам, правила проверок, таймауты, лимиты ходов |
| `setup.sh` | готовит свежую рабочую копию (установка зависимостей) |
| `test.sh` | полный прогон тестов; код 0 = зелено, в конце — строка итогов (ниже) |
| `WORKFLOW.md` | собирается из шаблона; **руками не правится** |
| `kanban/` | доска с карточками |
| `artifacts/<ID>/`, `wiki/` | артефакты агента; в рабочей копии видны как `docs/<ID>/` и `docs/llm-wiki/`, в git не попадают |
| `worktree-exclude` | что git в рабочих копиях не должен видеть |
| `.ours-state/` | состояние наших скриптов: база каждой карточки, замер базовой ветки `baseline.json`, журнал проверок, счётчики |

## Как подключить проект

Все команды запускать тем Python, в который установлен оркестратор (тот же, что `symphony`): его путь попадёт в настройки.

1. **Создать папку доски.**
   ```bash
   /путь/к/python ~/oh-my-symphony/ours/bin/project-new eve \
     --repo ~/code/eve --base dev --prefix EVE --port 9971
   ```
   Команда откажет и ничего не создаст, если: папка уже есть; путь — не корень git-репозитория; нет ветки `dev`; папка доски оказалась бы внутри git-репозитория; имя или префикс в неверном формате (имя — строчные буквы, цифры и `-`; префикс — 2–10 заглавных букв и цифр); порт или префикс уже заняты другим проектом в той же папке; не найден `claude`, `python` или `symphony`.
2. **Заполнить `setup.sh` и `test.sh`.** Обе заготовки выходят с кодом 1 «не настроено» и содержат строку-метку `OURS-STUB` — её надо удалить вместе с двумя последними строками (`echo`, `exit 1`), иначе `project-doctor` не пропустит. В скриптах — полные пути к программам (login-оболочка не используется). Контракт `test.sh` — ниже.
3. **Заполнить `[checks]` в `project.toml`**: запрещённые пути (сюда же — файлы запуска тестов: `package.json`, конфиг раннера), шаблоны файлов тестов, исключения. Неизвестный ключ — ошибка. При желании — `[limits]` (ниже).
4. **Проверить и замерить: `project-doctor`.**
   ```bash
   /путь/к/python ~/oh-my-symphony/ours/bin/project-doctor eve
   ```
   Печатает список PASS / FAIL / WARN, код 0 — только без FAIL. Проверяет `project.toml`, программы из `[tools]` (`claude --version`), репозиторий и базовую ветку, что папка доски не внутри git, что порт и префикс не заняты соседним проектом, что `setup.sh` и `test.sh` — не заготовки. Затем делает **пробную рабочую копию** базовой ветки (временная папка вне доски и кода, без новых веток, всегда удаляется), гоняет в ней `setup.sh` и `test.sh` (предел — час на каждый) и требует: код 0, строка итогов, `failed=0`. Числа и время пишет в `.ours-state/baseline.json`, по замеру заполняет `[timeouts]` (правится только этот раздел, остальной текст файла не меняется), пересобирает `WORKFLOW.md` и запускает `symphony doctor`. Два WARN ядра ожидаемы и помечены «известно»: `git history writable` (папка доски — не git) и `agent git grant` (абсолютный путь к `claude`). Пока служба этого проекта запущена, `symphony doctor` пожалуется на занятый порт — `project-doctor` запускать при остановленной службе.
   **Перезапускать `project-doctor`, когда в базовой ветке менялись тесты** (добавили, убрали, пропустили): иначе `check.py` сравнивает с устаревшим замером.
5. **Пересобрать `WORKFLOW.md`**, если менялся `project.toml` без `project-doctor`: `ours/bin/project-render eve` — покажет разницу и запишет новый файл. Эта же команда разносит правку общего шаблона по проекту.
6. **Запустить службу**: `symphony service start ~/symphony-projects/eve/WORKFLOW.md`.

### Контракт `test.sh`: строка итогов

`test.sh` в конце печатает строку `PIPELINE_TESTS passed=<n> skipped=<n> failed=<n>` (с начала строки; если таких строк несколько, считается последняя). Печатает её `ours/hooks/summarize.py` по отчёту JUnit XML, который умеют писать все распространённые раннеры. Отчёт — во временный файл вне рабочей папки (`mktemp`), чтобы он не попал в git:

```bash
report="$(mktemp -t ours-junit.XXXXXX)"; trap 'rm -f "$report"' EXIT
/полный/путь/node_modules/.bin/vitest run --reporter=junit --outputFile="$report"   # Vitest
# .venv/bin/python -m pytest -q --junitxml="$report"                               # pytest
rc=$?
"$SYMPHONY_PYTHON" ~/oh-my-symphony/ours/hooks/summarize.py "$report" || exit $(( rc ? rc : 1 ))
exit $rc
```

`check.py` при коде 0 требует эту строку и отказывает, если: строки нет; `failed` больше нуля; `passed` меньше, чем в замере базы; `skipped` больше, чем в замере. Так ловится агент, который убрал тест из запуска, не трогая сам файл теста (например, через конфиг раннера). Нет `baseline.json` — отказ «запусти project-doctor».

### Таймауты и лимиты

- `[timeouts]` заполняет `project-doctor`: `tests_s` = max(300, удвоенное время тестов, округлённое вверх до минуты) — таймаут `test.sh` в `check.py`; `gate_ms` = (`tests_s` + 60) × 1000 — шлюз Done; `hooks_ms` = (max(1,5 × время `setup.sh`, `tests_s`) + 60) × 1000 — хуки. `fixed = true` в разделе — не перезаписывать (только показать рекомендацию). Старый ключ `[checks] test_timeout_s` убран: его наличие — ошибка с подсказкой.
- `[limits]` — лимиты ядра, попадают в раздел `agent` `WORKFLOW.md`: `max_turns` (30) — ходов за один запуск агента по карточке; `max_total_turns` (60) — ходов по карточке за всё время работы службы; `max_attempts` (3) — возвратов назад по этапам (Verify → In Progress и т.п.). Точный смысл — в комментариях `project.toml` и в REPORT-12. Счётчики ядра живут в памяти службы и обнуляются при её перезапуске.

Карточки заводятся с ID `<ПРЕФИКС>-<номер>` (например `EVE-1`); карточку с чужим префиксом хук рабочей копии не возьмёт.

## Что гарантирует шаблон

Агент заканчивает работу в `Human Review`; `Done` ставит только человек (Confirm done), и перед этим `check.py gate` ещё раз проверяет ветку (вместе с прогоном тестов и сравнением с замером базы). Автослияние и пуш выключены, `auto_recover_blocked` выключен, лестница бюджета ведёт в `needs_human`. Проверки разрешений агента не отключаются.

## Проверка

```bash
python -m pytest ours/tests -q
python -m ruff check ours
E2E_OUT=/tmp/kit-e2e ours/tests/e2e/run.sh                   # обычный путь до Human Review
E2E_DROP_TEST=1 E2E_OUT=/tmp/kit-e2e ours/tests/e2e/run.sh    # агент убирает тест из запуска
```
