# Форк oh-my-symphony для ИИ-конвейера разработки (ночью и днём, в том числе удалённо)

## Что это за репозиторий

Форк `cskwork/oh-my-symphony`. Ветка `our-main` — наша зафиксированная версия, вся работа идёт от неё.

Цель: на базе oh-my-symphony построить конвейер по спецификации `docs/our/ARCHITECTURE.md` — уровни задач, лестница эскалации по провалам, механические проверки, резервы лимитов, удалённое управление.

## Если ты агент конвейера

Ты агент конвейера, если текущая ветка называется `symphony/*` (проверь: `git branch --show-current`). Тогда действуют только правила этого раздела, а правила ниже про ветки, PR и блок состояния к тебе не относятся.

- Ветки не создавай и не переключай.
- Не коммить: коммит делает хук конвейера (блок `hooks.after_run` в `WORKFLOW.md`, после каждого хода).
- Не пушь. PR не создавай.
- Блок «Текущее состояние» в `docs/our/DECISIONS.md`, таблицу «Расход облачного кредита» и `docs/our/ROADMAP.md` не трогай.
- Работай по промпту этапа (его даёт конвейер): читай только то, что нужно для карточки. Правила про тесты, язык и безопасность из этого файла остаются в силе.
- **Тесты — только командой, которую даёт карточка или промпт этапа** (обычно `/bin/bash <папка доски>/test.sh`). Прямой `pytest` в окружении службы даёт ложные падения: там лишние переменные `SYMPHONY_*`, а `test.sh` их чистит. И не чаще, чем разрешает промпт этапа: полный прогон делает хук один раз.
- **Python — `.venv/bin/python` рабочей копии**, не системный и не чужой.
- **Одна команда на вызов Bash**: без `&&`, `;`, `|`. Составная команда отклоняется, если хоть одна часть не разрешена, и ходы уходят впустую.
- Если задание неясное или противоречит спецификации — остановись и опиши вопрос, не угадывай.

## Перед любой задачей прочитай

1. `docs/our/DECISIONS.md` — принятые решения и текущее состояние. Если спецификация и решения расходятся, верны решения.
2. `docs/our/ROADMAP.md` — текущий этап.
3. `docs/our/ARCHITECTURE.md` — спецификация. Чаще всего нужны разделы 4 (лестница), 5.1 (уровни задач), 7 (лимиты), 15 (что берём готовым и что дописываем).
4. `README.md` проекта — как устроен oh-my-symphony.
5. `AGENTS.md` автора проекта — его правила разработки соблюдаем; при противоречии приоритет у этого файла (`CLAUDE.md`).

## Правила изменений

1. **Минимум правок ядра.** Сначала — конфигурация, хуки, внешние скрипты, программы поверх JSON API. Правка `src/symphony/` — только если иначе нельзя, и в описании PR объясняется почему.
2. **Где лежит наше:** скрипты, хуки, бот — в `ours/`; документы, отчёты, задачи — в `docs/our/`.
3. **Тесты.** Перед PR должны проходить `python -m pytest -q` и `python -m ruff check src tests`. Каждая правка ядра — с новыми тестами.
4. **Не трогать существующие тесты проекта** (не менять, не удалять, не помечать пропускаемыми), если задача прямо этого не требует. Упавший тест — повод разобраться, а не подогнать тест.
5. **Новые зависимости** — только с обоснованием в описании PR.
6. **Ветки.** Работа — в отдельной ветке от `our-main`, PR — в `our-main`. Никогда не пушить в `main` и в `our-main` напрямую. Никаких PR в исходный репозиторий автора.
   - **Рабочая копия.** Локальный Claude Code работает только в отдельной рабочей копии (git worktree) рядом с основной папкой (`/Users/helloworld10011/dev/oms-dev/<код>`, ветка `dev/<код>` от `our-main`), не в основной папке: из неё работает служба. Задание может прийти файлом из `tmp_workspaces/inbox/<код>.md` основной папки — тогда первым коммитом сохрани его в `docs/our/tasks/TASK-<код>.md`.
   - **Слияние.** PR сливается только по явному добру Сергея, командой `gh pr merge <ветка> --repo Serg10011/oh-my-symphony --merge`, и сразу после этого запускается `ours/bin/post-merge`. Сессия свой PR сама не сливает. Репозиторий для `gh` — строго `Serg10011/oh-my-symphony`, не `cskwork`.
   - **Очередь команд** (`ours/bin/inbox-runner`, `tmp_workspaces/inbox/` основной папки). Команд-файлов ровно три: `<код>.run` — когда задание готово к запуску; `<код>.test` — когда Claude Code закончил и нужно прогнать проверки; `<код>.merge` — **только после явного «добро» Сергея в чате** (это то же разрешение, что и на `gh pr merge`). Других файлов-команд нет. Файл `<код>.run` пуст или содержит одну строку `model=sonnet|opus|haiku` и/или `effort=low|medium|high|xhigh|max` через пробел (без `effort` усилие Claude Code по умолчанию); правки ядра запускай с `effort=high`.
     - **Сессия Claude Code в `tmp_workspaces/inbox/` и `outbox/` не пишет и не читает оттуда команды.**
     - Если сессию запустила очередь (`.run`), рабочая копия `/Users/helloworld10011/dev/oms-dev/<код>` и ветка `dev/<код>` от `origin/our-main` уже созданы службой — сама их не создавай и не переключай; файл задания читай по полному пути в основной папке (первым коммитом сохрани его в `docs/our/tasks/TASK-<код>.md`).
     - Повтор неудачной попытки — только под новым кодом: чат кладёт копию задания под новым кодом (например `S4-01b.md`) и пишет `S4-01b.run`; прежняя рабочая копия и ветка остаются, удаляет их Сергей.
7. **Совместимость с исходным проектом.** Правки ядра — маленькие и изолированные, чтобы их легко было перенести при обновлении.
8. **Безопасность.**
   - В репозиторий не попадают ключи, токены, реальные данные.
   - В наших примерах конфигурации автослияние (`auto_merge_on_done`) и пуш в удалённый репозиторий выключены.
   - Не добавлять в наши конфигурации флаги, отключающие проверки разрешений агентов.
   - Конвейер никогда не отправляет команды реальному оборудованию.
9. **Язык.** Отчёты, описания PR и документы в `docs/our/` — на русском, простым понятным языком: пользователь не всегда глубоко в теме, термины объясняются. Код, комментарии в коде, имена — на английском.

## Как писать критерии приёмки

Для людей и ИИ, которые пишут задания и карточки.

- Критерий — результат по существу, который проверяется чтением и одним понятным действием.
- Не писать мелочные измеримые правила вроде «1–3 предложения на термин», точной длины, порядка слов: они дают возвраты без пользы.
- Число или формат допустимы, только если это настоящее требование (лимит поля, формат файла, который читает программа).
- На каждый критерий — один сигнал проверки.
- Не больше 5 критериев на карточку.

## Формат результата

- **Описание PR:** что сделано, зачем, как проверено (команды и результат), что не сделано, риски.
- **Исследовательская задача:** отчёт в `docs/our/reports/REPORT-NN.md`, код не меняется.
- **Задание неясное или противоречит спецификации:** остановиться и описать вопрос, а не угадывать.
- **Последний шаг любой задачи (обязательно):** переписать блок «Текущее состояние (обновляется каждой сессией)» в самом верху `docs/our/DECISIONS.md` — дата, что сделано, что в работе, что следующее — и отметить выполненные пункты в `docs/our/ROADMAP.md`. Это входит в тот же PR, что и сама задача.
  - **Кредит.** Облачный кредит израсходован (25.10.2026): строка кредита в блоке «Текущее состояние» больше не ведётся. В запись журнала о задаче вместо «Кредит: …» указывай модель, которой сделана задача (например, «Модель: Sonnet»). Таблица «Расход облачного кредита» в `DECISIONS.md` остаётся как история.
  - В итоговом сообщении после ссылки на PR: после слияния выполняется `/Users/helloworld10011/dev/oh-my-symphony/ours/bin/post-merge`.
