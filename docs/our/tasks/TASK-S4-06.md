## Часть А. Замечание приёмки K14 №1: испорченный `level` посреди захода

Что происходит. Уровень карточки (`level` во frontmatter) разбирается заново на каждом шаге через `_config_for_issue_agent` → `apply_level`, и на неизвестное имя уровня она бросает `LevelError`. Проверка «до первого хода» (`dispatch._hold_ticket_with_bad_level`) защищает только старт. Если карточку правят во время работы воркера, два места остаются без защиты:

1. `src/symphony/orchestrator/retry_reconcile.py`, `_stall_timeout_ms_for_entry`: исключение попадает в общий `except` цикла `_reconcile_running`, и `_reconcile_stall_state` для этой карточки не выполняется — сторож зависания не работает до конца захода.
2. `src/symphony/orchestrator/agent_phase.py`, `_transition_agent_phase`, строка `phase_cfg = _config_for_issue_agent(base_cfg, issue)`: исключение ловит `attempt._transition_phase` и возвращает `_AttemptExit("phase_transition_error", …)` — воркер завершается как «ошибка воркера», дальше обычная цепочка повтора.

Что сделать.

а) В `_stall_timeout_ms_for_entry`: ловить `LevelError`, считать таймаут по базовой конфигурации без уровня (как для карточки без уровня) и писать в журнал **одну** запись `level_unusable_for_stall` на запись запуска (не на каждый такт сверки — иначе журнал будет засорён; для «уже писали» заведи простое поле в `RunningEntry`, `entries.py`, или другое минимальное решение — выбери и объясни в PR).

б) В `_transition_agent_phase`: ловить `LevelError` на строке `phase_cfg = …` и вести себя как при исчерпанном бюджете возвратов (там же выше в функции, `rewind_budget_exceeded`): карточка укладывается в `Blocked` с разделом `## Level` с причиной, функция возвращает `None`, и заход штатно завершается без `phase_transition_error`. Укладку карточки сделай **общей** с `dispatch._hold_ticket_with_bad_level`: вынеси из неё часть «записать в журнал `level_rejected`, перевести в целевое состояние, дописать заметку `## Level`» в одну вспомогательную функцию (например, `_block_ticket_for_bad_level(self, issue, cfg, reason)`), и вызывай её из обоих мест. Поведение старта (`_hold_ticket_with_bad_level`) не менять.

в) Просмотри остальные вызовы `_config_for_issue_agent` в `src/symphony/orchestrator/` во время захода (не на старте): если найдёшь ещё места, где испорченный уровень роняет воркер или сверку, — перечисли в PR; исправляй только если это та же правка в 1–3 строки, иначе только перечисли (не расширяй PR).

## Часть Б. Поле `model_used` в событии `turn_completed`

Сейчас по журналу службы не видно, какой моделью реально ответил `claude`: там только то, что ядро вписало в команду (`--model`). Для статистики лестницы нужна фактическая модель.

Что сделать. Кадр `result` настоящего `claude` содержит `modelUsage` — словарь «полное имя модели → {…, `costUSD`}» (например, `claude-haiku-5-5`), накопительный по сессии; рядом может быть `model_usage_since_last_result` в том же формате (за последний ход). Событие `turn_completed` уже получает этот кадр как `payload` (см. `_apply_cost_usd(issue_id, entry, payload)` в `agent_phase.py`).

1. В `agent_phase.py` добавь маленькую чистую функцию (например, `_model_used(payload) -> str | None`): берёт словарь `model_usage_since_last_result`, если он есть, непустой и словарь; иначе `modelUsage`; возвращает имя модели с наибольшим `costUSD` (при равенстве или отсутствии `costUSD` — первая по порядку; нечисловые значения игнорировать). Если подходящих данных нет — `None`. Имя должно быть непустой строкой не длиннее 100 символов, иначе не используется.
2. Если результат не `None`, добавь ключ `model_used` в данные события `turn_completed` (там, где сейчас собирается словарь с `turn_cost_usd`, `cost_usd`, `session_cost_usd`). Если `None` — ключа нет (чтобы не менять форму событий для старых тестов и других бэкендов).
3. В `src/symphony/orchestrator/diagnostics.py` добавь `"model_used"` в `_ALLOWED_FIELDS["turn_completed"]`.
4. `docs/reference.md`, строка про `modelUsage` («Per-model `modelUsage` is not stored.»): поправь так, чтобы было понятно, что в событие записывается только имя основной модели хода (`model_used`), а разбивка по моделям по-прежнему не хранится.

Разбивку по нескольким моделям в одном ходе и расчёт цены по моделям НЕ делай.
