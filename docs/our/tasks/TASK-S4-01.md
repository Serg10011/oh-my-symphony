## Что сделать

### 1. `ours/bin/post-merge` (+ логика в `ours/hooks/post_merge.py`)

Тонкая обёртка `ours/bin/post-merge` (по образцу `project-render`), вся логика — в `ours/hooks/post_merge.py` (рядом с `project_config.py`, чтобы тесты могли импортировать функции и подменять внешнее). Только стандартная библиотека, Python ≥ 3.11, сообщения для человека — по-русски простым языком.

```
ours/bin/post-merge [--project ИМЯ ...] [--dry-run] [--root DIR] [--main DIR]
```

- `--root` — корень проектов (по умолчанию `~/symphony-projects`, как у остальных скриптов). `--main` — основная папка форка (по умолчанию — основная рабочая копия репозитория, в котором лежит сам скрипт: первая запись `git worktree list --porcelain`; **не** путь самого скрипта, потому что скрипт можно запустить из рабочей копии). `--project` можно повторять; без него — все подходящие проекты.
- **Какие проекты подходят:** каждый `<root>/<имя>/project.toml`, у которого `[project] repo` — клон того же репозитория, что и основная папка (совпадает нормализованный URL `origin`; основная папка тоже считается). Для `oms` это `~/dev/oms-pipeline`. Нечитаемый `project.toml` — предупреждение и пропуск (есть `pc.other_projects`).
- **Шаг 1. Проверки до любых действий:** основная папка стоит на ветке `our-main`, в ней нет незакоммиченных изменений отслеживаемых файлов (иначе отказ с объяснением, без `stash`). То же для клона проекта.
- **Шаг 2. Обновление:** `git fetch` + `git pull --ff-only` в основной папке и в клонах (по одному разу на репозиторий). Не `--rebase`, не `merge` без `--ff-only`.
- **Шаг 3. Что изменилось.** Для каждой цели (основная папка; каждый клон) в файле состояния хранится «последний обработанный коммит» (`applied_sha`); изменения = `git diff --name-only <applied_sha>..HEAD`. Файл состояния — `<main>/tmp_workspaces/post-merge-state.json` (папка в `.gitignore`; путь можно переопределить `--state`). Нет записи — база = коммит, на котором цель стояла **до** этого `pull`. **`applied_sha` обновляется только после успешного выполнения действий этой цели**: если действие отложено (см. ниже «карточки в работе») или упало, повторный запуск всё равно увидит те же изменения. Так «повторный запуск безопасен» и ничего не теряется.
- **Шаг 4. Решения кодом (таблица, не ветвление «на глаз» — правила вынеси в одну структуру в начале модуля):**

  | Изменились файлы | Действие для проекта |
  |---|---|
  | `src/**` основной папки | перезапуск службы |
  | в репозитории проекта (клон) — `tests/**`, `conftest.py`, `pytest.ini`, `pyproject.toml`, `uv.lock`, `package.json`, `package-lock.json`, `**/test_*.py` или `**/*_test.py` | `project-doctor` (служба на это время остановлена; он же пересоберёт `WORKFLOW.md`) |
  | `ours/templates/**`, `ours/prompts/**`, `ours/hooks/project_config.py` основной папки | `project-render` (без перезапуска: служба перечитывает сама) |
  | только `docs/**`, `*.md`, прочее | ничего |

  Если нужны и `project-doctor`, и перезапуск — делается только остановка → doctor → запуск (запуск и есть перезапуск). Если нужны `render` и перезапуск — сначала render, потом перезапуск. Если нужен `render` вместе с `doctor` — только doctor (он сам вызывает render). `ours/hooks/*.py` кроме `project_config.py`, `ours/bin/**`, `ours/tests/**` — действий не требуют (печатай, что подхватится само).
- **Шаг 5. Карточки в работе.** Перед перезапуском и перед остановкой (для doctor) — запрос `GET /api/v1/state` по порту проекта. Если `running + retrying > 0`: **ничего не трогать** для этого проекта и напечатать простым языком: что изменилось, какое действие требуется, почему отложено, что делать (дождаться, когда карточки выйдут из работы, и запустить `ours/bin/post-merge` ещё раз; либо остановить службу самому). Если API не отвечает (служба не запущена) — карточек в работе быть не может: перезапускать нечего (напечатать, как запустить службу), а doctor можно выполнять без остановки. `project-render` проверки карточек не требует (горячая перезагрузка), но если карточки в работе — добавь в вывод одну строку, что новый `WORKFLOW.md` подхватится на следующем такте.
- **Шаг 6. Как делать.** Перезапуск: `launchctl kickstart -k gui/<uid>/local.symphony.<имя>`. Остановка: `launchctl bootout gui/<uid> <board>/launchd.plist`, запуск: `launchctl bootstrap gui/<uid> <board>/launchd.plist` (plist из папки доски, делает `project-launchd`). Если задание не загружено в launchd или plist нет — не падать: напечатать, какой командой службу запустить (`project-launchd`, затем `bootstrap`). `project-doctor` и `project-render` запускай как подпроцессы тем же Python, что и скрипт (`sys.executable`), вывод показывай. **После doctor службу всегда запускать обратно** (`try/finally`), даже если doctor упал; после любого запуска или перезапуска — подождать до ~30 с, пока API ответит, и сообщить результат. Если doctor упал — `applied_sha` не обновлять и сказать, что смотреть.
- **Шаг 7. Уборка (после обновления; только если не `--dry-run`).** `git worktree prune`; удалить рабочие копии разработки, чья ветка уже влита в `our-main` (`git branch --merged our-main`, ветки вида `dev/<код>`), если в копии нет незакоммиченных и неотслеживаемых файлов (`git status --porcelain` пусто; `.venv` игнорируется) — через `git worktree remove` **без `--force`**, затем удалить локальную ветку `git branch -d`; удалить `<main>/tmp_workspaces/inbox/<код>.md` для влитых `dev/<код>`. Основную папку и клоны проектов никогда не удалять; рабочие копии вне `dev/*` не трогать. Что пропущено и почему — напечатать.
- **`--dry-run`:** только `git fetch`, затем печатает план: что подтянется, что изменится, какие действия потребуются, что будет убрано. Ничего не меняет (кроме удалённых ссылок fetch).
- Защита от двух одновременных запусков: файл-замок рядом с файлом состояния; второй запуск отказывает с понятным сообщением. Код возврата: 0 — всё сделано или нечего делать; 1 — отказ или ошибка; 2 — часть действий отложена из-за карточек в работе (чтобы Сергей и я видели «нужно повторить»).
- Вывод — короткий итог в конце: что обновлено, что сделано, что отложено и что делать дальше.

### 2. Тесты `ours/tests/test_post_merge.py`

Настоящие временные git-репозитории (bare «origin», основная папка, клон проекта, корень проектов с `project.toml`), без настоящей службы: `launchctl`, запрос к API и запуск `project-doctor`/`project-render` — подменяемые функции (аргументы или поля объекта, а не monkeypatch глобалов). Обязательные случаи:
- изменён только документ → ни одно действие не вызвано, `applied_sha` обновлён;
- изменён `src/…` → один перезапуск; изменён `src/` и файл теста → остановка, doctor, запуск, без отдельного перезапуска; изменён шаблон/промпт → один render, без перезапуска;
- карточки в работе (`running` > 0 и `retrying` > 0 по отдельности) → ни перезапуска, ни остановки, код возврата 2, `applied_sha` **не** обновлён; повторный запуск после «освобождения» выполняет отложенное;
- API не отвечает → перезапуск пропущен с подсказкой, doctor выполняется без остановки;
- doctor падает → служба всё равно запущена обратно, `applied_sha` не обновлён, код 1;
- `--dry-run` ничего не меняет (HEAD, состояние, рабочие копии) и печатает план;
- повторный запуск без новых коммитов — ничего не делает;
- не `our-main` / грязное дерево → отказ без `pull`;
- проект не на этом репозитории не затрагивается; `--project` ограничивает выбор;
- уборка: влитая чистая рабочая копия `dev/X` удалена вместе с `inbox/X.md`; влитая, но с неотслеживаемым файлом — оставлена; невлитая — оставлена;
- один тест всей командой как подпроцессом: `ours/bin/post-merge --dry-run` на временных репозиториях и поддельный API (`http.server` в потоке на свободном порту); настоящий `launchctl` не вызывать никогда (на не-macOS `launchctl` нет — путь без него должен давать понятное сообщение, а не падение).
