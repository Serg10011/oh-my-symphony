## Как это работает (разобрано по коду ядра, учитывай)

- Агент на этапе Document сам ставит карточке `Human Review`. Затем ядро запускает `hooks.after_run`: первой строкой `check.py hook` (проверки и полный `test.sh`, карточка в `Human Review`), потом стандартный блок, который делает `git add -A` и коммит `wip: …` — **или выходит `exit 0`, если изменений нет**, и тогда ничего после него не выполняется.
- Только после `after_run` ядро заканчивает ход: при состоянии `Human Review`/`Done` оно делает `finalize_delivery_history` (схлопывает все `wip`-коммиты ветки `symphony/<ID>` в один коммит поверх `symphony.basesha`), и **уже после этого** освобождает слот агента. При `Done` ядро дополнительно прогоняет `check.py gate` (повторные тесты; это известная цена, см. «На будущее» п. 2 в записи S4-11 — не оптимизировать здесь) и убирает рабочую копию.
- Значит вливать надо **внутри `after_run`, после коммита стандартного блока**: это единственный момент, когда и работа уже в коммите, и слот ещё занят, и следующая подзадача не может стартовать. Вливаем именно текущий `HEAD` рабочей копии (ещё не схлопнутый — содержимое то же самое).
- `Done` подзадаче ставим в том же `after_run`, командой `symphony board mv <ID> Done --root <доска>` (как откат в `check.py`). Зависимая подзадача (`blocked_by`) стартует только после этого `Done`, а база для неё уже сдвинута — гонки нет. Это и есть доказательство п. 1в для отчёта PR: вливание и Done происходят до конца хода, до освобождения слота и до того, как `blocked_by` отпустит следующую карточку.

### 3. `ours/hooks/integrate.py` — подкоманда `hook`

Запускается из `after_run`: `cwd` — рабочая копия, окружение как у `check.py` (`SYMPHONY_WORKFLOW_DIR`, `SYMPHONY_ISSUE_ID`, `SYMPHONY_PYTHON`). Всегда код выхода 0 (хук не должен ломать ход), любая ошибка — событие `error` в журнале и строка в stderr. Порядок:

1. `ctx = check.build_context("integrate")`; `project = pc.load_project(...)`. Если `[integration] enabled` ложь — молча выйти (без события).
2. Прочитать карточку (`read_card_front`, добавь в неё поле `title`); условия для продолжения: состояние `Human Review`; `task_of(...)` даёт задачу; запись базы `<ID>.base.json` существует и её `task` равен этой задаче (карточка стартовала от интеграционной ветки). Любое несовпадение — событие `skipped` с причиной, карточка не трогается.
3. Взять блокировку карточки `check.try_lock(ctx, 5)` (чтобы не пересечься с шлюзом); занята — `skipped`.
4. Проверить отметку `.pass.json`: есть, `ppid == os.getppid()` **и** `git rev-parse HEAD^{tree}` рабочей копии равен полю `tree` (добавка архитектора: вливаем ровно то содержимое, что прошло тесты; `commit --amend` стандартного блока хэш дерева не меняет, а любая правка файла после проверки — меняет). Поле `head` — только для журнала, с текущим `HEAD` его не сравнивать: после `amend` прежний `HEAD` не предок нового. Нет отметки или чужой `ppid` — `skipped` «проверка этого хода не пройдена»; дерево не совпало — `skipped` «содержимое не совпадает с проверенным», карточка не трогается. Отметку удалить в любом случае после чтения.
5. Рабочая копия должна быть чистой относительно `HEAD` (`git status --porcelain` пуст с учётом `core.excludesFile`; ссылки `kanban`, `docs/<ID>`, `docs/llm-wiki` исключены там же). Грязная — `skipped` с перечнем файлов (значит стандартный блок не закоммитил; вливать незакоммиченное нельзя).
6. Вливание в репозитории кода (`[project] repo`; refs общие для всех рабочих копий), ветка `branch = integration_branch(project, task)`:
   - `old = tip(branch)`; `sub = HEAD` рабочей копии;
   - `git merge-tree --write-tree --name-only <old> <sub>`: код 0 → первая строка — дерево; код 1 → первая строка — дерево, дальше список конфликтных файлов → **конфликт**; другой код — ошибка;
   - дерево равно дереву `old` (`git rev-parse <old>^{tree}`) → **без изменений**: коммит не создаётся, ветка не двигается;
   - иначе `git commit-tree <tree> -p <old> -m "<ID>: <title>" -m "Task: <ЗАДАЧА>\nSource: symphony/<ID>@<sub>"` с `GIT_AUTHOR_NAME/EMAIL` и `GIT_COMMITTER_NAME/EMAIL` = `symphony` / `symphony@local` (как коммиты стандартного блока). **Один родитель** — коммит на интеграционную ветку плоский, один коммит на подзадачу, как ядро само делает при Done; история `wip` остаётся в `symphony/<ID>` и в трейлере `Source`. Это уточнение к формуле архитектора «merge-tree → commit-tree → update-ref»: все три шага на месте, второй родитель не нужен — записать в DECISIONS;
   - `git update-ref -m "integrate <ID>" refs/heads/<branch> <new> <old>` — с проверкой старого значения; отказ (ветку сдвинули) → **одна** повторная попытка от нового конца (снова merge-tree); второй отказ → как конфликт с причиной «ветка сдвинулась».
7. Исходы:
   - **влито / без изменений** → `symphony board mv <ID> Done --root <доска>` (двоичный файл — `check.resolve_symphony_bin(cfg)`), затем `read_card_state` должен показать `Done`; заметка в карточку `## Integration`: `at`, `task`, `branch`, `source` (`symphony/<ID>@<sub>`), `commit` (новый sha или `no changes`), `check: passed (check.py hook)`, `moved to: Done`; событие `done` в `check.log` (поля `task`, `branch`, `commit`, `old_tip`). Если `board mv` не подействовал — событие `error`, заметка с `moved to: Done FAILED`, ветка остаётся сдвинутой (это честно: код влит, а статус пусть поправит Сергей).
   - **конфликт** → ветка не меняется; `board mv <ID> needs_human`; заметка `## Integration` с `result: conflict`, списком файлов и строкой «интеграционная ветка не изменена; разбор — человек»; событие `conflict`.
   - **ошибка** (git упал, нет `symphony`, нет записи базы и т.п.) → ничего не двигать; событие `error`; stderr.

   Done ставим только мы и только здесь; агент маршрутов не вызывает, `allowed_bash` не расширяется (п. 2в архитектора — проверь, что в `project_config.py` ничего не добавилось).
