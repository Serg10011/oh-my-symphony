## Что сломалось (факт, 26.10.2026)

Команда `S4-06.test` (ветка меняет `src/`, поэтому очередь запускает полный `pytest -q`) дала `245 failed, 97 errors`, почти все — `OSError: [Errno 24] Too many open files`. Причина: служба очереди работает под launchd, а у процессов launchd мягкий лимит открытых файлов маленький (256), и все дочерние процессы (проверки) его наследуют. Полный набор тестов ядра столько файлов не умещает. Те же тесты, прогнанные вручную с `ulimit -n 10240`, прошли (3888 passed; 2 падения только из-за node — отсутствия `node_modules` и скачивания node в урезанном окружении). `project-doctor` под той же службой проходит, потому что `test.sh` проекта сам поднимает лимит (в `ours/bin/project-new` об этом есть комментарий про `ulimit -n 10240`). Значит, ошибка только в нашей очереди: она не поднимает лимит. Для веток, меняющих только `ours/`, это не заметно (набор маленький), поэтому раньше не проявлялось.

## Что сделать

1. В `ours/hooks/inbox_runner.py` добавить функцию `raise_open_files_limit(wanted: int = 10240) -> tuple[int, int]`: через модуль `resource` прочитать `RLIMIT_NOFILE`; если мягкий лимит меньше желаемого — поднять его до `min(wanted, жёсткий лимит)` (жёсткий `RLIM_INFINITY` считать «без предела»; на macOS мягкий лимит не может превышать 10240 — это значение по умолчанию и есть `wanted`); любые ошибки (`ValueError`, `OSError`) гасить, не роняя службу; вернуть пару (мягкий, жёсткий) **после** попытки. Лимит никогда не понижать.
2. Вызвать её один раз при старте службы (в `run()` перед `serve()`), чтобы поднятый лимит унаследовали все дочерние процессы: проверки `.test`, `git`, `gh`, `post-merge`. Одну строку в журнал службы (stdout, он попадает в `_launchd.log`): `лимит открытых файлов: мягкий N, жёсткий M`.
3. В `Runner.do_test` перед первой проверкой добавить в отчёт строку `Лимит открытых файлов: мягкий N` (значение из `resource.getrlimit` самой службы — его наследуют проверки), чтобы такой сбой было видно в отчёте сразу.
4. Остальное поведение не менять. Файлы и правила ограничения среды проверок (`clean_env`, `SAFE_PATH`, отсутствие `SYMPHONY_*`) остаются как есть — лимит файлов не переменная окружения, а свойство процесса.

## Тесты (новые в `ours/tests/test_inbox_runner.py`; существующие не менять)

Все подпроцессы со скриптами — только через `sys.executable`; тесты должны проходить и в среде `env -i HOME="$HOME" PATH=/usr/bin:/bin:/usr/sbin:/sbin`.

- `raise_open_files_limit` с подменённым `resource` (`getrlimit` → (256, жёсткий), `setrlimit` записывает вызов): поднимает мягкий до 10240; при жёстком 4096 — до 4096; при мягком уже 20000 — не вызывает `setrlimit` и ничего не понижает; при `OSError`/`ValueError` из `setrlimit` — не бросает, возвращает прежние значения.
- Настоящий подпроцесс (через `sys.executable`, чтобы не менять лимит самого процесса pytest): скрипт ставит мягкий лимит 256 (в пределах жёсткого), импортирует `ours/hooks/inbox_runner.py` по пути, вызывает `raise_open_files_limit()`, затем через `inbox_runner.run_process([sys.executable, "-c", "import resource; print(resource.getrlimit(resource.RLIMIT_NOFILE)[0])"])` запускает дочерний процесс и печатает его вывод; ожидание: значение ≥ min(10240, жёсткий лимит), то есть дочерний процесс унаследовал поднятый лимит. Если жёсткий лимит окружения ниже 1024 — тест пропускается с причиной.
- `do_test`: в отчёте есть строка `Лимит открытых файлов:` (используй существующие подмены `Ops`, как в соседних тестах `.test`).
