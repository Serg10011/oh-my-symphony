# S4-36 — Предупреждения FLAKY в успешном отчёте проверки

Сергей разрешил сравнение двух последовательных независимых реализаций: сначала
архитектор GPT-6.1 Sol / max, затем свежий разработчик GPT-6 Luna / max. Обоим
назначено это одинаковое задание. База обеих попыток —
`our-main @ 22b692f85c6b333d6038e593fb95f833fe535619`.

Проблема уже записана в текущем состоянии DECISIONS: `check.py` скрывает строки
`FLAKY` при успешной проверке. Оператор получает PASS, но не видит предупреждение
о том, что зелёный результат потребовал повтора тестов.

## Проверяемый результат (5 критериев)

1. Успешные отчёты обоих режимов `hook` и `gate` показывают все полные строки,
   начинающиеся с буквального `FLAKY:`, которые уже находятся в `Result.tail`.
   Сохраняются текст и порядок этих строк, включая повторяющиеся предупреждения.
2. Вместе с предупреждениями не выводится остальной успешный тестовый шум.
   Успешный отчёт без таких строк остаётся прежним. Вхождение `FLAKY:` в середине
   строки не считается предупреждением. Название раздела предупреждений свободное.
3. PASS/FAIL, коды возврата, пропуск тестов, метаданные task-карточек, откат и
   допуск Done не меняются. При неуспехе сохраняется прежний полный ограниченный
   хвост вывода; предупреждения отдельно не дублируются.
4. Добавлены регрессионные проверки этого поведения: обычный успех, успех с
   несколькими предупреждениями и шумом, неуспех, фактический вывод обоих CLI
   режимов. Старые тесты не ослаблены. Ruff `ours`, целевой модуль и полный
   `ours/tests` пройдены, команды, время и результаты сохранены.
5. Код ограничен `ours/hooks/check.py`, новыми проверками в
   `ours/tests/test_check.py` и при необходимости исправлением устаревшего
   комментария в `ours/projects/eve/test.sh` без изменения работы обёртки.
   TASK-S4-36, отдельный отчёт попытки, текущее состояние DECISIONS и ROADMAP
   отражают подготовку и проверки, без утверждения о приёмке, слиянии или применении.

## Границы

Обрабатывается только уже имеющийся ограниченный хвост; сбор предупреждений за
пределами `Result.tail` не входит в задачу. Менять API `run_tests`, чтение полного
вывода, JSONL-журнал событий, формат карточек, политику повторов или проверки
допуска не нужно. Без новых зависимостей, правок `src/`, `tests/`, конфигураций,
настроек агентов и оплаты. Не запускать конвейер, не создавать исполняемых карточек,
не менять служебную копию и доски. Слияние и post-merge не разрешены.

## Одинаковая среда проверок

Python 3.12+, собственная `.venv`, проект `-e '.[dev]'`. Полный набор использует
временные локальные HTTP-серверы, процессы и временные Git-репозитории: запускать
его с обычным разрешением среды `require_escalated`, если sandbox мешает этим
локальным тестовым операциям. Не менять проверки или тайм-ауты для обхода среды.
S4-35 с изоляцией E3c пока только открытый PR №65 и НЕ входит в исходную базу.
Если проявится известный E3c/TIME_WAIT сбой, сохранить факт и причину отдельно;
не примешивать исправление PR №65 и не приписывать сбой модели без проверки.

## Порядок эксперимента

Архитектор сохраняет своё решение A в своей рабочей копии и отдельном архиве,
не публикуя его до завершения попытки B. Luna работает только со своей исходной
базой и этим заданием, не читает другие рабочие копии, ветки, архивы эксперимента,
счётчики и решение A. Сначала обе попытки доходят до кода, проверок и отчёта;
коммит, публикацию PR и общую сводку делает архитектор после независимого review.
Результат попытки оформляется в `docs/our/reports/REPORT-26-ATTEMPT.md`.

Стоимость сравнивается по разностям счётчиков чатов. Вариант B включает весь
расход архитектора с передачи задания до завершения проверок и комментариев.
Общая подготовка задания/измерителя и финальная публикация сравнения отдельно
обозначаются, без искусственного отнесения к одной реализации. Время — реальное
прошедшее время, отдельно сохраняется время прогонов. Кэшированные входные токены
являются частью входных, reasoning — частью выходных; их нельзя складывать повторно.
