## 1. Краткий вывод

1. **Зависимости в ядре есть и работают:** `blocked_by` в карточке, проверка циклов при создании, карточка ждёт, пока блокер не станет «успешно завершённым» (у нас — только `Done`). А вот «родитель закрывается, когда закрыты все дети» в ядре **нет** (по коду); есть только группировка по полю `request` и показ счётчиков по группе.
2. **Готовых «нарезчиков» два, и оба плохо ложатся на наш конвейер.** `factory` даёт хороший *формат плана* (карточка с критериями, командами проверки, зависимостями) и идемпотентную загрузку в доску, но заточен под свои колонки (`Ready/Build/Verify`), создаёт карточки в состоянии `Ready` и не знает про `level`. PM Workspace — тяжёлый веб-процесс с человеческими согласованиями на каждом шаге, для ночного автомата не подходит.
3. **Агенту создать карточки командой `board new` формально можно, но на практике неудобно:** у команды и API нет `--level`; наши права `Bash` не пускают команды с кавычками и конвейерами. Надёжнее схема «агент пишет файл-план, хук после хода создаёт карточки» (как коммит делает хук) — правка ядра не нужна, `level` проставляет наш код.
4. **Главная ловушка подтверждена:** ветка `symphony/B` создаётся от *локальной базы* в момент старта B, а код A попадает в базу только после PR, который сливает человек. Решения без правки ядра есть (раздел 3, вопрос 5); рекомендую «ветка-интеграция на задачу» (вариант 3) как основной и «слияние A в базу человеком до старта B» как запасной.
5. **Продолжение той же карточки без правки ядра невозможно** для остановок по `max_turns` и `max_total_turns`: флаг `budget_exhausted` хранится в `state.db` и ни одно место кода его не снимает (по коду; в `state.db` проекта `oms` он есть у `OMS-1` — проверено). Остановку по `max_state_turns` можно обойти сменой состояния карточки + `/resume`. Нужен **точечный сброс**: ≈45 строк кода + ≈80 строк тестов в 3 файлах `src/` (вопрос 6).
6. **Руководителю в API не хватает:** лимита и счётчика «ходов на этап» (`max_state_turns`), лимитов именно *уровня* карточки, числа провалов `check.py` (они вне ядра), флага `budget_exhausted` отдельным полем; счётчики ходов обнуляются при перезапуске службы.
7. **Учёт:** фактическая модель ответа есть в кадре `result` (`modelUsage`) — проверено запуском; запись в учёт — ≈15 строк в ядре. Цена карточки: догадка из DECISIONS **подтверждена** — итог карточки лежит в `runs.cost_usd`, суммировать значения `cost_usd` по событиям нельзя (вопрос 12).
8. **Замечание приёмки №1** (сломанный `level` посреди захода): найдены два места, исправление ≈15 строк (вопрос 13).

## 2. Ответы на вопросы

### А. Нарезка: что есть в ядре

**1. `factory` (Wayfinder → доска).** *По коду.*

Что это. Набор из трёх частей: (а) инструкция для агента `bundled_skills/supergoal/reference/wayfinder.md` — как разбить большую цель на карту `wayfinder/map.md` и билеты `wayfinder/tickets/NNN-*.md`; (б) строгий разбор билетов — `src/symphony/factory/wayfinder.py` (`parse_wayfinder_ticket`); (в) загрузка билетов на файловую доску — `src/symphony/factory/sync.py` (`sync_wayfinder`) и команды `symphony factory init|sync|start` (`src/symphony/cli/factory.py`).

Формат билета (`wayfinder.py`): YAML-шапка `id`, `title`, `route` (GREENFIELD/DEBUG/LEGACY), `blocked_by`, `skills`, `kind`, `browser`; обязательные разделы `## Acceptance criteria` (непустой список), `## Proof commands` или `## Proof` (точная команда в обратных кавычках), `## Non-goals`. Лишнее — ошибка.

Что создаёт `sync` (`_sync_locked`): по карточке на билет в `kanban/` через `tracker.create_with_next_identifier(prefix, …)`; состояние **жёстко `Ready`**, метки `factory`, `route:<…>`, `blocked_by` переводится из ключей билетов в номера карточек; в тело карточки пишется скрытая метка происхождения с хэшем (`symphony-factory-source …`), поэтому повторный `sync` ничего не дублирует и обновляет только карточки, ещё стоящие в `Ready` и не правленные руками. Ключ `--all-tickets` / `--ready-only`: во втором случае создаются только билеты, чьи блокеры уже `done` — это «открывать следующее, когда закончено предыдущее».

Годится ли как шаг «нарезка»:
- **Как образец формата плана — да.** Критерии приёмки + точная команда проверки + «не цели» + зависимости — это почти наша карточка (у нас в карточке ещё команда `test.sh`, область правок, критерии). Проверка графа (неизвестные зависимости, циклы, `_topological_order`) полезна как готовый код, но функции с подчёркиванием — приватные, импортировать их из `ours/` можно, при обновлении ядра может сломаться.
- **Как готовый шаг — нет:** колонки `Ready/Build/Verify` и `contract_profile: factory` (см. `factory/templates/WORKFLOW.md`) не совпадают с нашими `Todo/In Progress/Verify/Document`; состояние `Ready` в нашем `WORKFLOW.md` не объявлено; `level` не создаётся; профиль «factory» включает `auto_merge_on_done: true`, а у нас автослияние выключено по правилу 8; навыки (`supergoal`, `superpm`…) рассчитаны на другой набор агентов (`opencode`).

**2. PM Workspace.** *По коду и документации.*

Как из плана получаются карточки: вручную в веб-интерфейсе (`pm.*` флаги в `WORKFLOW.md`) — идея → требования → дизайн → план → управляемая декомпозиция задач (`tasks.md`, постоянные номера `T-…`), проверка OpenSpec 1.14.2 (нужен Node.js ≥ 20.19), **утверждение человеком конкретной ревизии**, затем «передача» (`handoff`) создаёт обычные карточки с неизменяемой отметкой происхождения `symphony_pm` и зависимостями `blocked_by` (`pm/handoff.py`, `pm/routes.py`, `docs/pm-workspace.md`).

Программно вызвать можно: есть JSON API `/api/v1/pm/changes/...` (создать изменение, патчить документы и WBS, `validate`, `approvals`, `handoffs/preview` и `handoffs`) — более 40 маршрутов (`pm/routes.py`). Но: (а) каждая мутация требует идентификацию проекта, ожидаемую ревизию и ключ идемпотентности; (б) утверждение и передача задуманы как действия человека; (в) помощник планирования работает только через Codex; (г) карточки после передачи «не запускаемые», пока не сойдётся сверка; (д) зависимость `requires_code` проверяет **предка в git** (`pm/authority.py::_verify_ancestry` — `git merge-base --is-ancestor`): если в рабочей копии преемника нет принятого коммита предшественника, запуск отказан. То есть PM **обнаруживает** ловушку из вопроса 5 и отказывает, но не *решает* её (код предшественника не подтягивает).

Вывод: для ночного автомата слишком тяжёлый; полезен как образец «задача с `verification_policy`, `requires_code`/`order_only` зависимостями». Нам нужна идея `order_only` / `requires_code` — различие «только порядок» и «нужен код предшественника».

В процессе службы экспортируется `SYMPHONY_CLI` (`orchestrator/core.py:604`). Штатные промпты (`verify.md`) уже учат: `${SYMPHONY_CLI:-symphony} board new … --description-file -`.
- Маршруты API: `POST /api/v1/issues` (поля `title, state, priority, labels, description, agent_kind, skills, blocked_by, request, identifier|prefix`), `PATCH /api/v1/issues/{id}`, `GET /api/v1/issues/{id}` (`webapi/issue_routes.py`). Идентификатор в API можно не задавать — он выдаётся автоматически (`prefix-N`); в CLI `board new` номер надо задавать самому (гонка при параллельных вызовах).
- **Пробелы:** ни в CLI, ни в API, ни в `update_fields` нет поля `level` (оно известно файловому трекеру и хранится в шапке, `trackers/file.py:92`, `:379`, но ставить его нечем, кроме ручной правки шапки). Неверный `level` при создании не проверяется — карточка уйдёт в `Blocked` только при старте (K14).
- **Файловый трекер и проверка:** `create_validated` под замком доски проверяет формат идентификатора, циклы и висячие блокеры (`trackers/validate.py::validate_ticket_dependencies`). Это работает и из CLI, и из API, и из Python-вызова.

Запись в `allowed_bash` — это префикс команды, который `claude -p` сверяет с *буквальным текстом*: `${SYMPHONY_CLI:-symphony}` как переменную правило не раскроет, надо писать абсолютный путь к `symphony`. Команды с кавычками, `|`, `&&` отклоняются (находка №1 приёмки K14), а `board new` без кавычек в заголовке и описании не вызвать. Узкое правило `Bash(<абсолютный путь>/symphony board new:*)` формально возможно; голые подстановки вроде `*`, `bash`, `env` наш валидатор отвергает (`_BARE_WILDCARDS`).
- **Практичная схема без Bash вообще:** агент пишет план обычным файлом в `docs/<ID>/work/` (папка артефактов уже разрешена через `--add-dir`), а хук `after_run` (как сейчас `check.py hook`) читает файл и создаёт карточки Python-кодом из `ours/`, проставляя `level`, метки, `request`. Права `claude` для этого не расширяются, и «лимиты соблюдает код, а не модель».

**4. Зависимости.** *По коду.*

- Готовность к старту: `orchestrator/dispatch.py::_eligibility_contention_decision` → `core_support._blocker_dependency_is_resolved` → `_successful_blocker_terminal_states`: состояние блокера должно быть *терминальным и не «неудачным»*. Неудачные: `archive, archived, blocked, cancelled, canceled, duplicate, human review, needs_human` (`core_support.py:30`). У нас терминальные — `Human Review, needs_human, Done, Blocked, Archive`, значит **успешный блокер — только `Done`**. Блокер, который ещё выполняется (в работе или в очереди повтора), тоже удерживает зависимого (`_blocker_is_in_flight`).
- Блокер в `needs_human`/`Blocked`/`Human Review`: зависимый **ждёт бесконечно** — не отменяется и не «падает»; в карточке-зависимом `attention` = «Blocked dependency … waiting on unresolved dependency» (`api_views.issue_attention`), одинаково для всех причин. Блокер, которого нет на доске, даёт отдельный сигнал `dangling_dependency`.
- **Следствие для нас:** по правилу конвейера агент заканчивает в `Human Review`, а `Done` ставит человек (`confirm_done`, `ours/prompts/CHANGES.md`). Значит цепочка подзадач сейчас *встанет после первой же подзадачи* до ручного подтверждения. Чтобы цепочка шла сама, `Done` должна ставиться программой после успешного `check.py gate` — это решение человека (см. раздел 5).
- Родитель/эпик/под-задачи: **нет** (поиск по `src/symphony/{issue.py,trackers,orchestrator,webapi}` — ничего). Есть поле `request` (свободная метка группы, например `REQ-1`): `GET /api/v1/requests` и `/api/v1/requests/{id}/schedule` дают по группе счётчики `running/ready/waiting/retrying/successful/needs_action` (`webapi/issue_routes.py::handle_requests`), без автоматического закрытия. «Задача закрывается, когда закрыты все подзадачи» — наш код: читает группу и сам переводит карточку-задачу.

**5. Главная ловушка: откуда B возьмёт код A.** *По коду (`ours/hooks/worktree.py`, `check.py`).*

Что происходит сейчас:
1. `worktree.py create` делает `git worktree add <папка> -b symphony/B refs/heads/<base>` — от *локальной ветки базы в момент старта B* (`worktree.py:create`), и записывает её хэш как `base_sha` (`write_base_record`).
2. A живёт в ветке `symphony/A`. Ядро её никуда не вливает (`auto_merge_on_done: false`, а «хост» ядра у нас — папка доски без git, поэтому штатное автослияние ядра у нас вряд ли заработало бы вообще; не проверялось).
3. A доходит до `Human Review`, человек сливает PR и ставит `Done`; только `Done` отпускает B. Если база к этому моменту обновлена (`post-merge` подтянул её), B увидит код A. Если человек подтвердил `Done`, но не слил PR — B стартует **без кода A**, агент перепишет его заново или не справится, а `check.py` сравнивает только с `base_sha`, ошибки не заметит.
4. Ветка B содержит только коммиты B; при слиянии PR выясняется, что B не вписывается в A.

Варианты:

| # | Вариант | Плюсы | Минусы | Размер правки |
|---|---|---|---|---|
| 1 | **Слияние A в базу до старта B** (человек: PR → `post-merge` → `Done`) | ничего не менять; простая модель; каждый PR маленький | цепочка из N подзадач = N ручных действий, ночью встаёт; `Done` отпускает B даже без слияния — нужно правило «не ставить `Done`, пока PR не влит» | 0 строк кода; правило в промпте руководителя и памятка Сергею |
| 2 | **Цепочка веток**: B создаётся от конца `symphony/A` (`worktree.py` читает блокер из карточки) | полностью автономно; код A виден; `check.py` сравнивает B с концом A — в диффе только правки B | PR от B содержит коммиты A (слияния только по порядку); если A вернули на доработку или «чистый старт» (ветка `attempts/…`), B повисает на старом; блокеры из нескольких веток не решает | ≈60–90 строк в `worktree.py` + проверки в `check.py` + тесты; ядро не трогаем |
| 3 | **Интеграционная ветка на задачу**: подзадачи идут от `symphony/<TASK>`; после успешного шлюза хук вливает ветку подзадачи в `symphony/<TASK>`; человек сливает **один PR** на задачу | автономно; B видит A; один PR на задачу — естественно для «результат — PR»; ветка-интеграция откатывается целиком | новый шаг слияния = новый риск (конфликты — при `max_concurrent_agents: 1` редки, но возможны → `needs_human`); нужна связь подзадач с задачей (метка или `request`); `Done` подзадачам должна ставить программа | ≈150–250 строк в `ours/hooks` (выбор базы по `request`, шаг слияния, обработка конфликта, ключ в `project.toml`) + тесты на настоящих временных git-репозиториях; ядро не трогаем |

Поддерживающий факт для варианта 3: при чистом старте `worktree.py` уже переименовывает старую ветку в `attempts/<ID>-<UTC>`, а `check.py` берёт базу из записи `<ID>.base.json`, а не из «слияния с базой» — значит база подзадачи может быть любым коммитом, проверки считаются верно (`check.py::resolve_base`).
