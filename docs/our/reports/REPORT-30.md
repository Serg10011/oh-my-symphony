## Как проходит составная задача

| Момент | Что делает модель | Что выполняет программа |
| --- | --- | --- |
| Родитель в Plan | Готовит план и проверки подзадач | Проверяет plan.toml, создаёт карточки и зависимости |
| Подзадача в In Progress | Реализует изменение, оставляет доказательства | Сохраняет рабочую копию и результат хода |
| Подзадача в Verify | Проверяет изменение и доказательства | Запускает механические проверки; для подходящих документов используется лёгкий путь |
| Завершение подзадачи | Отдельный Document пропускается | После проверки и коммита сливает результат в integration-ветку, затем ставит Done |
| Все подзадачи Done | — | Готовит итоговый diff родителя, согласует integration-ветку с базой, переводит родителя в Verify |
| Родитель в Verify и Document | Проверяет весь результат, оформляет документацию | Выполняет предусмотренные хуки, полный контроль результата и запись истории |
| Родитель в Human Review | Автоматический агент не нужен | Приёмка человеком; доставка через предусмотренный цикл, без автоматического слияния в our-main |

## Контекст уже разделён по этапам

При смене состояния код останавливает прежний backend, создаёт новый и
открывает новую сессию. Между этапами передаются карточка и файлы результата,
а не вся беседа исполнителя. Verify получает свежий контекст.
`claude.resume_across_turns=true` сохраняет сессию при продолжении внутри
одного этапа; это не отменяет сброса при переходе на другой этап.
Источники: [смена этапа](../../../src/symphony/orchestrator/agent_phase.py),
[цикл попытки](../../../src/symphony/orchestrator/attempt.py),
[Claude backend](../../../src/symphony/backends/claude_code.py).

Следовательно, идея отделять исполнительский контекст уже реализована
в самом конвейере. Результат этапа всё равно требуется прочитать и проверить;
экономическая польза дополнительного помощника или локальной LLM пока
не доказана и в этом аудите не измерялась.

## Что ограничивает расход сейчас

OMS использует Claude Code, оплату `plan` и одного одновременного агента.
Раздел billing в OMS project.toml опущен: plan берётся из действующего
DEFAULT_BILLING; это проверено штатным загрузчиком конфигурации.
Таблица соответствует утверждённому решению 29.10: simple — Haiku low,
standard — Haiku high, complex — Sonnet high, critical — Opus medium.
Эксперименты с чатами Codex эту настройку не переключали.

| Настройка OMS | Что ограничивает |
| --- | --- |
| max_state_turns = 2 | Ходы без смены этапа |
| max_turns = 12 | Внешние ходы в одной попытке |
| max_total_turns = 20 | Общий бюджет внешних ходов выполнения карточки через попытки |
| max_attempts = 2 | Возвраты из проверки/оформления к разработке; автоматической смены модели здесь нет |
| budget_exhausted_state = needs_human | Сохраняет исчерпание общего бюджета в состоянии карточки |
| max_concurrent_agents = 1 | Одновременную работу внутри этой службы, а не общий расход всех проектов |

Один внешний ход Claude backend — один процесс CLI, внутри которого модель
может делать несколько запросов и обращений к инструментам. В сгенерированной
команде OMS нет `--max-turns` или `--max-budget-usd` самого Claude CLI.
Ограничения оркестратора нельзя представлять как лимит внутренних запросов
или как гарантированный остаток подписки.

Backend сохраняет кадры rate_limit_event, но автоматического общего резерва
подписки для всех досок нет; резерв ≥10% и порог 75–80% остаются открытыми
пунктами этапа 5 [ROADMAP](../ROADMAP.md). Отдельная реакция на исчерпание
API-кредита в режиме api не является таким резервом режима plan.
Источники: [учёт событий](../../../src/symphony/orchestrator/agent_phase.py),
[генерация настроек оплаты](../../../ours/hooks/project_config.py).

Счётчики Claude здесь имеют свою семантику: input_tokens и отдельно
cache_input_tokens, куда backend складывает чтение и создание кэша.
Формулу обработки входа из проб Codex переносить на эти данные нельзя.
Историческая оценка cost_usd не доказывает фактический расход лимита
подписки. Новых денежных оценок, процентов расхода и обещаний экономии нет.

## Следующая задача — предложение для Сергея

Предлагается старый незавершённый пункт `Merging` для подзадач.
Сейчас хук подхватывает прошедшую Verify подзадачу в Human Review,
проверяет её результат, сливает в integration-ветку и только затем ставит
Done. Нарушения порядка «сначала слияние, потом Done» не обнаружено.
При этом Human Review временно обозначает и машинную сборку подзадачи,
и настоящую ручную приёмку всей задачи.

Предлагаемые границы: отдельное состояние машинной сборки подзадач;
его обработка без вызова модели; Done после успешного слияния; понятный
отказ при конфликте и возможность безопасно продолжить после прерывания.
Ручная приёмка родителя, модели, оплата и число параллельных агентов
сохраняются. Совместимость старого маршрута через Human Review следует
проверить при разработке. Это предложение ещё не утверждено; код и
конфигурация Merging не подготовлены и на досках не включены.

Другие старые пункты — `.clean`, ladder, manager-diagnose, stage_levels —
остаются открытыми. Их наличие в прежнем порядке не разрешает автоматически
начать все эти работы. Новых исполнителей и проб локальных LLM нет.
