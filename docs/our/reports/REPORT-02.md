## Главное

1. **Единой точки записи статуса «Done» нет, и поставить её без правки ядра нельзя.** Агент правит файл карточки напрямую, мимо кода Symphony. Команда `board mv`, веб-API и оркестратор пишут в файл разными функциями.
2. **Зато есть одна точка, где ядро «принимает» Done**, если за карточкой стоит рабочая папка: функция `_auto_merge_done_gate_or_block` (`src/symphony/orchestrator/blocked_recovery.py:467`). Её вызывают три из четырёх путей приёмки Done. Там же уже есть готовая реакция на провал: карточка выводится из Done, в неё пишется заметка, папка сохраняется. Это лучшее место для `agent.done_gate_command`.
3. **Почему Todo→Done не остановили:** контракты этапов проверяют только то, что агент должен был написать на *этапе, с которого уходит*, а у `Todo` контракта нет. Подтверждено запуском: пустая карточка из `todo` проходит, из `in progress`/`verify`/`document` — нет.
4. **Контракты вообще не вызываются** при переносе в Done вне хода агента: через `confirm_done`, веб-API, `board mv`, при «приёмке» в `reconcile` и при автопереносе из Human Review. Включение `stage_contracts: on` этого не меняет.
5. **Наш `needs_human` контракты не отключает** [запуск]: решение «включены ли контракты» зависит только от активных колонок, список терминальных статусов в нём не участвует.
6. **Находка, важная для решения «финал — Human Review»:** каждый такт опроса ядро само переводит карточки из `Human Review` в `Done` без каких-либо проверок, если в тексте карточки есть раздел `## As-Is -> To-Be Report` (его агент и так пишет) и нет «маркера вмешательства» [запуск]. Подробности — в разделе «Вопрос 1», пункт E1.
7. **Папку `needs_human` ядро не сохраняет**, а список сохраняемых статусов (`blocked`, `human review`) зашит в код (`retry_reconcile.py:1192`) и конфигурацией не меняется. Но работа агента при этом не пропадает, если `auto_commit_on_done` включён: она фиксируется коммитом в ветке `symphony/<ID>` до удаления.
8. **Падение `after_run` оставляет след** в журнале и в файлах на диске, но не в карточке и не в API.

**Что нужно решить тебе** — в разделе «Вопрос 3» (варианты A–C). Я остановилась на описании вариантов, как ты просил, и ничего не придумывала в обход.

### 1.2. A. Агент правит файл

- **[код]** Агент пишет `state: Done` в YAML карточки (или вызывает `symphony board mv`, см. B). Код Symphony при этом не участвует.
- Ядро узнаёт о результате двумя способами:
  1. **После хода** — `_evaluate_turn_result` (`src/symphony/orchestrator/attempt.py:961`) перечитывает карточку; вызывается из цикла ходов сразу после `after_run` (`attempt.py:656` → `:671`).
  2. **При опросе** — `_reconcile_one` (`src/symphony/orchestrator/retry_reconcile.py:748`) видит, что у работающего агента карточка стала терминальной.
- Последствия Done, увиденного после хода: цикл останавливается (`attempt.py:1131-1132`), затем `_finalize_clean_exit` (`src/symphony/orchestrator/worker_exit.py:660`): снимок в git (`:679`), потом `_post_process_done` (`:859`) → «ворота» слияния → `after_done` → удаление папки.

### 1.3. B. Команды `symphony board …`

- **[запуск]** `symphony board mv P-1 Done` на временной доске перевела карточку из `Todo` в `Done` без единой проверки. `board show` потом печатает строку `delivery: Done alone does not confirm target merge or workspace cleanup.`
- **[запуск] Поправка к проба-наблюдению.** Строку `delivery: …` в карточку ядро **не дописывает**: её печатает команда `board show` при показе карточки со статусом Done (`src/symphony/cli/board.py:339-341`). В файле карточки её нет (я проверила содержимое файла). Если ты видел её в самой карточке, значит это был вывод `board show`, а не запись в файл.
- **[запуск] Находка:** `board mv` принимает **любое** имя статуса: `symphony board mv P-1 NoSuchState` вернула код 0 и записала `state: NoSuchState`. Команды `board new` и `board update` статус проверяют (`board.py:184-196`, `:260-270`), а `cmd_mv` (`board.py:229-238`) — нет. Это подтверждает и дополняет REPORT-01 (раздел 4.1).
- Запись: `FileBoardTracker.transition` (`src/symphony/trackers/file.py:947-957`) просто ставит `front["state"] = new_state`. `update_state` (`:959-970`) — обёртка над ним.

### 1.4. C. «Confirm done»: TUI, JSON API, веб-панель

- **[код]** Клавиша `c` — `Binding("c", "confirm_done_focused", "Confirm done")` (`src/symphony/tui/app.py:126`) → `_confirm_done_issue` (`:700-710`) → `Orchestrator.confirm_done` (`src/symphony/orchestrator/api_views.py:57`).
- Тот же метод вызывают `POST /api/v1/<ID>/confirm-done` (`src/symphony/server.py:113-123`, маршрут `:226`) и `PATCH /api/v1/issues/<ID>` с переходом «Human Review → Done» (`src/symphony/webapi/issue_routes.py:608-619`).
- Что проверяет `confirm_done`: карточка должна быть в `Human Review` (`api_views.py:73`, ещё раз `:152`), агент не должен работать, папка должна существовать; затем история git (`:160`), «ворота» слияния `_auto_merge_done_gate_or_block` (`:168`) и только потом запись `Done` (`:173`).
- Это **единственный** путь, где проверка стоит **до** записи Done: если «ворота» не пропустили, карточка в Done не попадает.
- Контракты этапов здесь **не вызываются** (в `api_views.py` нет ни `evaluate_contract`, ни `_enforce_stage_contract`).

### 1.5. D. Веб-доска и веб-API (любой другой переход)

- **[код]** `handle_issue_patch` (`src/symphony/webapi/issue_routes.py:546`, регистрация `:709`). Статус проверяется только на «существует ли такой статус в доске» (`_check_state`, `src/symphony/webapi/validation.py:286-292`).
- Если переход **не** из `Human Review` в `Done`, то записью занимается `tracker.update_fields(...)` (`issue_routes.py:622`; сама функция — `src/symphony/trackers/file.py:1318`, запись состояния — `:1346`). Единственная защита: ответ 409, если агент уже работает над карточкой (`issue_routes.py:598-607`).
- То есть перетаскивание карточки на колонку Done из `Todo` в веб-доске ничем не останавливается. [код]
- Создание карточки сразу в Done: через CLI возможно ([запуск]: `board new P-2 … --state Done` создала карточку). Через веб-API создание (`issue_routes.py:363`) на допустимость начального статуса я не проверяла.

### 1.6. E. Автоматические переносы ядра

**E1. Human Review → Done (важно!)**

- **[код]** Функция `_auto_normalize_legacy_human_review_done` (`src/symphony/orchestrator/blocked_recovery.py:520-576`) вызывается на **каждом такте опроса** (`src/symphony/orchestrator/dispatch.py:141`). Для каждой карточки в `Human Review`, у которой `_legacy_human_review_is_done` (`blocked_recovery.py:238`) истинно, она дописывает в карточку раздел `## Human Review Normalized` и ставит `Done`.
- Условие «истинно» — в тексте есть строка `Confirm Done` **или** раздел `## As-Is -> To-Be Report` / `## Unblock Note`, и нет «маркеров вмешательства» (`## Operator Action`, `## Intervention Required`, `## History Failure`, `## Merge Missing`, строка «Do not confirm…») (`blocked_recovery.py:111-139`).
- **[запуск]** Я проверила функцию на примере: карточка в `Human Review` с разделом `## As-Is -> To-Be Report` → `True` (будет переведена в Done); та же карточка с добавленным `## Operator Action` → `False`; пустой текст → `False`; карточка в `needs_human` с тем же отчётом → `False`.
- **Почему это важно для нас.** Решение журнала «финальное состояние — Human Review, человек подтверждает Done» не выполняется само: при включённом ядре карточка с отчётом уйдёт в Done на следующем такте, **без** `confirm_done`, без «ворот» слияния и без нашей проверки. Отключающей настройки я не нашла (`_human_review_done_state`, `blocked_recovery.py:222`, возвращает `None` только когда в доске вообще нет статуса Done).
- Варианты — в разделе «Вопрос 3», пункт «Дополнительно».

**Какой терминальный статус выбирает ядро** (важно для порядка в `terminal_states`):

- `_terminal_state_matching` (`helpers.py:246`) берёт **первый по списку** статус, в имени которого есть ключевое слово, перебирая слова по порядку.
- «К человеку» (`_human_review_target_state`, `helpers.py:262`): слова `human`, `review`, `block`. При твоём порядке `["Human Review", needs_human, Done, Blocked, Archive]` выберется `Human Review` (он первый). **Если поставить `needs_human` раньше `Human Review`, ядро начнёт отправлять туда.**
- «После провалов бюджета/истории» (`_rewind_budget_target_state`, `helpers.py:284`, и `blocked_recovery.py:347`): сначала `block`, потом `human` → выберется `Blocked`, а не `needs_human`.
- Вывод: **сам ядро `needs_human` никогда не выбирает** при этом порядке. Туда карточку может перевести только наш скрипт/агент.

### 1.7. Где единая точка?

- **Записи — нет** (см. таблицу: агент, `transition`, `update_fields`, `confirm_done`, нормализатор — разные места).
- **Приёмки — частично да.** Все пути, где за Done стоит рабочая папка, сходятся в функции `_auto_merge_done_gate_or_block` (`blocked_recovery.py:467`):

| Путь приёмки | Вызов |
|---|---|
| Агент закончил в рамках работающего воркера | `worker_exit.py:865` (внутри `_post_process_done`) |
| `reconcile` увидел Done у работающего воркера | `retry_reconcile.py:1019` |
| `confirm_done` (TUI / API / веб) | `api_views.py:168` |
| Старт службы с уже существующей папкой Done | **не вызывается**: свой код `retry_reconcile.py:1199-1260` |

- **Не покрыто** никакой приёмкой: карточка, переведённая в Done, когда агент не работает и папки нет или служба не перезапускалась (пути B, D, E1). Карточка просто стоит в Done; ядро её не просматривает.

### 2.2. Почему Todo→Done без доказательств не остановили

- **[запуск]** Набор «производящих» этапов по умолчанию — `in progress, verify, document, learn, done` (`src/symphony/orchestrator/contracts.py:181-183`). **`todo` в нём нет.** Я вызвала `evaluate_contract` с пустым телом карточки:

| Этап, с которого ушла карточка | Прошла? | Чего не хватает |
|---|---|---|
| `todo` | **да** | ничего не проверяется |
| `in progress` | нет | 5 пунктов (разделы и папка работы) |
| `verify` | нет | 5 пунктов |
| `document` | нет | 2 пункта |

- Итого: переход `Todo → Done` одним ходом **минует контракт по построению** (контракт этапа «Todo» не существует). Это объясняет твоё наблюдение [код].
- Второй нюанс [код]: проверяется контракт этапа, с которого карточка **ушла**, а не «контракт Done». Например, `In Progress → Done` проверит только разделы `In Progress` (`## Plan`, `## Acceptance Tests`, `## Done Signals`, `## Implementation`, `## Self-Critique` + непустую папку `docs/<ID>/work`), а требования к самому Done (`## As-Is -> To-Be Report`, `## Merge Status`, папки `qa`/`work`; `contracts.py:414`) применяются только когда карточка *уходит из Done*, чего в нашей доске не бывает.
- Третий нюанс [код]: ядро сравнивает только состояние в начале и в конце хода. Если за один ход агент прошёл `Todo → In Progress → Done`, то для ядра это переход «Todo → Done».

### 2.3. Срабатывают ли контракты при…

| Ситуация | Срабатывают? | Основание |
|---|---|---|
| Перенос в терминальный статус, который не Done (Blocked, Human Review, needs_human) | **Нет** (кроме `blocked` в профиле `factory`) | Условие `_is_successful_terminal_state` (`attempt.py:1069`, `helpers.py:271-281`); в комментарии `attempt.py:1058-1063` так и сказано |
| Перенос в Done вне агента (`confirm_done`, веб, `board mv`, нормализатор E1) | **Нет** | Вызов контракта есть только в цикле хода (`attempt.py:1079`) и при смене этапа (`agent_phase.py:162`) |
| Перенос в Done, замеченный `reconcile` у работающего воркера | **Нет** (кроме `factory`) | `retry_reconcile.py:925`: вызывается только `_enforce_factory_exit_contract` (`dispatch.py:1122`), у него фильтр `producing in {"build","verify"}` |

### 2.4. Родственные проверки

- **Ворота истории** `finalize_delivery_history` (`src/symphony/workspace.py`, вызов `worker_exit.py:777`, `api_views.py:160`) — только если включён `auto_commit_on_done` и статус `done`/`human review`: проверяет, что работа записана в git.

## Вопрос 4. Что происходит при ненулевом коде `after_run`

### 4.1. Кратко

Код возврата хука **ничего не решает**, но **след остаётся**: в журнале службы и в трёх файлах на диске. В карточке, в событиях запуска и в JSON API следа **нет**.

### 4.2. Как это устроено [код]

1. `after_run` вызывается после каждого хода (`attempt.py:898`, `workspace.py:655`). Если папки уже нет — хук пропускается с записью `hook_after_run_skipped_missing_cwd` уровня info (`workspace.py:661-664`).
2. `_run_hook` (`workspace.py:854`) запускает `bash -lc <скрипт>` в рабочей папке с `stdin=/dev/null` и общим таймаутом `hooks.timeout_ms`.
3. **Независимо от кода** сразу пишутся файлы вывода (`_write_hook_output_artifacts`, `workspace.py:804-852`) в `<workspace.root>/.symphony-workspace-hook-output/<ключ папки>/<UTC-метка>-after_run.{stdout,stderr,json}` (`workspace.py:32`). В `.json` лежат `hook`, `cwd`, `returncode`, пути к файлам вывода и `warning_patterns`. Эта папка лежит **рядом** с рабочими папками, а не внутри них, поэтому удаление рабочей папки её не трогает.
4. При `rc != 0` дополнительно `log.error("hook_failed", hook, cwd, returncode, stderr[:400], artifact)` (`workspace.py:955-962`) и исключение `SymphonyError("hook after_run exited N; stderr: …; full output: <путь>")`.
5. При таймауте — `log.error("hook_timeout", …)` (`workspace.py:931-936`), `returncode: -1` в `.json`, то же исключение.
6. Исключение ловит `after_run_best_effort` и **проглатывает**: `log.warning("hook_after_run_failed", path, error)` (`workspace.py:665-668`). Дальше ход считается обычным.
7. При успехе: `log.info("hook_completed", …)` (`workspace.py:972`), `.json` с `returncode: 0`.

### 4.3. Можно ли отличить «хук упал» от «хук отработал»

| Где смотреть | Как отличить |
|---|---|
| Журнал службы (stderr процесса; файла журнала ядро не создаёт, `logging.py:45`) | События `hook_completed` vs `hook_failed` / `hook_timeout` / `hook_after_run_failed` |
| Файлы `…/.symphony-workspace-hook-output/<ключ>/*-after_run.json` | Поле `returncode`: `0` — отработал, `≠0` — упал, `-1` — таймаут |
| Карточка | **Нет следа** |
| `/api/v1/state`, поле `last_error` | **Нет следа** (хук не пишет в `debug.last_error`, ср. `api_views.py:612`) |
| События запуска (`_append_run_event`) | **Нет следа** |

Для твоей пробы: в журнале должна быть пара `hook_failed` + `hook_after_run_failed`, а в папке вывода — `.json` с `returncode: 1`. Если журнала уже нет, `.json`-файл остался на диске. [код: ожидание, не проверено запуском]

### 4.4. Что делать нам

- Хук-проверка, которая *обязана* что-то запретить, не может опираться на код возврата. Либо она сама меняет статус карточки (как предлагал REPORT-01), либо проверка встроена в ядро (Вопрос 5).
- Хук может сам оставить след, который виден человеку: дописать в карточку раздел с результатом (`symphony board` для добавления текста нет; текст можно дописать файлом карточки или через `$SYMPHONY_CLI board update --description`, это заменяет всё тело, поэтому осторожно). Это вне рамок исследования.

## Вопрос 6. Что удаляет рабочую папку и можно ли сохранить `needs_human`

### 6.1. Кто и когда удаляет [код]

Удаление — всегда `WorkspaceManager.remove` (`src/symphony/workspace.py:701`): сначала хук `before_remove` (его сбой игнорируется, `:713-714`), потом `shutil.rmtree` с повторами (`_force_rmtree`, `:72`). Ветку git `remove` **не** удаляет (в коде нет `branch -D` на этом пути), что соответствует твоему наблюдению про `symphony/<ID>`.

Вызывают `remove` пять мест:

| Когда | Что удаляется | Код |
|---|---|---|
