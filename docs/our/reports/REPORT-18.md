## 1. Замок может освободить путь, пока новый владелец ещё работает

**Приоритет: исправить до закрытия технической приёмки.**
Место: `~/symphony-projects/eve/test.sh`, `break_stale_lock`, строки 137–144.

`acquire_lock` читает PID и отдельно проверяет, жив ли процесс. Между этой
проверкой и `mv "$LOCK_DIR" "$moved"` другой участник может успеть очистить
старый замок и занять его заново. Очиститель тогда переименует уже **живой**
замок. Проверка PID после переименования обнаружит подмену, но исходный путь
в этот момент свободен: ещё один участник может успешно выполнить `mkdir`
и начать свой прогон одновременно с прежним владельцем.

Попытка вернуть каталог тоже некорректна: если `LOCK_DIR` уже существует,
обычный `mv "$moved" "$LOCK_DIR"` помещает старый каталог внутрь нового,
а не возвращает владение. Команда при этом заканчивается успешно.

**Как воспроизведено.** Из действующего `test.sh` извлечена неизменённая
функция `break_stale_lock`; `LOCK_DIR` направлен в новую временную папку.
Смоделировано допустимое чередование трёх участников:

1. Очиститель раньше прочитал старый PID `1001`.
2. Новый владелец уже записал `2002` в `test.lock/pid`.
3. Сразу после первого настоящего `mv` другой участник создаёт каталог
   на освободившемся пути и пишет PID `3003`; затем функция продолжает работу.

Детерминированная проверка на файловой системе дала:

```text
CONTENDER_ACQUIRED_AFTER_RENAME=3003
CURRENT_OWNER=3003
DISPLACED_OWNER=2002
```

`DISPLACED_OWNER` прочитан из вложенного `test.lock/test.lock.stale.<PID>/pid`.
Чередование было управляемой имитацией; реальные параллельные прогоны Vitest
не запускались, настоящий `~/symphony-projects/.locks/test.lock` не трогался.

Нужна блокировка, сохраняющая исключительное владение на всё время прогона
и не освобождающая путь живого владельца при очистке. Исправить только
поведение второго `mv` недостаточно: окно для другого запуска уже открылось.
Проверка исправления должна воспроизводить конкуренцию при очистке старого
замка и подтверждать, что в защищённой секции одновременно один участник.

## 2. Корневой testsuite не заменяется результатом повтора

**Дополнительное замечание к поддерживаемому формату.**
Место: `~/symphony-projects/eve/bin/junit-merge.py`, строки 116–120.

Загрузчик и описание функции явно поддерживают оба корня: `<testsuites>`
и `<testsuite>`. Для второго `_file_suites` возвращает пару `(root, root)`,
но `merge` заменяет узел только при `suite is not parent`. Поэтому успешный
повтор объявляется прошедшим, а исходный корень с падением остаётся в XML.

Минимальные данные, переданные настоящей CLI-команде `junit-merge.py merge`:

```xml
<!-- первый прогон -->
<testsuite name="retry.test.ts"><testcase name="flaky"><failure/></testcase></testsuite>
<!-- повтор -->
<testsuite name="retry.test.ts"><testcase name="flaky"/></testsuite>
```

Фактический результат:

```text
exit: 0
FLAKY: retry.test.ts
PIPELINE_TESTS passed=0 skipped=0 failed=1
```

Последняя строка получена отдельным вызовом `summarize.py` для объединённого
XML. `check.py` отвергнет такую сводку: это ложный отказ, не пропуск плохого
кода. В штатном проверенном формате Vitest `<testsuites>` дефект не проявился.
Нужно заменить корень при одиночном `<testsuite>` либо явно отказаться от
его поддержки; проверить согласованность кода возврата, XML и итоговой строки.
