## Вопрос 1. Модель, усилие и авторизация на задачу

### 1.1. Как устроено сейчас: `claude`

- Команда запуска — **одна строка из конфигурации**, общая для всех задач. По умолчанию: `claude -p --output-format stream-json --include-partial-messages --verbose` (`src/symphony/workflow/constants.py:106-108`). Её можно заменить в `WORKFLOW.md` в блоке `claude.command` (`src/symphony/workflow/builder.py:486-487`).
- На каждый ход (turn) запускается новый процесс. Команда собирается так: берётся `claude.command`, сразу после слова `claude` вставляются `--add-dir <путь>` для папок git вне рабочей папки, в конец дописывается `--resume <id сессии>` для продолжения (`src/symphony/backends/claude_code.py:122-128`, вставка — `:48-64`, суффикс — `src/symphony/backends/per_turn.py:586-595`).
- Запуск идёт через `bash -lc "<команда>"` — то есть через *login-оболочку* (`src/symphony/backends/per_turn.py:403-418`). Промпт передаётся через stdin.
- **Поля «модель» и «усилие» для `claude` в конфигурации нет.** Класс `ClaudeConfig` содержит только `command`, три таймаута и `resume_across_turns` (`src/symphony/workflow/config.py:360-372`). Единственный способ выбрать модель — дописать `--model ...` в строку `claude.command`.
- Установленный здесь `claude` (версия 2.1.309) знает флаги `--model <алиас или полное имя>` и `--effort <low|medium|high|xhigh|max>` (проверено по `claude --help`). Значит, с точки зрения самого Claude Code модель и усилие задаются обычными флагами.

### 1.2. Как устроено сейчас: `codex`

- Бэкенд Codex — один долгоживущий процесс `codex app-server`, общение по JSON-RPC (`src/symphony/backends/codex.py:309-325`, команда по умолчанию — `src/symphony/workflow/constants.py:46`).
- Модель и усилие **есть в конфигурации**: `codex.model` и `codex.reasoning_effort` (`src/symphony/workflow/config.py:355-356`, разбор — `src/symphony/workflow/builder.py:477-481`). Значения по умолчанию: `gpt-5.5` и `high` (`src/symphony/workflow/constants.py:53-54`). Имена `gpt-6-luna` и `gpt-6.1-sol` из спецификации — просто значения этого поля; допустимость имён проверяет сам Codex, а не оркестратор.
- Они уходят в запрос `turn/start` на **каждом ходе**: `params["model"]` и `params["effort"]` (`src/symphony/backends/codex.py:574-577`). В запросе `thread/start` модели нет (`:484-489`).
- Важная тонкость: пустое значение `codex.model` **не отключает** передачу — `_as_str(...) or DEFAULT_CODEX_MODEL` подставит `gpt-5.5` (`builder.py:477`). Поэтому обойти параметр запроса флагом `-c model=...` в команде нельзя: параметр `turn/start` всё равно будет передан.

### 1.3. Можно ли задать модель и усилие во frontmatter отдельной задачи

**Нет, ни для `claude`, ни для `codex`.**

- Во frontmatter задачи ядро понимает фиксированный набор ключей (`src/symphony/trackers/file.py:78-95`), модель в нём нет. Разбор задачи в объект `Issue` (`src/symphony/issue.py:28-49`, `src/symphony/trackers/file.py:344-388`) читает из frontmatter, помимо общих полей, только `agent_kind`/`agent.kind`, `last_agent_kind`, `skills`, `request`, `symphony_pm`.
- **Что задаётся на задачу сейчас — только вид бэкенда** (`claude`, `codex`, …): `agent_kind` во frontmatter, затем `agent.stage_kinds` по колонкам доски, затем глобальный `agent.kind` (`src/symphony/workflow/config.py:329-343`, `src/symphony/orchestrator/helpers.py:175-179`, использование — `src/symphony/orchestrator/dispatch.py:1291`). Это даёт «эту задачу на Claude, ту на Codex», но не «эту на Haiku, ту на Sonnet».
- Конфигурация `ServiceConfig` неизменяемая (`frozen`) и общая; в `BackendInit.cfg` попадает она целиком, без учёта задачи (`src/symphony/orchestrator/attempt.py:449-453`, `src/symphony/orchestrator/agent_phase.py:529-533`).

### 1.4. Точка расширения и минимальная правка

**Вариант A — без правки ядра (только для `claude`): обёртка-скрипт.**

1. Задача получает во frontmatter свой ключ, например `tier: L1`. Парсер ядра неизвестные ключи не отбрасывает: при перезаписи задачи ядро работает с полным словарём frontmatter (`src/symphony/trackers/file.py:926-945`, `write_ticket_atomic`) — по коду; отдельным тестом это не проверялось.
2. В `WORKFLOW.md` пишется `claude.command: ours/bin/claude-tier.sh -p --output-format stream-json --include-partial-messages --verbose` (путь к скрипту — наш, в `ours/`).
3. Скрипт определяет задачу и собирает настоящую команду. **Откуда он знает задачу:** рабочая папка агента называется как идентификатор задачи после очистки символов (`src/symphony/issue.py:93-95`, `src/symphony/workspace.py:511-513`), а доска подключена в рабочую папку ссылкой (`src/symphony/orchestrator/helpers.py:63-72`, имя ссылки — `SYMPHONY_BOARD_ROOT_NAME`, по умолчанию `kanban`). Скрипт берёт `basename "$PWD"`, читает `kanban/<ID>.md`, достаёт `tier`, превращает в `--model haiku|sonnet --effort ...` и делает `exec claude "$@" --model ... --effort ...`.
4. **Обязательное условие:** слова `--add-dir` ядро вставляет только если команда начинается с литерального `claude` (`claude_code.py:56-60`). Для обёртки этого не будет, но список папок ядро кладёт в переменную окружения `SYMPHONY_GIT_WRITABLE_ROOTS` (`src/symphony/utils/git_sandbox.py:161`, `claude_code.py:117-120`). Скрипт обязан сам превратить её в `--add-dir` (путь разделён `os.pathsep`), иначе `git add`/`git commit` в рабочей папке упадёт на записи в общую базу объектов (причина описана в `git_sandbox.py:1-24`).
5. Скрипт должен передавать дальше все свои аргументы (`"$@"`), потому что `--resume <id>` ядро дописывает **в конец** строки (`per_turn.py:586-595`).

Плюсы: ядро не меняется. Минусы: связь «задача → модель» держится на соглашении (имя папки и имя ссылки на доску), а не на контракте; только `claude`; ключ `tier` не виден в веб-панели и API как отдельное поле.

**Вариант B — небольшая правка ядра (нужна для `codex`, желательна и для `claude`).**

1. Добавить в `Issue` два необязательных поля `model` и `effort` (`src/symphony/issue.py`), читать их из frontmatter (`src/symphony/trackers/file.py`, функция `issue_from_file` и список ключей `_CANONICAL_FRONT_MATTER_KEYS`). Допустимые значения проверять по белому списку из `WORKFLOW.md` (чтобы опечатка не уходила в CLI).
2. **Расширить уже существующую функцию** `_config_for_issue_agent(cfg, issue)` (`src/symphony/orchestrator/helpers.py:205-222`). Сейчас она через `dataclasses.replace` подменяет только `agent.kind` по закреплению на задаче и колонке. Это единственная точка, где конфигурация подгоняется под задачу, и она уже вызывается во всех нужных местах: при старте попытки (`src/symphony/orchestrator/attempt.py:290`), при смене колонки (`src/symphony/orchestrator/agent_phase.py:217`) и при повторе (`src/symphony/orchestrator/retry_reconcile.py:645`). В неё добавляется подмена:
   - `cfg.codex.model` и `cfg.codex.reasoning_effort` (для `codex` дальше всё работает само — `codex.py:574-577`);
   - `cfg.claude.command`: вставка `--model X --effort Y` после слова `claude` (по образцу `_inject_add_dirs`, `claude_code.py:48-64`).
3. Править места сборки `BackendInit` (`attempt.py:449`, `agent_phase.py:529`) **не нужно** — они получают уже подменённую конфигурацию.
4. Заметно проще, если сопоставление уровня и модели хранить в `WORKFLOW.md` (`tiers: {L1: {claude: {model: haiku, effort: medium}, codex: {...}}}`), а в задаче писать только `tier: L1` — тогда уровни из спецификации (раздел 5.1) переносятся в конфигурацию, а не в код.

### 1.5. Авторизация: как бэкенд выбирает способ входа

- **Оркестратор способ авторизации не выбирает вообще.** В коде нет ни одного упоминания `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CODEX_HOME` или очистки ключей (поиск по `src/symphony`: ключи упоминаются у трекеров Linear/Jira, у Gemini в `doctor` и в подсистеме PM Workspace — `src/symphony/pm/codex_compatibility.py:36-37`, где они вычищаются из окружения; к основным бэкендам `claude`/`codex` это не относится). Способ входа выбирает сам CLI по тому, что нашёл в окружении и в своём каталоге настроек.
- **Окружение агента = всё окружение оркестратора + добавки.** Для `claude`: `{**os.environ, **git_roots_env, **init.env}` (`src/symphony/backends/per_turn.py:414`, `:175`); для `codex`: `os.environ.copy()` + то же (`codex.py:392-396`). Фильтрации нет: любая переменная, которая есть у `symphony`, видна агенту, включая ключи.
- **Добавки от оркестратора** (`BackendInit.env`): `SYMPHONY_TOKEN_EMA`, `SYMPHONY_TOKEN_BUDGET` и (при откате) `SYMPHONY_REWIND_SCOPE` (`src/symphony/orchestrator/dispatch.py:1209-1250`), плюс `SYMPHONY_GIT_WRITABLE_ROOTS`; у `codex` ещё `SYMPHONY_CODEX_WRITABLE_ROOTS` (`codex.py:406`). **Идентификатора задачи среди них нет** — поэтому в варианте A задача определяется по имени рабочей папки.
- Поскольку запуск идёт через `bash -lc`, команда подхватывает и переменные из профиля пользователя (`~/.profile` и т. п.) — ещё один источник ключей, о котором легко забыть.

**Следствие для конфигурации B (Claude Max + API-кредит).** Если у процесса `symphony` в окружении есть `ANTHROPIC_API_KEY`, то, по документации Claude Code, `claude` будет работать по ключу (деньги кредита), а не по подписке. В этой песочнице проверить это нельзя (нет учётных данных), поэтому помечаю: **«по документации, не проверено»**. Практический вывод: способ входа определяется тем, *с каким окружением запущен* `symphony`, а не конфигурацией задачи.

### 1.6. Можно ли задать способ авторизации для отдельной задачи

**Нет, штатно — нет.** Но есть два способа без правки ядра (для `claude`):

1. **Обёртка из варианта A.** Скрипт перед `exec claude` либо делает `unset ANTHROPIC_API_KEY` (работаем по подписке), либо экспортирует ключ из нашего хранилища (работаем по кредиту), в зависимости от `tier` или другого ключа во frontmatter. Это самый простой путь для правила из `DECISIONS.md` («кредит — днём, подписка — ночью до порога»): решение принимает скрипт по внешним данным (время, счётчик расхода).
2. Флаг `--bare` у `claude` (есть в 2.1.309) принудительно использует только `ANTHROPIC_API_KEY`/`apiKeyHelper` и не читает OAuth. Но он ещё и отключает хуки, `CLAUDE.md` и часть возможностей (см. `claude --help`), поэтому **как способ выбора авторизации не рекомендую**.

Для `codex` способ входа определяется содержимым его каталога настроек (`CODEX_HOME`/`~/.codex`) и окружением; на задачу не настраивается. Для разных способов входа пришлось бы запускать оркестратор с разным `CODEX_HOME` — это не «на задачу», а «на запуск». Подробно авторизацию Codex **не разбирал**.

### 1.7. Риски

- Вариант A хрупкий: если изменится имя ссылки на доску или правило очистки имени папки, скрипт молча выберет модель по умолчанию. Нужна проверка в `symphony doctor`-стиле: скрипт обязан **падать**, а не выбирать «по умолчанию», если не нашёл задачу или `tier` неизвестен.
- Для `codex` без правки ядра модель на задачу не задать (см. 1.2).
- Через `bash -lc` и полное наследование окружения ключи видны агенту; агент в принципе может прочитать их командой `env`. Это вопрос безопасности, подробнее — в Вопросе 7.
- Совместимость с автором: вариант B трогает разбор frontmatter — самое «горячее» место проекта; правки надо делать маленькими, чтобы переносились при обновлении.

## Вопрос 3. Хуки

### 3.1. Какие хуки есть и когда они срабатывают

Хуки — это строки bash в блоке `hooks:` файла `WORKFLOW.md` (`src/symphony/workflow/config.py:88-103`, разбор — `src/symphony/workflow/builder.py:296-310`): `after_create`, `before_run`, `after_run`, `before_remove`, `after_done`. Каждый запускается как `bash -lc "<скрипт>"` в рабочей папке задачи, с `stdin=/dev/null`, с общим таймаутом `hooks.timeout_ms` — **по умолчанию 60 секунд** (`src/symphony/workflow/constants.py:36`, запуск — `src/symphony/workspace.py:854-921`). Для хука с полным прогоном тестов 60 секунд почти наверняка мало — таймаут нужно поднять в `WORKFLOW.md`.

Порядок на одном ходу агента (`src/symphony/orchestrator/attempt.py:788-899`, `:605-678`):

1. `before_run` (на первом ходу — при подготовке, `attempt.py:377`; на следующих — `:848`);
2. ход агента;
3. **`after_run`** (`attempt.py:898`);
4. сбор артефактов, фиксация коммита в журнале;
5. оркестратор **перечитывает файл задачи** и решает, что дальше (`_evaluate_turn_result`, `attempt.py:961-1162`), в том числе применяет контракт этапа при переходе в Done.

То есть `after_run` выполняется **раньше**, чем оркестратор смотрит на новый статус задачи — это ключевое для Вопроса 3.3.

### 3.2. Переменные окружения в `after_run`

Окружение хука = окружение оркестратора + (`src/symphony/workspace.py:876-892`):

| Переменная | Значение | Источник |
|---|---|---|
| `SYMPHONY_WORKFLOW_DIR` | папка с `WORKFLOW.md` | `workspace.py:877-880` |
| `SYMPHONY_FEATURE_BASE_BRANCH` | базовая ветка для новых веток задач (может быть пустой) | `src/symphony/orchestrator/helpers.py:63-72` |
| `SYMPHONY_MERGE_TARGET_BRANCH` | целевая ветка автослияния (может быть пустой) | там же |
| `SYMPHONY_BOARD_ROOT` | абсолютный путь к доске | там же |
| `SYMPHONY_BOARD_ROOT_NAME` | имя ссылки на доску внутри рабочей папки (обычно `kanban`) | там же |
| `SYMPHONY_PYTHON` | интерпретатор оркестратора | `workspace.py:891` |
| `SYMPHONY_WORKSPACE_ROOT` | корневая папка всех рабочих папок | `workspace.py:892` |

**Чего в `after_run` нет:**

- **идентификатора задачи** (`SYMPHONY_ISSUE_ID`) — он передаётся *только* в `after_done` (вместе с `SYMPHONY_ISSUE_TITLE`, `workspace.py:670-699`);
- пути к рабочей папке — но она и есть текущая папка хука (`cwd`);
- названия ветки.

**Как получить недостающее без правки ядра:**

- *идентификатор задачи* — `basename "$PWD"` (имя рабочей папки — очищенный идентификатор, `src/symphony/issue.py:93-95`, `workspace.py:511-513`); файл задачи — `$PWD/$SYMPHONY_BOARD_ROOT_NAME/<ID>.md` (имя файла = идентификатор, `src/symphony/trackers/file.py:882`);
- *ветка* — `git branch --show-current`; по соглашению это `symphony/<ID>` (`src/symphony/workflow/constants.py:144`);
- *базовый коммит для сравнения* — `SYMPHONY_FEATURE_BASE_BRANCH`, а если он пуст — `git merge-base HEAD <ветка хоста>` (какую ветку считать базой при пустом значении, **не выяснено**; нужна проба на демо-доске).

**Минимальная правка ядра (по желанию, не обязательна):** передать в `extra_env` хука `after_run` (и `before_run`) `SYMPHONY_ISSUE_ID`, `SYMPHONY_ISSUE_STATE`, `SYMPHONY_BRANCH`, `SYMPHONY_WORKSPACE`. Это ~10 строк в `workspace.py` (`before_run`, `after_run_best_effort`) + вызовов в `attempt.py` (передать идентификатор) + 1–2 теста. Делать её стоит, только если соглашение об имени папки окажется неудобным.

### 3.3. Что происходит, если хук завершился с ошибкой

| Хук | При ненулевом коде или таймауте | Ссылка |
|---|---|---|
| `after_run` | **Ошибка проглатывается**: пишется предупреждение `hook_after_run_failed`, работа идёт дальше как будто всё хорошо | `workspace.py:655-668` |
| `before_run` | Попытка прерывается с ошибкой `before_run_error`; дальше работают общие правила повторов | `attempt.py:377-379`, `:845-850` |
| `after_done` | Предупреждение; при `agent.after_done_failure_policy: block` рабочая папка сохраняется и в отладочную запись пишется `last_error`, **но статус задачи остаётся Done** | `workspace.py:670-699`, `src/symphony/orchestrator/blocked_recovery.py:306-341` |
| `before_remove` | Предупреждение, удаление продолжается | `workspace.py:702-714` |
| `after_create` | Ошибка подготовки рабочей папки (задача не стартует) | `workspace.py:588-590` |

То есть **код возврата `after_run` ничего не решает** — именно поэтому «упал, значит не пускать» тут не работает.

### 3.4. Можно ли хуком запретить переход в Done

**Прямого запрета нет, но есть рабочий обходной путь без правки ядра — «откат статуса из `after_run`».**

Как это устроено: агент сам пишет `state: Done` в файл задачи (README: «When the agent finishes, it sets `state: Done` in `kanban/TASK-1.md`»). `after_run` срабатывает *до* того, как оркестратор перечитает файл (3.1, шаг 3 → 5). Значит, хук может:

1. прогнать наши проверки (тесты, запрещённые пути, неизменённые тесты);
2. если проверка не пройдена и в файле стоит `Done` — вернуть статус обратно командой `symphony board mv <ID> "In Progress"` (команда есть в README, раздел Commands; путь к CLI — переменная `SYMPHONY_CLI`, оркестратор кладёт её в своё окружение при старте, `src/symphony/orchestrator/core.py:603-604`, поэтому её видят и хуки, и агент) и дописать в задачу раздел с логом ошибок;
3. оркестратор увидит `In Progress`, не увидит Done и продолжит цикл ходов: агент получит новый ход, где в задаче уже лежит лог (`attempt.py:1131-1162`).

Свойства этого способа:

- **Плюсы:** ядро не меняется; проверка работает на каждый ход, а не только при Done; хук запускается уже после завершения процесса агента, поэтому состязания с записью агента нет.
- **Ограничения и риски:**
  - Откат хуком **не считается «откатом» в бюджете** `agent.max_attempts` (он увеличивается только при откате по контракту этапа или релизному гейту, `attempt.py:1098-1130`). Защита от бесконечного цикла остаётся только общая: `agent.max_state_turns` (30), `max_turns` (100), `max_total_turns` (200) (`src/symphony/workflow/constants.py:38-41`, проверки — `attempt.py:1133-1161`, `:611-624`). Лестницу «N попыток → тренер → другая модель → needs_human» надо считать самим хуком (счётчик в файле задачи или рядом) — см. Вопрос 2.
  - Если хук упадёт или не успеет за таймаут, откат не произойдёт и **задача пройдёт в Done**: «закрытый по умолчанию» режим этим способом не получить. Поэтому дополнительно нужна защита второго рубежа (см. 4.4).
  - Хук видит только состояние файла на момент своего запуска. Если агент поставил `Done` позже (в следующем ходу), хук сработает снова — после каждого хода.
  - Не пробовал на живой доске (нет учётных данных для агентов в облачном окружении) — **механизм подтверждён чтением кода, не запуском**. Нужна проба на встроенном тестовом бэкенде (этап 2 дорожной карты).

**Вариант с минимальной правкой ядра (закрытый по умолчанию):** добавить в `evaluate_contract` вызов внешней команды из `WORKFLOW.md` (см. 4.4).

### 3.5. Риски по хукам

- Бэкенды запускаются и хуки исполняются через login-оболочку (`bash -lc`), поэтому содержимое профиля пользователя влияет на хуки.
- `after_run` выполняется после **каждого** хода, а не раз за задачу; тяжёлые проверки надо ограничивать (например, запускать полные тесты только когда в файле задачи уже стоит `Done`, а на промежуточных ходах — быстрые проверки путей).
- Таймаут 60 секунд общий для всех хуков; без повышения длинные проверки будут тихо обрываться (а ошибка `after_run` проглатывается — см. 3.3).

## Вопрос 4. Кто меняет статус задачи

### 4.1. Как устроено сейчас

- **Статус меняет агент сам.** Задача — Markdown-файл с YAML-шапкой (`state: ...`); агент (или команда `symphony board mv`) записывает туда новый статус. Оркестратор после каждого хода просто перечитывает файл (`src/symphony/orchestrator/attempt.py:966`). Запись статуса через трекер ничего не проверяет: `FileBoardTracker.transition` выставляет `front["state"] = new_state` без проверки допустимости и без проверки «можно ли сюда из текущего» (`src/symphony/trackers/file.py:947-957`). Проверка допустимого имени статуса есть только в командах `symphony board new/update` и в веб-API (`src/symphony/cli/board.py:184-196`, `:260-270`, `src/symphony/webapi/validation.py:285-292`); агент, редактирующий файл руками, её обходит.
- **Это то самое «слабое место», о котором говорит `ARCHITECTURE.md` (15.3):** решает не код, а запись агента.

### 4.2. Что проверяют «контракты этапов»

Контракты — это `src/symphony/orchestrator/contracts.py`; вызываются из `_enforce_stage_contract` (`src/symphony/orchestrator/agent_phase.py:266-423`) в `_evaluate_turn_result` (`attempt.py:1058-1097`) — **только в момент перехода в «успешный терминальный» статус** (`Done`/`Completed`, `helpers.py:271-281`), из активного статуса.

Что именно проверяется на стандартной доске (Todo → In Progress → Verify → Document → Done):

- **наличие разделов** в тексте задачи: для In Progress — `## Plan`, `## Acceptance Tests`, `## Done Signals`, `## Implementation`, `## Self-Critique`; для Verify — `## Security Audit`, `## QA Evidence`, `## AC Scorecard`, `## Merge Status` и один из `## Review`/`## Review Findings`; для Document — `## Wiki Updates` и итоговый отчёт; для Done — `## As-Is -> To-Be Report`, `## Merge Status` (`contracts.py:143-158`, `:360-436`);
- **наличие непустых папок** `docs/<ID>/work` и `docs/<ID>/qa` (`contracts.py:370-372`, `:422-428`);
- **существование файлов, которые агент процитировал** как доказательства (`_cited_path_failures`, `contracts.py:712-780`);
- согласованность записей (например, «fail» в аудите безопасности при «чистом» ревью).

Что происходит при провале: оркестратор дописывает в задачу раздел `## Contract Failure`, **возвращает статус** в этап-производитель и ведёт новый ход (`agent_phase.py:388-420`); число таких откатов ограничено `agent.max_attempts` (по умолчанию 3), после чего задача уходит в `Blocked`/`Human Review` (`attempt.py:1098-1130`, `helpers.py:284-290`).

**Вывод: контракты проверяют, что агент *написал нужные разделы*, но не что *код работает*.** Они не запускают тесты, не сравнивают изменённые пути с запрещёнными и не следят за неизменностью существующих тестов; существование цитируемого файла проверяется, его содержимое — нет. Это самопроверка агента с механической проверкой формы. Для наших требований (раздел 4.3 спецификации: «основную проверку делает код») этого недостаточно.

Дополнительно:
- Режим включается настройкой `agent.stage_contracts`: `auto` (по умолчанию) — только если все активные колонки стандартные (`Todo/In Progress/Verify/Document`) или это в точности «глубокий» набор; `on` — всегда; `off` — никогда (`src/symphony/workflow/config.py:290-300`, `src/symphony/workflow/presets.py:204-215`). Переименовав активную колонку, контракты в режиме `auto` молча отключаются.
- В профиле `factory` есть таблица «Verification» с командами-доказательствами и требование `result = pass` (`src/symphony/orchestrator/factory_contracts.py:70-140`), но в прочитанном коде эти команды **хост сам не запускает**: проверяется, что агент вписал в таблицу заявленные команды и слово `pass`. Полностью весь `factory/` на предмет запуска команд не просматривал.

### 4.3. Как гарантировать «в Done только после успешной внешней проверки»

Нужна проверка, которую запускает **не агент**. Варианты по возрастанию вмешательства в ядро:

**Вариант 1 — хук `after_run` с откатом статуса (без правки ядра).** Подробно — в Вопросе 3.4. Хук после каждого хода запускает `ours/hooks/check.sh` (тесты, запрещённые пути, неизменённые существующие тесты); если агент поставил `Done`, а проверка не прошла, — возвращает статус и пишет лог ошибок в задачу. Достаточно для первой версии конвейера и этапа 3 дорожной карты.

Слабые места варианта 1:
1. Ошибка самого хука (падение скрипта, таймаут 60 с) проглатывается, и задача пройдёт в Done (`workspace.py:655-668`). Смягчение: скрипт сам перехватывает все ошибки и в любом сомнении откатывает статус; таймаут `hooks.timeout_ms` поднят.
2. Запрета нет «по конструкции»: если хук не настроен или отключён в `WORKFLOW.md`, ничего не мешает Done.
3. Откат хуком не тратит бюджет `max_attempts` (см. 3.4) — счётчик попыток ведёт хук.

**Вариант 2 — второй рубеж на выходе из Done (без правки ядра).** Автослияние выключено (см. Вопрос 7), а финальная точка — состояние `Human Review` (`DECISIONS.md`). Если агент «дожал» Done без проверки, ничего не вливается в основную ветку; вручную видно по журналу проверки, что задача не прошла. Это не запрет, но делает ложный Done безвредным для основной ветки. Нужно только следить, чтобы `agent.auto_merge_on_done: false` и `agent.auto_merge_push_target: false` стояли в *нашей* конфигурации (по умолчанию в ядре оба `True`, `config.py:218`, `:224`, подробно — Вопрос 7).

**Вариант 3 — небольшая правка ядра: внешний контракт.** Добавить в `WORKFLOW.md` необязательную команду, например `agent.done_gate_command`, и вызывать её в `_enforce_stage_contract` рядом с `evaluate_contract` (`agent_phase.py:321`): код возврата ≠ 0 → стандартный путь отката (`## Contract Failure` + возврат статуса, `agent_phase.py:388-420`) с выводом команды в тексте. Это даёт «закрытый по умолчанию» режим, переиспользует существующий откат и бюджет `max_attempts`. Оценка: ~40–70 строк, 2–3 файла (`workflow/config.py`+`builder.py` для настройки, `agent_phase.py` для вызова; запуск через `asyncio.to_thread(subprocess.run, ...)` с таймаутом), **нужны новые тесты** (успех, провал, таймаут, отсутствие команды). Риск: команда выполняется с правами оркестратора, поэтому её путь должен задаваться только в `WORKFLOW.md`, а не из задачи.

**Рекомендация:** на этапе 3 начать с варианта 1 (скрипт в `ours/hooks/`), параллельно подготовить вариант 3 как единственную правку ядра для этого вопроса; вариант 2 включить сразу как страховку.

### 4.4. Можно ли добавить свой статус или колонку (`needs_human`)

**Да, через конфигурацию, ядро менять не нужно.**

- Списки статусов — это `tracker.active_states` и `tracker.terminal_states` в `WORKFLOW.md` (`src/symphony/workflow/builder.py:247-250`; значения по умолчанию — `src/symphony/workflow/constants.py:23-33`; в терминальных уже есть `Human Review`, `Blocked`, `Done`). Любое имя допустимо; колонки веб-доски строятся из этих списков, а `symphony board new/update` проверяют статус по ним же (`cli/board.py:184-196`).
- Статус `needs_human` логично добавить в **`terminal_states`** (оркестратор перестаёт брать такую задачу в работу). Если добавить в `active_states`, оркестратор будет её дальше диспетчеризовать.
- **Не добавляйте новые колонки в `active_states` и не переименовывайте стандартные**: режим `stage_contracts: auto` включается только при стандартных активных колонках (см. 4.2).
- **Подводный камень — сопоставление по подстроке.** Когда ядру нужно перенести задачу «к человеку» (исчерпан бюджет откатов, провал снимка в git и т. д.), оно выбирает *первый терминальный статус, чьё имя содержит* ключевое слово: `human`, `review`, `block` (`src/symphony/orchestrator/helpers.py:236-268`, использование — `:284-290`, `blocked_recovery.py:358-367`). Статус `needs_human` содержит `human`, поэтому при выборе по ключу `human` ядро может выбрать его вместо `Human Review`, если в списке он стоит раньше. Порядок в `terminal_states` определяет результат. В отчёте по Вопросу 2 это важно для лестницы: нужно явно решить, какой из двух статусов получает автоматический перенос ядра.
- Что происходит с рабочей папкой в таком статусе: для `Done` выполняется автокоммит, автослияние и удаление папки (`src/symphony/orchestrator/worker_exit.py:701-721`); для других терминальных статусов в прочитанных ветках папка **не удаляется**, а работа снимком фиксируется в ветке при `auto_commit_on_done` (`worker_exit.py:745-790`). Как ведёт себя очистка при сверке (reconcile) для терминальных статусов — **не проверял**; перед тем как класть диагностику в рабочую папку проблемной задачи, это надо проверить пробой, либо хранить диагностику вне рабочей папки (в `docs/our/` или в самом файле задачи).
- Предложенный набор для конфигурации B: `terminal_states: [Human Review, needs_human, Done, Blocked, Archive, Cancelled]` (точный состав и порядок — на согласование).

### 4.5. Риски по вопросу

- Самый серьёзный: пока не внедрён вариант 1 или 3, «Done» означает лишь «агент написал нужные разделы». До этого момента Done нельзя считать подтверждённым; проверка человека в `Human Review` обязательна.
- Ошибки в имени статуса при ручной правке файла агентом не ловятся (4.1); неизвестный статус не активный и не терминальный — как ядро с ним обращается на всех путях, **не выяснено**.

## Вопрос 2. Эскалация по провалам

Лестница из спецификации (4.1, `DECISIONS.md`): попытки на стартовой ступени → тренер → более сильная модель с чистой ветки → `needs_human`. Ниже — какие механизмы повторов в ядре уже есть и что из лестницы они покрывают.

### 2.1. Три разных механизма ядра (их легко перепутать)

| Механизм | Что считает | Лимит по умолчанию | Что делает при исчерпании |
|---|---|---|---|
| **Повторы запуска** (`agent.max_retries`) | Аварийные завершения процесса агента: таймаут, падение, временная ошибка бэкенда | 3 (`workflow/constants.py:43`, `config.py:176-183`) | Дописывает `## Escalation`, переводит задачу в терминальный `Blocked` (иначе в статус с «block»/«human» в имени) — `src/symphony/orchestrator/retry_reconcile.py:215-260`, `:310-400` |
| **Откаты** (`agent.max_attempts`) | Возвраты задачи назад по колонкам: провал контракта этапа, находки ревью, провал QA | 3 (`constants.py:41`) | Перенос в терминальный статус `Blocked`/«human» — `src/symphony/orchestrator/agent_phase.py:177-200`, `attempt.py:1098-1130`, `helpers.py:284-290` |
| **Переключение при исчерпании квоты** (`agent.fallback_kinds`) | Ошибка «лимит/квота исчерпаны» у бэкенда | пока есть непробованные виды из списка | Записывает во frontmatter `agent.kind: <следующий>`, дописывает `## Backend Fallback`, ставит повтор — `src/symphony/orchestrator/worker_exit.py:1021-1090`, `tracker_bridge.py:299-308` |

Ключевое наблюдение: **ни один из трёх механизмов не реагирует на «тесты не прошли» как на событие.** Повторы запуска — про аварии процесса; `fallback_kinds` — только про исчерпание квоты (распознаётся по тексту ошибки, `src/symphony/orchestrator/core_support.py:138-147`); откаты возникают только если контракт этапа или ревью-находки вернули задачу назад. Если агент просто закончил ход с плохим кодом, ядро этого не заметит (см. Вопрос 4).

Откат — это возврат статуса назад по порядку колонок (`helpers.py:38-52`); при каждом откате вызывается пересборка бэкенда с переменной `SYMPHONY_REWIND_SCOPE` (находки в JSON, `dispatch.py:1209-1250`), и агент получает новый промпт. Сам откат **не меняет модель**: бэкенд (вид) пересчитывается заново в `_config_for_issue_agent` (`agent_phase.py:217`), но модель внутри вида берётся из общей конфигурации (см. Вопрос 1).

### 2.2. Можно ли получить «после N неудач — другой агент или модель»

**Да, без правки ядра, но счётчик и решение придётся вести снаружи; и есть одно ограничение (см. 2.4).**

Схема на хуке `after_run` (расширение механизма из 3.4):

1. Хук после каждого хода запускает механическую проверку (Вопрос 4, вариант 1).
2. Провал → хук увеличивает счётчик неудач для этой задачи. **Хранить счётчик** надо вне рабочей папки или в самом файле задачи (рабочая папка может быть пересоздана): например в `docs/our/state/<ID>.json` или в своём ключе frontmatter (`fails: 2`, `tier: L1`). Идентификатор — из имени папки (3.2).
3. Хук по счётчику решает: ещё попытка (откат статуса + лог ошибок в задачу), «тренер» (см. 2.3), «более сильная модель» (перезаписать `tier: S1` в frontmatter; для `claude` с обёрткой из Вопроса 1 новый уровень подхватится уже на следующем ходу, потому что процесс `claude` запускается заново каждый ход — `claude_code.py:122-128`; для `codex` модель фиксируется при создании бэкенда, то есть со следующей попытки или смены колонки), «человеку» (перевод в `needs_human`/`Human Review`).
4. Бюджет `max_attempts` откат хука **не расходует** (3.4), поэтому дополнительные ограничители остаются общие: `max_state_turns`, `max_turns`, `max_total_turns`.

Что нужно ядру, чтобы это стало «конфигурацией»: поддержка `tier` (Вопрос 1, вариант B) и, желательно, переменные `SYMPHONY_ISSUE_ID` и т. п. в `after_run` (3.2). Правка самой логики эскалации в ядре **не требуется**, пока она живёт в хуке и в обёртке.

**Что нужно в ядре, если хочется встроенного решения:** новое событие «внешняя проверка не прошла N раз» → смена `tier`/`agent_kind` на задаче. Оценка: 80–150 строк в `orchestrator/` (счётчик в `_IssueDebug`, запись ключа через `FileBoardTracker.record_agent_kind`-подобный метод, `file.py:1069-1100`), 3+ файла, много тестов. Для первой версии не рекомендуется (ядро сильно отдаляется от исходного проекта — правило 7 из `CLAUDE.md`).

### 2.3. «Тренер» (уточнение задания более сильной моделью)

В ядре такого шага нет. Он реализуется снаружи, тем же хуком: при втором провале хук отдельным вызовом `claude -p --model sonnet --effort high` (по подписке/кредиту — решает обёртка) читает задание и лог ошибок и дописывает в задачу раздел `## Clarified Request` (этот заголовок ядро уже использует в схожей роли в авто-восстановлении, `src/symphony/orchestrator/blocked_recovery.py:256-300`), после чего задача возвращается исполнителю. Один короткий вызов вне основного цикла ядра; это не расходует ходы задачи. Ограничение: хук выполняется под таймаутом (по умолчанию 60 с, 3.1), поэтому `hooks.timeout_ms` надо поднять либо запускать тренера отдельным фоновым процессом.

### 2.4. Рабочая папка (git worktree): как создаётся и можно ли начать с чистой ветки

**Как создаётся.** Хук `after_create` (в нашем форке — стандартный `scripts/symphony-setup-worktree.sh`, он же в README) выполняется при первом создании рабочей папки задачи:

- имя ветки: `symphony/<ID>` (`scripts/symphony-setup-worktree.sh`, строка с `BRANCH=`; префикс — `src/symphony/workflow/constants.py:144`);
- **если ветка уже существует, она переиспользуется**: `git worktree add "$WORKTREE_PATH" "$BRANCH"`; только если ветки нет — создаётся новая `-b "$BRANCH" "$FEATURE_BASE_BRANCH"` (база — `SYMPHONY_FEATURE_BASE_BRANCH`, а если пусто — текущая ветка хоста, т. е. `HEAD` репозитория, из которого запущен `WORKFLOW.md`);
- единственное исключение — если старая ветка уже целиком влита в целевую, скрипт сдвигает её на новую вершину цели (`_symphony_refresh_merged_branch`);
- точка отсчёта фиксируется в конфигурации worktree: `symphony.basesha`, `symphony.basebranch`, `symphony.mergetargetbranch` (`git config --worktree`) — от неё потом делается сжатие в один коммит при Done;
- доска подключается ссылкой, виртуальное окружение ставится заново.

При повторном запуске той же задачи рабочая папка **сохраняется** (`workspace.reuse_policy: preserve` по умолчанию) и `after_create` не выполняется заново (`src/symphony/workspace.py:515-590`; режим `refresh` перезапускает хук при каждом запуске, но он снова переиспользует существующую ветку).

**Можно ли начать с чистой ветки от той же базы — штатно нет.** Переиспользование ветки и папки — намеренное поведение (чтобы работа не терялась между попытками). Значит, «решение сильной моделью с чистой ветки» нужно сделать внешним скриптом `ours/` между попытками:

1. Остановить задачу (перевести в терминальный/неактивный статус, чтобы ядро её не брало).
2. Сохранить ветку неудачной попытки под другим именем: `git branch -m symphony/<ID> attempts/<ID>-a<N>` (история и диагностика не теряются).
3. Удалить рабочую папку и её регистрацию worktree. Для этого в проекте есть приватный модуль `python -m symphony._worktree_cleanup <папка>` (нужны переменные `SYMPHONY_WORKFLOW_DIR` и `SYMPHONY_WORKSPACE_ROOT`; удаляет worktree и восстанавливает отслеживание доски — `src/symphony/_worktree_cleanup.py`). Модуль приватный (подчёркивание в имени) — его интерфейс может измениться при обновлении исходного проекта; альтернатива — `git worktree remove --force` + удаление папки вручную.
4. Вернуть задачу в активный статус. При новом запуске ядро создаст папку заново, `after_create` увидит, что ветки `symphony/<ID>` нет, и создаст новую от `SYMPHONY_FEATURE_BASE_BRANCH` — то есть **от той же базы**, если эта переменная (или текущая ветка хоста) указывает на неё; чтобы база не «уезжала», надо **явно задать** `agent.feature_base_branch` в `WORKFLOW.md` (`config.py:228-230`, `helpers.py:63-72`).
5. В промпт новой попытки добавить сводку предыдущих попыток (ключ `## Attempt Summary` в файле задачи — наше соглашение).

Что не проверено: как ядро ведёт себя при удалении рабочей папки между попытками (сброс `_IssueDebug`, счётчиков ходов, аренд в SQLite — `run_leases.py`). Эти части **не разбирал**. Нужна проба на тестовом бэкенде.

**Правка ядра, которая упростила бы чистый старт (по желанию):** переменная в `WORKFLOW.md`/frontmatter «`fresh_branch: true`» — тогда `after_create` (скрипт, не ядро!) при её наличии переименовывает старую ветку. Это правка *скрипта* `scripts/symphony-setup-worktree.sh` (≈10 строк bash), а не Python-кода; однако ядро не передаёт скрипту ничего о задаче, кроме имени папки, поэтому признак пришлось бы читать из файла задачи. Рекомендую внешний скрипт (шаги 1–4), а не правку.

### 2.5. Итог по Вопросу 2

| Элемент лестницы | Способ | Правка ядра |
|---|---|---|
| Попытки на стартовой ступени (до N) | хук `after_run` + счётчик | нет |
| Тренер | вызов `claude -p` из хука | нет |
| Сильная модель на задачу | `tier` во frontmatter + подмена в `_config_for_issue_agent` (Вопрос 1) | да (малая, ~50–80 строк) для `codex`; для `claude` — нет (обёртка) |

## Вопрос 5. Лимиты и расход

### 5.1. Сведения о лимитах (rate limit)

**Общая схема.** Каждый бэкенд умеет отдавать «последние известные лимиты» через свойство `latest_rate_limits` (`src/symphony/backends/__init__.py:198-199`). Эти данные кладутся в каждое нормализованное событие (`src/symphony/backends/per_turn.py:106-130`, `:758`), оркестратор перехватывает их и **перезаписывает одно общее поле** `self._latest_rate_limits` (`src/symphony/orchestrator/agent_phase.py:1046-1049`), а `GET /api/v1/state` отдаёт его как `rate_limits` (`src/symphony/orchestrator/api_views.py:223`). Терминальный интерфейс показывает его строкой в подвале (`src/symphony/tui/widgets.py:494-497`).

Два общих недостатка:

1. **Поле одно на всех.** Нет ключа по бэкенду: если параллельно работают `claude` и `codex`, значение — это то, что пришло последним, а не лимиты обоих.
2. **Только в памяти.** Нигде, кроме `self._latest_rate_limits`, оно не хранится (в SQLite — нет; поиск по `src/symphony`). После перезапуска сервиса значение пустое, истории нет. Для «журнала обнулений» и калибровки (спецификация 7.2–7.4) нужен внешний сборщик, периодически читающий `/api/v1/state`.

**`claude`.** `ClaudeCodeBackend._latest_rate_limits` инициализируется `None` и **нигде не заполняется** (`src/symphony/backends/claude_code.py:87`, `:93-95`; присваивания в файле нет). Кадры потока, кроме `system/init`, `assistant`, `user`, `result`, сваливаются в общую ветку «прочее» и целиком уходят в событие как есть (`claude_code.py:153-154`), без разбора. То есть **сейчас `claude` не отдаёт ничего о лимитах**, и в `/api/v1/state` поле `rate_limits` для него `null`.

Что известно про сам Claude Code: в установленной здесь версии 2.1.309 внутри исполняемого файла есть тип кадра `rate_limit_event` с вложенным `rate_limit_info` и поля `rateLimitType` (значения вида `five_hour`, `seven_day`), `resetsAt`, `utilization`, `surpassedThreshold`, `overageStatus`, `isUsingOverage` (найдено поиском строк в бинарнике). Это сильный признак, что режим `--output-format stream-json` выдаёт такие кадры с данными о 5-часовом и недельном окнах. **Не проверено запуском** (в облачном окружении нет учётных данных подписки), точный состав и частота кадров — **не выяснено**; `ARCHITECTURE.md` (7.1) тоже указывает, что точного способа узнать процент лимита не найдено. Это надо проверить на локальном компьютере первым делом (этап 2): запустить `claude -p --output-format stream-json --verbose "ok"` и посмотреть, есть ли кадры `rate_limit_event`.

**Минимальная правка ядра для `claude`** (если кадры есть): в `_handle_stream_event` (`claude_code.py:130-155`) добавить ветку `elif kind == "rate_limit_event"`, которая кладёт `msg.get("rate_limit_info")` в `self._latest_rate_limits` и всё равно эмитит событие. Около 6–8 строк, 1 файл, 1–2 теста (по образцу существующих тестов Claude-бэкенда). Дальше данные сами пойдут в `/api/v1/state`.

**`codex`.** Бэкенд обрабатывает уведомление `account/rateLimits/updated`: сохраняет `params["rateLimits"]` как есть (`src/symphony/backends/codex.py:85`, `:820-826`), отдаёт через `latest_rate_limits` (`:464-465`) и кладёт в события (`:1035`). То есть **для `codex` данные уже доходят до `/api/v1/state`** в том виде, в каком их присылает `codex app-server`. Состав полей определяет Codex (ожидаемо — окна 5 часов и неделя с процентом использования и временем сброса), но **точный формат не проверял**; запроса `account/rateLimits/read` по требованию в коде нет — только пассивное получение уведомлений, то есть значение появляется после активности Codex.

**Общее предложение (небольшое):** хранить по бэкенду — `self._latest_rate_limits[agent_kind] = rl` вместо перезаписи одного поля (`agent_phase.py:1047-1049`, `api_views.py:223`). Это ~10 строк, но меняет форму ответа `/api/v1/state` (из объекта в словарь по видам бэкендов), поэтому это правка с риском для TUI (`tui/helpers.py:153`) и тестов; **делать только если параллельная работа двух бэкендов станет реальной** (в конфигурации B Codex — дополнительный исполнитель, пока не отключён Plus). Без правки сборщик может различать бэкенды по контексту запуска (какой бэкенд сейчас активен — виден в `running[*].agent_kind` того же `/api/v1/state`).

## Вопрос 7. Безопасность

### 7.1. С какими флагами разрешений запускаются бэкенды

**`claude`.**

- Встроенная команда по умолчанию — `claude -p --output-format stream-json --include-partial-messages --verbose` (`src/symphony/workflow/constants.py:106-108`) — **без каких-либо флагов разрешений**. Оркестратор сам их не добавляет (в `claude_code.py` дописываются только `--add-dir` и `--resume`). Как поведёт себя такой запуск, определяют правила самого Claude Code: в режиме `-p` вопросы о разрешении некому задать, поэтому всё, что требует подтверждения, отклоняется (по документации и `claude --help`: `--permission-prompts host|none`; **запуском не проверял**).
- Пример в репозитории (`WORKFLOW.example.md:310-316`, `examples/WORKFLOW.smoke.md:73`, `examples/advanced/WORKFLOW.file.example.md:307`): `claude -p --output-format stream-json --verbose --permission-mode acceptEdits --add-dir "$SYMPHONY_WORKFLOW_DIR"`. Комментарий в примере поясняет: без `acceptEdits` запись файлов ждёт подтверждения, которого не будет. Режим `acceptEdits` разрешает правки файлов в разрешённых папках; **остальные команды оболочки при этом остаются под вопросом и в `-p` отклоняются** (по документации; не проверял).
- Флаги, отключающие проверки (`--dangerously-skip-permissions`, `bypassPermissions`), в **основных путях для `claude` не используются**. Встречаются они в другом: профиль `agy` добавляет `--dangerously-skip-permissions` автоматически (`src/symphony/workflow/config.py:136-142`), `gemini` — `--yolo`. Эти бэкенды в нашей конфигурации не нужны и в `agent.kind`/`fallback_kinds`/`stage_kinds` попадать не должны (правило 8 из `CLAUDE.md`).
- **Вывод для нашей конфигурации:** брать `--permission-mode acceptEdits` и добавлять **точечные разрешения** на нужные команды через `--allowedTools` (например, запуск тестов и `git add/commit` в рабочей папке) — это не отключение проверок, а их настройка. Список команд — отдельное решение по итогам пробы (этап 2); в этом отчёте он не составлялся.
- **Замечание про `--add-dir "$SYMPHONY_WORKFLOW_DIR"` из примера:** это даёт записывать **во всю папку основного репозитория**, а не только в доску. Нам нужен минимум: доска (`kanban/`) и git-папки, которые ядро добавляет само (`claude_code.py:48-64`, `src/symphony/utils/git_sandbox.py`). Не копировать эту строку из примера.

**`codex`.**

- В запросах `thread/start` и `turn/start` передаются `approval_policy`, `thread_sandbox` и `turn_sandbox_policy` из блока `codex:` (`src/symphony/backends/codex.py:485-488`, `:566-573`). Если ключи не заданы — не передаются, действуют умолчания самого Codex.
- Пример в репозитории: `approval_policy: never`, `thread_sandbox: workspace-write`, `turn_sandbox_policy: {type: workspaceWrite, networkAccess: true}` (`WORKFLOW.example.md:288-304`). Это значит: запрос подтверждения не задаётся; запись — только в рабочую папку (плюс папки, которые ядро добавляет по ссылкам и git-путям, `codex.py:149-240`, `:377-425`); сеть разрешена. Режим `danger-full-access` в комментарии примера назван последним средством.
- Если Codex всё же присылает запрос на подтверждение, ядро автоматически одобряет его, **кроме** узкого списка опасных команд (рекурсивное `rm -f`, `sudo`, `mkfs`, `dd` в `/dev`, `shred`, `find -delete`, `git clean -fx`) — `src/symphony/backends/approval_policy.py:10-31`, применение — `codex.py:999-1012`. Это дополнительная сетка, а не граница безопасности (классификатор не учитывает кавычки, разбор текстовый).

### 7.2. Что агент может делать вне своей рабочей папки

Границы такие:

1. **Папка запуска.** Ядро отказывается запускать агента, если рабочая папка не внутри корня рабочих папок (`src/symphony/workspace.py:1557-1570`). Это защита от неверного пути, а не песочница процесса.
2. **Песочница — только у самого CLI.** У Codex это `workspace-write` (настоящая песочница ОС). У Claude Code ядро песочницу не включает; границу задают режим разрешений и список `--add-dir`. Как только команда оболочки разрешена (через `--allowedTools`), она выполняется с правами пользователя, под которым запущен оркестратор, **без ограничения по папкам**. Поэтому список разрешённых команд надо держать узким.
3. **Общий git.** Рабочая папка — это связанный worktree, и ядро намеренно даёт агенту запись в **общую базу объектов и ссылки хоста** (`<host>/.git`) и в служебную папку worktree (`src/symphony/utils/git_sandbox.py:1-24`; `--add-dir` у Claude — `claude_code.py:48-64`, `-c sandbox_workspace_write.writable_roots` у Codex — `codex.py:211-236`). Следствие: агент в одной задаче технически способен менять ссылки других веток, включая основные, и объекты репозитория. Это цена работы с worktree; защита — ревью в `Human Review` и то, что оркестратор не вливает ветку без команды.
4. **Общая доска.** Каталог `kanban/` подключён в рабочую папку ссылкой на доску хоста (`scripts/symphony-setup-worktree.sh`, цикл по `SYMPHONY_BOARD_ROOT_NAME`). Агент по задумке пишет в **свой** файл, но физически может править файлы *всех* задач (и менять им статусы). Это ровно тот риск «статус меняет агент» из Вопроса 4; даёт дополнительное обоснование внешней проверке.
5. **Переменные окружения и секреты.** Агент наследует всё окружение оркестратора (Вопрос 1.5), а запуск через `bash -lc` подмешивает профиль пользователя. Всё, что есть в окружении (ключи API, токены), агент может прочитать командой `env`. Меры: запускать оркестратор с минимальным окружением (без чужих ключей) или через обёртку `ours/bin/claude-tier.sh`, которая явно задаёт только нужные переменные.
6. **Хуки.** Хуки и скрипты `after_create`/`after_run` выполняются с правами оркестратора и ничем не ограничены (`workspace.py:854-921`); их текст задаёт оператор в `WORKFLOW.md`. Агент их менять не может, но если у него есть запись в `WORKFLOW.md` (он лежит в репозитории хоста — см. п. 3 и пример с `--add-dir "$SYMPHONY_WORKFLOW_DIR"`), он может изменить хуки для следующих запусков. Ещё одна причина **не** давать запись во всю папку хоста. В репозитории есть защита: запуск из самого репозитория `oh-my-symphony` с `WORKFLOW.md` отказывает (README, «Do not run tickets inside the checkout»).
7. **Сеть.** У Codex в примере сеть включена; у Claude Code сетевая политика — на стороне CLI. Полностью запретить сеть ядро не умеет; можно сузить на стороне CLI (`turn_sandbox_policy: workspace-write` без сети у Codex).
8. **Веб-интерфейс и API.** Они слушают `127.0.0.1` по умолчанию; для других интерфейсов требуется токен (`src/symphony/server.py:240-250`, `src/symphony/webapi/security.py`). В API есть действия, которые *пушат и вливают*: `POST /api/v1/git/push`, `/git/merge`, `/git/pr`, `/git/branch/delete` (`src/symphony/webapi/git_routes.py:517-526`). Их вызывает человек; при доступе по VPN надо открывать панель только с токеном и не давать эти маршруты боту (Вопрос 6).

### 7.3. Как отключить автослияние и всё, что пушит в удалённый репозиторий

**Умолчания опасны для нашей цели.** В ядре (`src/symphony/workflow/config.py:208-224`, разбор — `src/symphony/workflow/builder.py:400-408`):

| Ключ `agent.*` | По умолчанию | Что делает |
|---|---|---|
| `auto_commit_on_done` | `true` | снимок рабочей папки в один коммит при Done (локально) |
| `auto_merge_on_done` | **`true`** | слияние ветки `symphony/<ID>` в целевую ветку хоста (`git merge --no-ff`) |
| `auto_merge_push_target` | **`true`** | пуш целевой ветки в её upstream и проверка `git ls-remote` — только если у целевой ветки настроен upstream (`src/symphony/utils/auto_merge.py:508-535`) |

**Что поставить в нашем `WORKFLOW.md`:**

```yaml
agent:
  auto_merge_on_done: false
  auto_merge_push_target: false
  # auto_commit_on_done оставить true: это локальный коммит, он нужен для истории
```

- С `auto_merge_on_done: false` слияние не вызывается (`src/symphony/orchestrator/blocked_recovery.py:475-476`, `attempt.py:526`, `agent_phase.py:583`).
- `auto_merge_push_target: false` дополнительно отключает пуш и в других местах, где он передаётся как `push=` (журнал доставки `api_views.py:162`, `worker_exit.py:760-766`).
- **Пуш ветки задачи.** При Done и `Human Review` ядро сверяет «историю доставки» ветки `symphony/<ID>` (`finalize_delivery_history`, `worker_exit.py:756-766`). Скрипт делает `git push` ветки **только если у ветки настроен upstream** (иначе «local only»: скрипты в `src/symphony/workspace.py:1265-1285` и `:1455-1470`, коды 11/12/13). Ветка, созданная скриптом `symphony-setup-worktree.sh` как `-b symphony/<ID> <локальная ветка>`, upstream не получает (по умолчанию в git upstream ставится только для удалённо-отслеживаемой базы) — значит, при локальной базе пуша нет. Но этого нельзя оставлять на «по умолчанию»: при `auto_merge_push_target: false` пуш в этой функции тоже отключается (`push=cfg.agent.auto_merge_push_target`). Итог: **обе настройки `false` + локальная базовая ветка**.
- Способ не имеет проверки «живым прогоном»; перед первым запуском на реальном репозитории — проба на копии без настроенного `origin` (или с `origin`, указывающим на пустой локальный bare-репозиторий).
- **Не включать `deep`-набор колонок:** `symphony doctor` для него *требует* `auto_merge_on_done: true` (`src/symphony/cli/doctor.py:612-645`). Мы остаёмся на стандартных колонках.
- **PM Workspace** (подсистема планирования) отказывается работать при включённой автодоставке (`attempt.py:330-336`) — для нас безразлично, мы её не используем.
- Остаётся путь «человек»: веб-панель умеет по кнопке пушить, вливать и создавать PR (`git_routes.py:517-526`). Это явные действия пользователя; для бота эти маршруты не использовать.
- Дополнительно можно убрать у проекта сам `origin` в клоне, из которого запускается конвейер на ночных проверках (тогда пушить некуда) — инфраструктурная мера вне ядра.
- **Slack-уведомления** (исходящие HTTP-запросы) включаются отдельным блоком `notifications:`; по умолчанию выключены (`orchestrator/helpers.py:300-320`, `src/symphony/notifications/`). В нашей конфигурации не включать без необходимости.

Чтобы эти настройки не «слетали»: добавить проверку в `ours/` (скрипт, читающий `WORKFLOW.md` и падающий, если `auto_merge_on_done` или `auto_merge_push_target` не `false`) и запускать её в начале каждой ночной сессии; в `symphony doctor` отдельной проверки на это **нет** (проверено поиском по `cli/doctor.py`; для стандартных колонок предупреждения нет).

### 7.4. Итог и риски

| Что | Статус |
|---|---|
| Флаги, отключающие проверки разрешений | не используются в `claude`/`codex`; есть в `agy`/`gemini` — их не включать |
| Автослияние | включено по умолчанию → **выключить явно** |
| Пуш | включён по умолчанию → **выключить явно**, плюс локальная база |
| Окружение агента | наследуется целиком → сузить |
| Запись в общий git и в доску | предусмотрена архитектурой → компенсируется ревью и внешней проверкой |
| Права `--allowedTools` | не составлялись — нужны по итогам пробы |

Главный остаточный риск: настройки безопасности держатся на корректной конфигурации, а не на запрете в коде; поэтому нужен автоматический контроль конфигурации (см. выше) и пробный прогон на копии репозитория без доступа к удалённому серверу.

## Вопрос 6. JSON API для внешнего Telegram-бота

Разобрано по коду маршрутов (`src/symphony/server.py:215-228`, `src/symphony/webapi/issue_routes.py:690-727`, `src/symphony/webapi/meta_routes.py:53`); запросы к живому сервису не выполнялись.

### 6.1. Что нужно боту и какие эндпоинты есть

| Нужно боту | Эндпоинт | Что получится |
|---|---|---|
| **Статус** (сводка) | `GET /api/v1/state` | `counts` (running/retrying), `running[]`, `retrying[]`, суммы токенов `codex_totals`, `rate_limits` (см. Вопрос 5), `health` — `src/symphony/orchestrator/api_views.py:200-230` |

| Запуски, токены | `GET /api/v1/runs`, `GET /api/v1/runs/{run_id}` | история запусков (`issue_routes.py:690-691`), диагностика — `.../diagnostic` только с локальной машины (`security.py`, `_request_is_loopback`) |

Тела ответов подробно не просматривались; перед написанием бота надо один раз снять реальные ответы с демо-доски (этап 2).

### 6.2. Чего не хватает

1. **Глобальной паузы/остановки нет.** Все паузы — по одной задаче (`api_views.py:649-720`); поиск по `src/symphony` не нашёл ни глобального флага паузы, ни маршрута для него. Для команды «остановить конвейер на ночь» бот должен либо останавливать сервис через CLI на той же машине (`symphony service stop|restart`, README), либо ставить паузу на каждую работающую задачу по списку из `/api/v1/state`. **Правка ядра:** глобальный флаг в оркестраторе, который проверяется при выборе кандидатов, плюс `POST /api/v1/pause` и `/resume`. Оценка: 30–50 строк, 3 файла (`orchestrator/core.py`/`dispatch.py`, `server.py`, `api_views.py`), нужны тесты. Нужна ли она — решает отчёт об этапе 6: для первой версии хватит CLI и паузы по задаче. (Возможность остановить диспетчеризацию через `agent.max_concurrent_agents: 0` с перечитыванием `WORKFLOW.md` — **не проверял**.)
2. **Нет фильтра задач по статусу на сервере** — для списка в `Human Review` бот получает всю доску. На доске в десятки задач это допустимо; при росте — добавить `?state=` в `handle_board` (≈10 строк). Не обязательно.
3. **Свои поля задачи (`tier` и т. п.) через API не передать.** `POST`/`PATCH /api/v1/issues` собирают фиксированный набор полей (`issue_routes.py:376-387`); если ввести `tier` (Вопрос 1), его нужно добавить и сюда (≈5–10 строк + тест), иначе бот сможет создавать задачи только без уровня или с правкой файла вручную.
4. **Нет потока событий для уведомлений** (подписка/webhook). Встроенные уведомления — Slack-блок `notifications:` (`orchestrator/helpers.py`, `src/symphony/notifications/`); для Telegram бот либо опрашивает `/api/v1/state`/`board` (раз в 30–60 с), либо мы пишем отдельный мост. Чат-интерфейс в панели (`/api/v1/chat/*`, WebSocket) — отдельная функция, для бота не нужна.

### 6.3. Доступ и защита

- По умолчанию сервер слушает `127.0.0.1`; без токена работает «без трения» только на петлевом интерфейсе (`security.py:279-300`). Если привязка к другому интерфейсу без токена — в журнал пишется предупреждение (`server.py:240-246`).
- **Токен:** переменная окружения `SYMPHONY_API_TOKEN` (`security.py:40-60`); заголовок `Authorization: Bearer <токен>`; сравнение за постоянное время; **действует на весь `/api/`**, включая чтение (`security.py:279-300`). Для доступа по VPN токен обязателен. Токен не коммитить и не писать в отчёты (правило 8 из `CLAUDE.md`).
- **Проверка Host.** При привязке к петле допускаются только `localhost`, `127.0.0.1`, `[::1]`; другие имена (например, имя компьютера в VPN) нужно объявить в `SYMPHONY_TRUSTED_ORIGINS` (`security.py:51-58`, `:311-322`), иначе ответ 403 `forbidden_host`. Подробнее — в справочнике: `docs/reference.md`, раздел «Reverse proxy, tunnels, and API token» (в этом отчёте не читал).
- Запросы с изменением (`POST/PUT/PATCH/DELETE`) с телом должны иметь `Content-Type: application/json` (`security.py:335-348`); обычный HTTP-клиент бота без браузерных заголовков проходит.
- Диагностика запусков (`/runs/{id}/diagnostic`) и отладка задач доступны только с локальной машины. Для бота на другом компьютере через VPN они недоступны — достаточно для наших целей.
- В API есть опасные для бота действия: `POST /api/v1/git/push`, `/git/merge`, `/git/pr`, `DELETE /api/v1/issues/{identifier}`, `PUT /api/v1/workflow/...` (редактирование `WORKFLOW.md` и промптов) — `git_routes.py:517-526`, `issue_routes.py:721`, `workflow_routes.py:265-285`. Токен даёт доступ ко **всем** маршрутам; разделения прав «только чтение» / «управление» нет. Поэтому бот должен вызывать только перечисленные в таблице маршруты, а токен хранится как секрет; ограничить маршруты на стороне ядра нельзя без правки `security.py`.

### 6.4. Итог

Для первой версии бота (статус, пауза/возобновление задачи, создание задачи, список Human Review) **правки ядра не нужны**: всё есть, кроме глобальной паузы (обходится CLI) и серверного фильтра (обходится фильтром в боте). Единственное «обязательное» изменение — если вводится `tier`, пропустить его через `POST/PATCH /api/v1/issues`. Риск: единый токен без разделения прав; бот работает с правами оператора.
