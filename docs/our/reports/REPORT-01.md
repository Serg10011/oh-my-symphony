## Вопрос 1. Модель, усилие и авторизация на задачу

### 1.1. Как устроено сейчас: `claude`

- Команда запуска — **одна строка из конфигурации**, общая для всех задач. По умолчанию: `claude -p --output-format stream-json --include-partial-messages --verbose` (`src/symphony/workflow/constants.py:106-108`). Её можно заменить в `WORKFLOW.md` в блоке `claude.command` (`src/symphony/workflow/builder.py:486-487`).
- На каждый ход (turn) запускается новый процесс. Команда собирается так: берётся `claude.command`, сразу после слова `claude` вставляются `--add-dir <путь>` для папок git вне рабочей папки, в конец дописывается `--resume <id сессии>` для продолжения (`src/symphony/backends/claude_code.py:122-128`, вставка — `:48-64`, суффикс — `src/symphony/backends/per_turn.py:586-595`).
- Запуск идёт через `bash -lc "<команда>"` — то есть через *login-оболочку* (`src/symphony/backends/per_turn.py:403-418`). Промпт передаётся через stdin.
- **Поля «модель» и «усилие» для `claude` в конфигурации нет.** Класс `ClaudeConfig` содержит только `command`, три таймаута и `resume_across_turns` (`src/symphony/workflow/config.py:360-372`). Единственный способ выбрать модель — дописать `--model ...` в строку `claude.command`.
- Установленный здесь `claude` (версия 2.1.309) знает флаги `--model <алиас или полное имя>` и `--effort <low|medium|high|xhigh|max>` (проверено по `claude --help`). Значит, с точки зрения самого Claude Code модель и усилие задаются обычными флагами.

### 1.2. Как устроено сейчас: `codex`

- Бэкенд Codex — один долгоживущий процесс `codex app-server`, общение по JSON-RPC (`src/symphony/backends/codex.py:309-325`, команда по умолчанию — `src/symphony/workflow/constants.py:46`).
- Модель и усилие **есть в конфигурации**: `codex.model` и `codex.reasoning_effort` (`src/symphony/workflow/config.py:355-356`, разбор — `src/symphony/workflow/builder.py:477-481`). Значения по умолчанию: `gpt-5.5` и `high` (`src/symphony/workflow/constants.py:53-54`). Имена `gpt-6-luna` и `gpt-6.1-sol` из спецификации — просто значения этого поля; допустимость имён проверяет сам Codex, а не оркестратор.
- Они уходят в запрос `turn/start` на **каждом ходе**: `params["model"]` и `params["effort"]` (`src/symphony/backends/codex.py:574-577`). В запросе `thread/start` модели нет (`:484-489`).
- Важная тонкость: пустое значение `codex.model` **не отключает** передачу — `_as_str(...) or DEFAULT_CODEX_MODEL` подставит `gpt-5.5` (`builder.py:477`). Поэтому обойти параметр запроса флагом `-c model=...` в команде нельзя: параметр `turn/start` всё равно будет передан.

### 1.3. Можно ли задать модель и усилие во frontmatter отдельной задачи

**Нет, ни для `claude`, ни для `codex`.**

- Во frontmatter задачи ядро понимает фиксированный набор ключей (`src/symphony/trackers/file.py:78-95`), модель в нём нет. Разбор задачи в объект `Issue` (`src/symphony/issue.py:28-49`, `src/symphony/trackers/file.py:344-388`) читает из frontmatter, помимо общих полей, только `agent_kind`/`agent.kind`, `last_agent_kind`, `skills`, `request`, `symphony_pm`.
- **Что задаётся на задачу сейчас — только вид бэкенда** (`claude`, `codex`, …): `agent_kind` во frontmatter, затем `agent.stage_kinds` по колонкам доски, затем глобальный `agent.kind` (`src/symphony/workflow/config.py:329-343`, `src/symphony/orchestrator/helpers.py:175-179`, использование — `src/symphony/orchestrator/dispatch.py:1291`). Это даёт «эту задачу на Claude, ту на Codex», но не «эту на Haiku, ту на Sonnet».
- Конфигурация `ServiceConfig` неизменяемая (`frozen`) и общая; в `BackendInit.cfg` попадает она целиком, без учёта задачи (`src/symphony/orchestrator/attempt.py:449-453`, `src/symphony/orchestrator/agent_phase.py:529-533`).

### 1.4. Точка расширения и минимальная правка

**Вариант A — без правки ядра (только для `claude`): обёртка-скрипт.**

1. Задача получает во frontmatter свой ключ, например `tier: L1`. Парсер ядра неизвестные ключи не отбрасывает: при перезаписи задачи ядро работает с полным словарём frontmatter (`src/symphony/trackers/file.py:926-945`, `write_ticket_atomic`) — по коду; отдельным тестом это не проверялось.
2. В `WORKFLOW.md` пишется `claude.command: ours/bin/claude-tier.sh -p --output-format stream-json --include-partial-messages --verbose` (путь к скрипту — наш, в `ours/`).
3. Скрипт определяет задачу и собирает настоящую команду. **Откуда он знает задачу:** рабочая папка агента называется как идентификатор задачи после очистки символов (`src/symphony/issue.py:93-95`, `src/symphony/workspace.py:511-513`), а доска подключена в рабочую папку ссылкой (`src/symphony/orchestrator/helpers.py:63-72`, имя ссылки — `SYMPHONY_BOARD_ROOT_NAME`, по умолчанию `kanban`). Скрипт берёт `basename "$PWD"`, читает `kanban/<ID>.md`, достаёт `tier`, превращает в `--model haiku|sonnet --effort ...` и делает `exec claude "$@" --model ... --effort ...`.
4. **Обязательное условие:** слова `--add-dir` ядро вставляет только если команда начинается с литерального `claude` (`claude_code.py:56-60`). Для обёртки этого не будет, но список папок ядро кладёт в переменную окружения `SYMPHONY_GIT_WRITABLE_ROOTS` (`src/symphony/utils/git_sandbox.py:161`, `claude_code.py:117-120`). Скрипт обязан сам превратить её в `--add-dir` (путь разделён `os.pathsep`), иначе `git add`/`git commit` в рабочей папке упадёт на записи в общую базу объектов (причина описана в `git_sandbox.py:1-24`).
5. Скрипт должен передавать дальше все свои аргументы (`"$@"`), потому что `--resume <id>` ядро дописывает **в конец** строки (`per_turn.py:586-595`).

Плюсы: ядро не меняется. Минусы: связь «задача → модель» держится на соглашении (имя папки и имя ссылки на доску), а не на контракте; только `claude`; ключ `tier` не виден в веб-панели и API как отдельное поле.

**Вариант B — небольшая правка ядра (нужна для `codex`, желательна и для `claude`).**

1. Добавить в `Issue` два необязательных поля `model` и `effort` (`src/symphony/issue.py`), читать их из frontmatter (`src/symphony/trackers/file.py`, функция `issue_from_file` и список ключей `_CANONICAL_FRONT_MATTER_KEYS`). Допустимые значения проверять по белому списку из `WORKFLOW.md` (чтобы опечатка не уходила в CLI).
2. Одна функция `cfg_for_issue(cfg, issue) -> ServiceConfig`, которая через `dataclasses.replace` подменяет:
   - `cfg.codex.model` и `cfg.codex.reasoning_effort` (для `codex` дальше всё работает само — `codex.py:574-577`);
   - `cfg.claude.command`: вставляет `--model X --effort Y` после слова `claude` (по образцу `_inject_add_dirs`, `claude_code.py:48-64`).
3. Вызвать её в двух местах, где собирается `BackendInit`: `src/symphony/orchestrator/attempt.py:449` и `src/symphony/orchestrator/agent_phase.py:529` (смена колонки создаёт новый бэкенд).
4. Заметно проще, если сопоставление уровня и модели хранить в `WORKFLOW.md` (`tiers: {L1: {claude: {model: haiku, effort: medium}, codex: {...}}}`), а в задаче писать только `tier: L1` — тогда уровни из спецификации (раздел 5.1) переносятся в конфигурацию, а не в код.

Оценка объёма: порядка 60–100 строк, 4–5 файлов (`issue.py`, `trackers/file.py`, `workflow/builder.py` + `config.py` для таблицы уровней, `attempt.py`, `agent_phase.py`), **новые тесты нужны** (разбор frontmatter, подмена конфигурации, вставка флагов в команду, неизвестный уровень).

### 1.5. Авторизация: как бэкенд выбирает способ входа

- **Оркестратор способ авторизации не выбирает вообще.** В коде нет ни одного упоминания `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `CODEX_HOME` или очистки ключей (поиск по `src/symphony`: ключи упоминаются у трекеров Linear/Jira, у Gemini в `doctor` и в подсистеме PM Workspace — `src/symphony/pm/codex_compatibility.py:36-37`, где они вычищаются из окружения; к основным бэкендам `claude`/`codex` это не относится). Способ входа выбирает сам CLI по тому, что нашёл в окружении и в своём каталоге настроек.
- **Окружение агента = всё окружение оркестратора + добавки.** Для `claude`: `{**os.environ, **git_roots_env, **init.env}` (`src/symphony/backends/per_turn.py:414`, `:175`); для `codex`: `os.environ.copy()` + то же (`codex.py:392-396`). Фильтрации нет: любая переменная, которая есть у `symphony`, видна агенту, включая ключи.
- **Добавки от оркестратора** (`BackendInit.env`): `SYMPHONY_TOKEN_EMA`, `SYMPHONY_TOKEN_BUDGET` и (при откате) `SYMPHONY_REWIND_SCOPE` (`src/symphony/orchestrator/dispatch.py:1209-1250`), плюс `SYMPHONY_GIT_WRITABLE_ROOTS`; у `codex` ещё `SYMPHONY_CODEX_WRITABLE_ROOTS` (`codex.py:406`). **Идентификатора задачи среди них нет** — поэтому в варианте A задача определяется по имени рабочей папки.
- Поскольку запуск идёт через `bash -lc`, команда подхватывает и переменные из профиля пользователя (`~/.profile` и т. п.) — ещё один источник ключей, о котором легко забыть.

**Следствие для конфигурации B (Claude Max + API-кредит).** Если у процесса `symphony` в окружении есть `ANTHROPIC_API_KEY`, то, по документации Claude Code, `claude` будет работать по ключу (деньги кредита), а не по подписке. В этой песочнице проверить это нельзя (нет учётных данных), поэтому помечаю: **«по документации, не проверено»**. Практический вывод: способ входа определяется тем, *с каким окружением запущен* `symphony`, а не конфигурацией задачи.

### 1.6. Можно ли задать способ авторизации для отдельной задачи

**Нет, штатно — нет.** Но есть два способа без правки ядра (для `claude`):

1. **Обёртка из варианта A.** Скрипт перед `exec claude` либо делает `unset ANTHROPIC_API_KEY` (работаем по подписке), либо экспортирует ключ из нашего хранилища (работаем по кредиту), в зависимости от `tier` или другого ключа во frontmatter. Это самый простой путь для правила из `DECISIONS.md` («кредит — днём, подписка — ночью до порога»): решение принимает скрипт по внешним данным (время, счётчик расхода).
2. Флаг `--bare` у `claude` (есть в 2.1.309) принудительно использует только `ANTHROPIC_API_KEY`/`apiKeyHelper` и не читает OAuth. Но он ещё и отключает хуки, `CLAUDE.md` и часть возможностей (см. `claude --help`), поэтому **как способ выбора авторизации не рекомендую**.

Для `codex` способ входа определяется содержимым его каталога настроек (`CODEX_HOME`/`~/.codex`) и окружением; на задачу не настраивается. Для разных способов входа пришлось бы запускать оркестратор с разным `CODEX_HOME` — это не «на задачу», а «на запуск». Подробно авторизацию Codex **не разбирал**.

### 1.7. Риски

- Вариант A хрупкий: если изменится имя ссылки на доску или правило очистки имени папки, скрипт молча выберет модель по умолчанию. Нужна проверка в `symphony doctor`-стиле: скрипт обязан **падать**, а не выбирать «по умолчанию», если не нашёл задачу или `tier` неизвестен.
- Для `codex` без правки ядра модель на задачу не задать (см. 1.2).
- Через `bash -lc` и полное наследование окружения ключи видны агенту; агент в принципе может прочитать их командой `env`. Это вопрос безопасности, подробнее — в Вопросе 7.
- Совместимость с автором: вариант B трогает разбор frontmatter — самое «горячее» место проекта; правки надо делать маленькими, чтобы переносились при обновлении.

## Вопрос 3. Хуки

### 3.1. Какие хуки есть и когда они срабатывают

Хуки — это строки bash в блоке `hooks:` файла `WORKFLOW.md` (`src/symphony/workflow/config.py:88-103`, разбор — `src/symphony/workflow/builder.py:296-310`): `after_create`, `before_run`, `after_run`, `before_remove`, `after_done`. Каждый запускается как `bash -lc "<скрипт>"` в рабочей папке задачи, с `stdin=/dev/null`, с общим таймаутом `hooks.timeout_ms` — **по умолчанию 60 секунд** (`src/symphony/workflow/constants.py:36`, запуск — `src/symphony/workspace.py:854-921`). Для хука с полным прогоном тестов 60 секунд почти наверняка мало — таймаут нужно поднять в `WORKFLOW.md`.

Порядок на одном ходу агента (`src/symphony/orchestrator/attempt.py:788-899`, `:605-678`):

1. `before_run` (на первом ходу — при подготовке, `attempt.py:377`; на следующих — `:848`);
2. ход агента;
3. **`after_run`** (`attempt.py:898`);
4. сбор артефактов, фиксация коммита в журнале;
5. оркестратор **перечитывает файл задачи** и решает, что дальше (`_evaluate_turn_result`, `attempt.py:961-1162`), в том числе применяет контракт этапа при переходе в Done.

То есть `after_run` выполняется **раньше**, чем оркестратор смотрит на новый статус задачи — это ключевое для Вопроса 3.3.

### 3.2. Переменные окружения в `after_run`

Окружение хука = окружение оркестратора + (`src/symphony/workspace.py:876-892`):

| Переменная | Значение | Источник |
|---|---|---|
| `SYMPHONY_WORKFLOW_DIR` | папка с `WORKFLOW.md` | `workspace.py:877-880` |
| `SYMPHONY_FEATURE_BASE_BRANCH` | базовая ветка для новых веток задач (может быть пустой) | `src/symphony/orchestrator/helpers.py:63-72` |
| `SYMPHONY_MERGE_TARGET_BRANCH` | целевая ветка автослияния (может быть пустой) | там же |
| `SYMPHONY_BOARD_ROOT` | абсолютный путь к доске | там же |
| `SYMPHONY_BOARD_ROOT_NAME` | имя ссылки на доску внутри рабочей папки (обычно `kanban`) | там же |
| `SYMPHONY_PYTHON` | интерпретатор оркестратора | `workspace.py:891` |
| `SYMPHONY_WORKSPACE_ROOT` | корневая папка всех рабочих папок | `workspace.py:892` |

**Чего в `after_run` нет:**

- **идентификатора задачи** (`SYMPHONY_ISSUE_ID`) — он передаётся *только* в `after_done` (вместе с `SYMPHONY_ISSUE_TITLE`, `workspace.py:670-699`);
- пути к рабочей папке — но она и есть текущая папка хука (`cwd`);
- названия ветки.

**Как получить недостающее без правки ядра:**

- *идентификатор задачи* — `basename "$PWD"` (имя рабочей папки — очищенный идентификатор, `src/symphony/issue.py:93-95`, `workspace.py:511-513`); файл задачи — `$PWD/$SYMPHONY_BOARD_ROOT_NAME/<ID>.md` (имя файла = идентификатор, `src/symphony/trackers/file.py:882`);
- *ветка* — `git branch --show-current`; по соглашению это `symphony/<ID>` (`src/symphony/workflow/constants.py:144`);
- *базовый коммит для сравнения* — `SYMPHONY_FEATURE_BASE_BRANCH`, а если он пуст — `git merge-base HEAD <ветка хоста>` (какую ветку считать базой при пустом значении, **не выяснено**; нужна проба на демо-доске).

**Минимальная правка ядра (по желанию, не обязательна):** передать в `extra_env` хука `after_run` (и `before_run`) `SYMPHONY_ISSUE_ID`, `SYMPHONY_ISSUE_STATE`, `SYMPHONY_BRANCH`, `SYMPHONY_WORKSPACE`. Это ~10 строк в `workspace.py` (`before_run`, `after_run_best_effort`) + вызовов в `attempt.py` (передать идентификатор) + 1–2 теста. Делать её стоит, только если соглашение об имени папки окажется неудобным.

### 3.3. Что происходит, если хук завершился с ошибкой

| Хук | При ненулевом коде или таймауте | Ссылка |
|---|---|---|
| `after_run` | **Ошибка проглатывается**: пишется предупреждение `hook_after_run_failed`, работа идёт дальше как будто всё хорошо | `workspace.py:655-668` |
| `before_run` | Попытка прерывается с ошибкой `before_run_error`; дальше работают общие правила повторов | `attempt.py:377-379`, `:845-850` |
| `after_done` | Предупреждение; при `agent.after_done_failure_policy: block` рабочая папка сохраняется и в отладочную запись пишется `last_error`, **но статус задачи остаётся Done** | `workspace.py:670-699`, `src/symphony/orchestrator/blocked_recovery.py:306-341` |
| `before_remove` | Предупреждение, удаление продолжается | `workspace.py:702-714` |
| `after_create` | Ошибка подготовки рабочей папки (задача не стартует) | `workspace.py:588-590` |

То есть **код возврата `after_run` ничего не решает** — именно поэтому «упал, значит не пускать» тут не работает.

### 3.4. Можно ли хуком запретить переход в Done

**Прямого запрета нет, но есть рабочий обходной путь без правки ядра — «откат статуса из `after_run`».**

Как это устроено: агент сам пишет `state: Done` в файл задачи (README: «When the agent finishes, it sets `state: Done` in `kanban/TASK-1.md`»). `after_run` срабатывает *до* того, как оркестратор перечитает файл (3.1, шаг 3 → 5). Значит, хук может:

1. прогнать наши проверки (тесты, запрещённые пути, неизменённые тесты);
2. если проверка не пройдена и в файле стоит `Done` — вернуть статус обратно командой `symphony board mv <ID> "In Progress"` (команда есть в README, раздел Commands; путь к CLI — переменная `SYMPHONY_CLI`, оркестратор кладёт её в своё окружение при старте, `src/symphony/orchestrator/core.py:603-604`, поэтому её видят и хуки, и агент) и дописать в задачу раздел с логом ошибок;
3. оркестратор увидит `In Progress`, не увидит Done и продолжит цикл ходов: агент получит новый ход, где в задаче уже лежит лог (`attempt.py:1131-1162`).

Свойства этого способа:

- **Плюсы:** ядро не меняется; проверка работает на каждый ход, а не только при Done; хук запускается уже после завершения процесса агента, поэтому состязания с записью агента нет.
- **Ограничения и риски:**
  - Откат хуком **не считается «откатом» в бюджете** `agent.max_attempts` (он увеличивается только при откате по контракту этапа или релизному гейту, `attempt.py:1098-1130`). Защита от бесконечного цикла остаётся только общая: `agent.max_state_turns` (30), `max_turns` (100), `max_total_turns` (200) (`src/symphony/workflow/constants.py:38-41`, проверки — `attempt.py:1133-1161`, `:611-624`). Лестницу «N попыток → тренер → другая модель → needs_human» надо считать самим хуком (счётчик в файле задачи или рядом) — см. Вопрос 2.
  - Если хук упадёт или не успеет за таймаут, откат не произойдёт и **задача пройдёт в Done**: «закрытый по умолчанию» режим этим способом не получить. Поэтому дополнительно нужна защита второго рубежа (см. 4.4).
  - Хук видит только состояние файла на момент своего запуска. Если агент поставил `Done` позже (в следующем ходу), хук сработает снова — после каждого хода.
  - Не пробовал на живой доске (нет учётных данных для агентов в облачном окружении) — **механизм подтверждён чтением кода, не запуском**. Нужна проба на встроенном тестовом бэкенде (этап 2 дорожной карты).

**Вариант с минимальной правкой ядра (закрытый по умолчанию):** добавить в `evaluate_contract` вызов внешней команды из `WORKFLOW.md` (см. 4.4).

### 3.5. Риски по хукам

- Бэкенды запускаются и хуки исполняются через login-оболочку (`bash -lc`), поэтому содержимое профиля пользователя влияет на хуки.
- `after_run` выполняется после **каждого** хода, а не раз за задачу; тяжёлые проверки надо ограничивать (например, запускать полные тесты только когда в файле задачи уже стоит `Done`, а на промежуточных ходах — быстрые проверки путей).
- Таймаут 60 секунд общий для всех хуков; без повышения длинные проверки будут тихо обрываться (а ошибка `after_run` проглатывается — см. 3.3).
