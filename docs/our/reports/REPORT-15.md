## Что сделано

**а) Права агента.** В `project.toml` новая секция `[agent]`, ключ `allowed_bash` — список дополнительных разрешений для Bash. Шаблон добавляет в команду `claude` ключ `--allowedTools` (после `--permission-mode acceptEdits`, до `--add-dir`) со встроенной базой — ровно набор, прошедший пробу: `/bin/bash <папка доски>/test.sh`, `git merge-tree`, `test`, `echo`, `cat`, `wc`, `head`, `tail` — и записями проекта. Запись — начало команды; из неё получается правило `Bash(<запись>:*)`, каждое правило — отдельный аргумент, заключённый в кавычки (путь с пробелами не ломает команду). `project_config.py` отказывает с понятным текстом на: пустую запись, одиночный `*`, `Bash(*)` и любую запись с `Bash(...)`, суффикс `:*`, голые `bash` / `sh` / `zsh` / `env` / `sudo` / `eval` / `exec` (разрешают любую команду), управляющие символы и слова `dangerously`, `bypass`, `skip-permissions`, `permission-mode`, `allowedTools`, `yolo`. В заготовке `project.toml` из `project-new` — закомментированный пример `allowed_bash = [".venv/bin/python -m ruff"]`. **[запуск]** (тесты; WORKFLOW.md с новой командой принимает настоящее ядро).

**б) Сторож зависания.** Что сбрасывает таймер, по коду ядра **[код]**: `entry.last_progress_timestamp` обновляется в `agent_phase.py` на событиях агента, которые считаются прогрессом: любые события жизненного цикла, прирост *выходных* токенов и кадры `assistant` (`ClaudeCodeBackend.is_progress_event`, `claude_code.py`). Эхо результата инструмента (кадр `user` с `tool_result`) прогрессом **не** считается — это сделано намеренно (комментарий в коде: иначе скрывался 18-минутный простой модели). Сверка (`retry_reconcile.py`, `_reconcile_stall_state`) берёт позднейшее из `last_progress_timestamp`, `resumed_at`, `started_at` и отменяет воркера, когда прошло больше `stall_timeout_ms`; пока идёт `after_run` (в пределах `hooks.timeout_ms` плюс запас), проверка пропускается. Значит, один долгий вызов Bash — это тишина на всё его время, и формула «не меньше 300000 и не меньше (`tests_s` + 120) × 1000» для него годится: `tests_s` вдвое больше замеренного времени тестов, запас 120 с покрывает ответ модели вокруг вызова. Шаблон теперь пишет `stall_timeout_ms: {{int:stall_ms}}`; `project-doctor` после пересчёта `[timeouts]` пересобирает `WORKFLOW.md` и печатает строку `PASS  stall_timeout_ms = … (max(300 с, tests_s … + 120 с))`. Примеры: `tests_s` 300 → 420000; 420 → 540000; 900 → 1020000. **[запуск]** (тесты; `project-doctor` в тесте с фиксированным и с замеренным `tests_s`).
Чего формула не покрывает: собственный предел времени одного вызова Bash у `claude` (настройка самого `claude`, на пробе не проверялась) и два долгих вызова подряд без ответа модели между ними — между вызовами модель отвечает, и таймер сбрасывается.

Логики в заготовках нет. **[запуск]** (существующий тест заготовок проходит).

После записи печатает `launchctl bootstrap` / `bootout gui/$(id -u) …`, путь лога, `ps eww -p` и напоминание «одно вместо другого, не обе сразу». ## Расхождения с заданием и допущения

- Запись `allowed_bash` я определил как **начало команды без обёртки** `Bash(...)` (как в примере задания `.venv/bin/python -m ruff`); запись в обёртке отвергается с подсказкой. Совпадение — по началу (`:*`), включая аргументы: так же устроена и встроенная запись `/bin/bash <доска>/test.sh`, поэтому `test.sh` с аргументами разрешён. Точную форму правил из пробы Сергея я не видел; если на Mac требовалась другая (например, без `:*` у `test.sh`), это правится одной строкой в `agent_bash_rules`.
- Помимо перечисленного в задании, ключ `allowed_bash` отвергает голые `bash` / `sh` / `zsh` / `env` / `sudo` / `eval` / `exec` — они равносильны «разрешить всё». Это узко и в духе правила проекта про проверки разрешений.
- Пояснения к «трём ловушкам» проекта-форка в README (зачем отдельный клон, зачем своя venv) написаны мной по логике установки; на пробе проверялись сами меры, а не причины.
- Решение для `ours/**` в `check.py` не менялось и не предлагалось — описано как факт, выбор за Сергеем.
