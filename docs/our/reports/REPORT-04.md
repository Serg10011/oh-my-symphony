**Как работает [код].** Команда берётся только из `cfg.agent` (то есть из `WORKFLOW.md`), запускается через `bash -lc` в рабочей папке карточки, в отдельном потоке (цикл событий не ждёт). Окружение: обычные хуковые переменные + `SYMPHONY_ISSUE_ID`, `SYMPHONY_ISSUE_TITLE`, `SYMPHONY_ISSUE_STATE`, `SYMPHONY_WORKSPACE`, `SYMPHONY_BRANCH`. Исходы: код 0 → `passed`; 127 → `not_found`; другой код → `exit_code`; таймаут → `timeout` (группе процессов отправляется SIGKILL); любое исключение → `exception`. Отказ: `Blocked` (тем же вызовом `_tracker_call_update_state`, что у ворот слияния), затем заметка `## Done Gate Failure` (причина, код, папка, путь к полному выводу и последние 4000 символов вывода); `debug.last_error`. В журнал пишутся события `done_gate_passed` / `done_gate_failed`. Полный вывод сохраняется в `.symphony-workspace-hook-output/<ID>/*-done_gate.*`. Если записать `Blocked` не удалось, шлюз всё равно возвращает отказ (`done_gate_block_persist_failed`).

## Расхождения с заданием и REPORT-02

1. **Свой запуск, а не `_run_hook`.** Общий запуск хуков есть, но при таймауте `subprocess.run` убивает только `bash`, а его дети остаются жить (что подтвердил контроль 2). Кроме того, у него один общий `hooks.timeout_ms`. `run_done_gate` использует то же окружение (общий `_hook_process_env`) и ту же запись файлов вывода, но запускает команду в своей группе процессов (`start_new_session`) и при таймауте убивает всю группу. На Windows убивается только сам процесс [код].
2. **Таймаут 600000**, а не 300000: значение взято из REPORT-02, раздел 5.1, как сказано в задании.
3. **Заметка одна, `## Done Gate Failure`**: пункты в стиле `Merge Gate Failed` плюс блок с хвостом вывода. У ворот слияния нет формата для многострочного вывода (`detail[:1000]` в одной строке).
4. Не сделано из предложений 5.3 REPORT-02: `_record_stats_gate` (задание этого не требовало).
5. Если служба останавливается во время работы шлюза, поток не прерывается: команда дорабатывает до своего таймаута [код].

## Ответы на вопросы

**Q1. Окно.**
- *Воркер:* агент сам пишет `state: Done` → конец хода → `after_run` → снимок git (если включён) → шлюз → `Blocked` → заметка. На диске карточка в Done всё это время, вплоть до таймаута шлюза. Зависимые карточки этой службой **не запускаются**: пока идёт обработка выхода, карточка числится в `_running`/`_terminal_persist_pending`, и `_blocker_is_in_flight` держит их в `waiting_dependency` [запуск: 20 замеров во время шлюза — все «Done на диске» и «в работе», итог `Blocked`].
- *Reconcile:* то же, но сначала 60 с «льготы» сверки, затем отмена воркера и шлюз. Защита зависимых та же [запуск]. Побочный эффект: сверка ждёт шлюз внутри такта (`dispatch.py:108`, `retry_reconcile.py:729`), поэтому на время работы шлюза новые карточки не раздаются вообще [код]. Ворота слияния ведут себя так же.
- *`confirm_done`:* шлюз до записи Done; карточка идёт `Human Review` → `Blocked`, Done не пишется ни на миг [запуск: записан только `Blocked`].
- Видят «Done» в окне только внешние читатели: веб-доска, `board ls`, агенты других карточек, вторая служба на той же доске. Самое дешёвое исправление — ничего не менять в коде, а держаться уже принятого правила (агент заканчивает в `Human Review`, Done ставит только `confirm_done`): у этого пути окна нет.

**Q2.** Да: `symphony board new Q-1 … --state Done` (rc=0) и `POST /api/v1/issues` с `"state": "Done"` (201, в файле `state: Done`) [запуск]. Шлюз не запускается: у такой карточки нет воркера и рабочей папки, путь приёмки не проходится [код].

**Q3.** Шесть мест из REPORT-03 [код, оценки]:

Шлюз асинхронный, а `complete_ticket` выполняется в потоке, поэтому вызов пойдёт через `asyncio.run_coroutine_threadsafe(...)`. Ещё нужно получить карточку и `path_for`. При отказе нужно бросить исключение до `update_fields`. ≈15-20 строк + тесты. У PM-карточки может не быть рабочей папки: тогда закрытый шлюз всегда откажет (нужно решение).

## Попутная находка

При нашем `terminal_states: [Human Review, needs_human, Done, Blocked, Archive]` статус `needs_human` считается **успешно закрытой** зависимостью: `_blocker_dependency_is_resolved("needs_human") = True`, а `Blocked` и `Human Review` дают `False` [запуск]. Список «неуспешных» зашит в `core_support.py:30-38`. Значит, карточки с `blocked_by` на задачу в `needs_human` будут запущены. Это нужно решить до ночных прогонов с зависимостями.
