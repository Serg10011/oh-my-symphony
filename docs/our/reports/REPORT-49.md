## Что изменилось

После сохранённой сетевой ошибки теперь можно подготовить локальный план
продолжения и отдельно разрешить исполнение с той же историей. В прежнем
коде run возвращает остановку, поэтому новая попытка через init начинала
исследование заново. Поведение обычного run сохранено; продолжение
добавлено отдельными командами resume-plan и resume.

План показывает активного участника/часть, номер неопределённого запроса,
номер следующей отправки, остаток ресурсов и возможное прежнее списание.
Ключи и API ему не нужны. Платная команда требует точную контрольную сумму
плана и явное подтверждение возможного списания потерянного ответа.
План связан с абсолютным путём, исходными байтами состояния, пятью файлами
API-слоя и телом будущего запроса. Оба действия берут блокировку сессии;
план не меняет её содержимое. Изменившийся план нельзя выполнить по
предыдущему подтверждению.

Перед изменением создаётся точная приватная резервная копия с SHA-256
в имени. Сначала надёжно сохраняются копия и запись о продолжении, затем
идёт обычный цикл запросов с существующими проверками. Старые запросы,
их даты, неизвестный расход и резервы не переписываются. Новая отправка
получает новый номер и resume_of; повторная сетевая ошибка опять
останавливает выполнение и требует нового плана/подтверждения.

## Как восстанавливается точка работы

Безусловно менять stopped на running нельзя: обычный цикл начался бы
с ведущего, хотя мог ждать результат Luna. Поэтому сначала проверяются
последнее тело запроса по сохранённому SHA-256, целостность диалогов,
незаконченная очередь инструментов ведущего и её связь с активной частью.
Для Luna проверяется также последнее назначение и число её попыток.

Продолжается текущая попытка исполнителя; она не получает второй start
и не расходует адресное исправление. После ответа результат возвращается
в тот же вызов ведущего, затем исполняется оставшаяся часть его очереди.
Завершённые части и уже выполненные чтения повторно не запускаются.
Защита от повторных call_id и разделение reasoning сохраняются.
Частичный текст текущей попытки восстанавливается, если после продолжения
потребуется вернуть управление ведущему ради его резерва.

Общая выдача запросов вынесена в чистый сборщик без изменения промптов;
его использует и восстановление, и обычный цикл. Обработка очереди
ведущего общая для обоих путей. Новая логика — в api_resume.py;
ядро src/symphony, зависимости, платные профили и инструменты записи
не менялись. Только list/read фиксированного коммита доступны моделям.

## Деньги и границы

Поддерживается только api_error/network_error без полученного ответа
и HTTP-статуса, с charge_possible=true. Старое тело запроса должно точно
восстанавливаться текущим сборщиком. При изменении промптов, модели,
снимка проекта или несовместимом состоянии продолжение отклоняется.
Проверяется доступность прежнего коммита; текущая ветка проекта не
подставляется вместо него.

Лимиты и budget не повышаются, расход не обнуляется. Неизвестный запрос
остаётся в committed с полным прежним резервом. Новая отправка оплачивается
отдельно и при заданном budget проходит прежнее измерение/резервирование;
статус resume_ready не обещает, что бюджет вместит новый вход.
Истёкший тарифный снимок блокирует продолжение. Подтверждение относится
к продолжению текущей задачи в оставшихся границах, а не к одной генерации:
после ответа цикл работает до результата либо очередной остановки.

Гарантировать отсутствие списания за потерянный ответ нельзя. В нашем
транспорте OpenAI используется store=false, у запроса 47 нет response_id.
По [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/conversation-state)
store=false отключает сохранение ответа для последующего получения;
[получение ответа](https://developers.openai.com/api/reference/resources/responses/methods/retrieve)
требует его ID. Восстановление не включает поиск потерянного ответа,
включение серверного хранения или обещание дедупликации провайдером.

Остались вне первой версии: авария процесса в произвольной точке,
незавершённая запись ответа/локального инструмента, HTTP-ошибка,
неполный ответ, отказ, unknown_usage полученного ответа, ошибки бюджета
и целостности. Такие случаи сохраняют прежнюю остановку. При аварии уже
разрешённого resume обычный run отмечает interrupted_no_automatic_retry;
сам повторного запроса не делает. Это граница реализации, а не утверждение
восстановления после любого возможного сбоя.

Общий контекст между задачами одного проекта и улучшение кеширования
не реализованы в этой задаче. Сохранение диалога позволяет продолжить
его без повторного знакомства с файлами, но само по себе не гарантирует
попаданий в кеш провайдера. Учёт и разрешения по-прежнему относятся
к конкретной задаче.
