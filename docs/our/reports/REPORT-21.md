## Причина и результат

Прежний `_next_identifier_unlocked` считал максимум только по существующим
файлам. После удаления DEMO-2 новая задача могла снова получить DEMO-2;
её запрос истории по ID показывал прежние запуски. Сохранение истории
штатно; ошибка — выдача того же ID другой задаче.

Введён журнал `.symphony-identifiers.json` на самой доске. В нём выданные
ID, максимумы префиксов и идентичность плановых PM-карточек. Создание,
ручная выдача и удаление сериализуются одним постоянным замком. Резервирование
сохраняется атомарно и синхронизируется на диск перед записью/удалением
карточки. Прерывание оставляет безопасный пропуск.

CLI может получать номер сам: `board new --prefix DEMO "Название"`.
Прежний синтаксис с явным свободным ID сохранён. Регистр и ведущие нули
не позволяют обойти резервирование; вручную можно выдать никогда не
использовавшийся номер ниже максимума, автоматическая выдача идёт выше него.

Переход учитывает файлы и front matter, старые замки, run history и PM
handoff. SQLite открывается `mode=ro`, без миграции и изменения запусков;
плановая идентичность берётся из связанных записей задачи, передачи и снимка.
Проверка неизменяемого PM-входа остаётся в PM-модуле. Путь истории берётся от WORKFLOW.md,
в том числе при внешнем board_root. Повреждённые данные останавливают
выдачу/удаление с понятной причиной, без очистки истории или карточки.

## Почему изменено ядро

Выдачей ID владеет FileBoardTracker. Только правка `ours/` или интерфейса
оставила бы обход через CLI, API и служебные создатели. Все три метода
создания теперь сходятся в `create_validated`; `delete` сохраняет ID перед
удалением. Библиотека журнала выделена в `trackers/identifiers.py`.
TrackerConfig получает внутренний путь истории от builder; нового YAML
параметра, зависимости или изменения схемы SQLite нет.

## Находки прежней разработки и ограничения

Решение от 27.10 уже описывало постоянный максимум и отказ от собственного
подсчёта в `create-*.py`. Подтверждены пять локальных создателей прежних проб:
EVE, E4, словарь, S4-20 и S4-22. Их копии и контрольные суммы находятся
в журнале аудита `~/symphony-projects/.backups/s4-28-20261031-194134/`.
Скрипты не запускались и не переписывались. Повтор использованного номера
через них получит отказ; для новой пробы нужен автоматический путь API/CLI.

PM-восстановление по неизменяемому входу — существующий механизм исходного
проекта. Оно сохранено для прежней задачи при полном совпадении PlanningRef.
Обычная новая карточка этой идентичностью не обладает.

Планировщик `ours/hooks/plan.py` создаёт обычные подзадачи с фиксированными
ID и при частичном отказе удаляет уже созданные файлы. Теперь эти ID остаются
занятыми; повтор с теми же ID требует человека. Это проверяется отдельно
на реальном CLI; автоматическое восстановление такого плана не добавляется.

Уже потерянные старые ID без файлов, замков и записей истории восстановить
невозможно. Уже смешанная история не разделяется. Прямая запись новых
Markdown-файлов и старое ядро обходят протокол выдачи. Откат к старому коду
требует приостановить выдачу ID, сохранив журнал и историю.

Зависимость старых E3c-тестов от настоящего TIME_WAIT остаётся отдельной
находкой. Рабочие доски и службы в S4-31 не менялись. Подробная инструкция —
[BOARD-IDS.md](../BOARD-IDS.md), задание — [TASK-S4-31](../tasks/TASK-S4-31.md).

Дополнительно: унаследованный `.github/workflows/tests.yml` запускается
для PR/push в `main` и `dev`, не `our-main`. Автоматический GitHub CI для
этого PR не ожидается; приёмка опирается на локальные полные проверки.
Причина сохранения такого фильтра в прежней работе не подтверждена.
Настройка CI в этой задаче не менялась.
