## Что изменено и зачем

- `ours/hooks/plan.py`: журнал `.ours-state/<ЗАДАЧА>.plan-create.json`
  записывается и синхронизируется с диском до первой карточки. Он связывает
  исходный план, проект/доску, цель/шапку задачи, ветку/исходный коммит и ключ
  операции. Фазы — `creating`, `committed`, `done`; после завершения журнал остаётся.
- Подзадачи создаются в `Subtasks`, затем сохраняются `Plan Accepted` и
  `Subtask Progress`, и только после принятия полного набора происходит выпуск
  в `In Progress`. Сбой сохраняет файлы и сразу требует человека; попытка
  планирующего агента не тратится. Новый `recover TASK --board PATH` продолжает
  журнал под общим замком задачи. Хук умеет продолжить незавершённый журнал
  при возврате исходной карточки в `Subtasks`, даже с уже записанным `Plan Accepted`.
- Необходимое дополнение ядра: квитанции `creations` в журнале ID,
  `create(..., creation_key=...)` / CLI `board new --creation-key ... --json`.
  Только тот же явный ID, ключ и исходные параметры могут вернуть результат
  прежней операции. Существующая карточка не перезаписывается; исходный
  `created_at` сохраняется. Обычное повторное использование ID запрещено,
  прежний PM-путь с `PlanningRef` сохранён.
- `release_created` / `board release` атомарно записывает рабочее состояние
  и `creation_release` в карточку. Повтор не сбрасывает работу, новый статус
  или ручную паузу. Файлы recoverable-операций и каталоги синхронизируются
  с диском; обычный путь записи карточек не перерабатывался.
- CLI `--staged` требует неисполняемое состояние данного WORKFLOW.
  `--root` вместе с явно переданным `--workflow` той же доски сохраняет
  настройки WORKFLOW и путь истории; другой корень или отсутствие явного
  WORKFLOW сохраняют самостоятельный режим. Это нужно для `Subtasks`:
  прежний CLI при любом `--root` забывал состояния доски.

Ключевые документы: [BOARD-IDS.md](../BOARD-IDS.md), `ours/README.md`,
`ours/hooks/README.md`. В заготовках `project-new`/WORKFLOW изменены только
пояснения, новые состояния и параметры оплаты не добавлялись. Новых зависимостей нет.

## Границы и применение

Старые частичные планы без журнала автоматически не принимаются. После
`committed` пропавшая карточка не создаётся заново: в ней могла быть работа.
Изменённые исходные данные, лишние карточки и повреждённые данные требуют
человека. Контрольная сумма журнала обнаруживает повреждение, не заменяет
права доступа. Создание нового Markdown вручную в обход трекера не входит
в гарантию ID; квитанции, журнал и отметки выпуска нужно сохранять.

Выпуск набора по карточкам: при сбое уже выпущенные подзадачи могут работать,
остальные ждут. Полный набор и приёмка к этому моменту уже сохранены;
повтор не перезаписывает выпущенные карточки. Операционная команда `recover`
разрешает их выполнение и применяется только в рамках согласованной задачи.
Автоматического фонового повтора и запуска новой платной нарезки нет.

Применение — только после отдельной приёмки PR и через `post-merge`.
Возврат к прежнему коду требует сохранить журналы, квитанции и работу;
незавершённые журналы нельзя отдавать старому планировщику. Архив проверки
разработки не заменяет снимок живой среды перед будущим обновлением.
