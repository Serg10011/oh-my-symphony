## Подтверждённые возможности

- src/symphony/backends/__init__.py: build_backend поддерживает не только
  встроенные виды агентов, но и agent.profiles. Для профиля выбирается
  PlainCliBackend; новый вид агента не обязательно требует отдельного
  драйвера ядра.
- src/symphony/backends/plain_cli.py и workflow/config.py: профиль получает
  промпт через stdin, stdout считается ответом. Текущий format — text;
  потоковый протокол требует отдельного драйвера. В финальном событии
  stats пуст, поэтому один профиль сам по себе не решает показ API-расходов.
- backends/per_turn.py: общий драйвер уже управляет дочерним процессом,
  отменой и завершением. У обычного текстового профиля нет промежуточных
  событий прогресса; нужно учитывать тайм-аут ожидания.
- webapi/payloads.py передаёт agent_kinds из selectable_agent_kinds,
  web/static/app.js строит выбор агента для карточки из этого набора.
  Интерфейс уже имеет точку подключения профиля исполнителя.
- ours/hooks/worktree.py и текущий WORKFLOW.md OMS уже обеспечивают
  рабочие копии, хуки check.py, проверки и путь к человеческой приёмке.
  Следует переиспользовать готовый цикл, а не дублировать доску и учёт задач.

## Что требует проектирования

Нельзя считать добавление имени в список исполнителей готовым конвейером.
Нужно определить совместное поведение API-сессии и этапов карточки,
доступ к актуальным изменениям обоих участников, применение и проверку
кода, прекращение платного выполнения после остановки, восстановление
и показ фактических расходов. Выбор реализации ещё не принят.

Нынешний api_session работает отдельно от досок и предоставляет только
list_project_files, read_project_file, search_project_files фиксированного
Git-коммита. Записи и команд нет. Добавление таких возможностей требует
реальной изоляции исполняемого кода: одного исключения ключей из окружения
недостаточно для защиты файлов Mac и вывода проверки, который получит модель.
Ключи должны оставаться у доверенного процесса, обслуживающего API.

Текущий веб-контур — src/symphony/webapi/security.py: есть проверки
loopback, Host/Origin, необязательный SYMPHONY_API_TOKEN и отдельные
возможности подтверждения. При добавлении запуска с оплатой нужно проверить
защиту именно новых изменяющих маршрутов, а не предполагать, что локальный
адрес сам подтверждает действие пользователя.

Обзор ours/hooks/project_overview.py объявлен read_only и показывает
две доски. Превращать его в управляющий интерфейс без отдельного решения
не следует. Обычная доска OMS обслуживается на localhost:9972.
Её работающий профиль пока Claude, EVE выключена.

## Проверка доступных средств изоляции

На этом Mac найдены встроенный в приложение codex и /usr/bin/sandbox-exec;
docker, bwrap и opencode в текущем PATH не найдены. Службы или программы
не устанавливались.

По официальной документации OpenAI именованные профили разрешений
поддерживают ограничение чтения выбранными путями, режим :minimal и
выключение сети. Это кандидат на переиспользование для локальных команд,
не подтверждённая реализация изоляции нашего конвейера:
[Permissions](https://learn.chatgpt.com/docs/permissions),
[Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).
Источники открыты и проверены 04.11.2026.

Есть различие с примерами документации: установленный codex sandbox --help
показывает команду непосредственно после опций, а не платформенную подкоманду
macos. Попытка codex sandbox macos --help из уже ограниченной среды закончилась
sandbox_apply: Operation not permitted. Успешного испытания границ доступа
не было; нельзя объявлять такой путь рабочим без локальной проверки.
Настройки ~/.codex не менялись, авторизация и модели Codex не переключались.
