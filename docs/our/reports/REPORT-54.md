## Реализация первого блока после «го» — 04.11.2026

Подготовлена общая изменяемая копия исходников для API-команды. Это часть
S4-62, ещё не весь браузерный конвейер. Режим execution включается явно
в новой сессии; старым сессиям новые разрешения не добавляются.

- api_workspace.py материализует разрешённые Git-объекты отдельно от
  исходного репозитория, без его .git, ссылок доски и секретных файлов.
  Ведущий и Luna работают последовательно с одними актуальными файлами.
  Запись и удаление требуют хеша прочитанной версии; новые тесты сразу видны
  через список изменений и чтение файла. Пути, ссылки и специальные файлы
  проверяются через дескрипторы без перехода по ссылкам.
- api_sandbox.py использует установленный codex sandbox только для
  системной изоляции macOS. Модель Codex и API OpenAI при этом не вызываются.
  Права задаются на отдельную рабочую папку и явно указанные среды Python,
  сеть закрыта, окружение собирается по разрешённому списку. Конфигурация
  запуска читается из пустой служебной папки, которую модель не меняет.
  Обхода изоляции при ошибке нет. Перед первым API-запросом — локальная
  проверка границ; её неуспех останавливает сессию до расхода.
- Команды ограничены ожиданием до 1800 секунд и выводом до 512 КиБ;
  в историю модели попадает ограниченный фрагмент большого вывода и его
  хеш. Автоматического повторения команды нет. Нулевой код выхода не
  подменяет факт тайм-аута или ограниченного вывода.
- Состояние незавершённой команды сохраняется до её запуска. После команды
  исходники переносятся копированием в новые файлы по новому пути. Старый
  процесс не получал разрешений на этот путь. Старые копии сохраняются для
  диагностики, автоматически не чистятся. При неудаче снимка выполнение
  останавливается, результат не выдаётся как готовый к проверке.
- api-session review формирует локальный обзор фактических изменений,
  включая новые файлы, хеши, режимы и текстовый diff. Это данные для
  человеческой проверки, не автоматически применяемый патч. Сеть и ключи
  для обзора не нужны. Во время запуска или при незакрытой командной
  операции обзор отклоняется. Прочитанный diff не означает приёмку.
- Прежнее восстановление доказано только для чтения. Для изменяемых
  сессий resume пока запрещён; неизвестное списание сохраняется,
  автоматического повторения платного выполнения нет.

## Находки при проверке на самом Mac

Первый разрешительный профиль сохранял запись в общей /tmp. После явного
запрета общей временной папки и выдачи отдельной временной папки задачи
проверены чтение/запись внутри, запрет чужого файла, перехода наружу по
ссылке, записи снаружи и сети. Проверены отсутствие фиктивных ключей
в окружении команды и отказ читать окружение или остановить соседний
контрольный процесс. Настоящие записи symphony.deepseek и symphony.openai
не читались. Запрос заведомо несуществующей записи Keychain завершился
ошибкой; он сам по себе не является доказательством всех границ Keychain.

Отдельная проба показала: setsid позволяет фоновому процессу пережить
завершение основной команды. Простое переименование папки тоже недостаточно:
запись через уже открытый дескриптор продолжалась. Поэтому принят именно
снимок в новые файлы, а не переименование или жёсткие ссылки. Регрессия
подтверждает: старый дескриптор дописал прежний файл, но материал для
приёмки не изменился. Это защита результата, **не обещание уничтожить
любой отделившийся процесс**. Фоновые службы/демоны, общий серверный запуск
и полноценное ограничение всех ресурсов требуют отдельного контура.

Обычная группа дочерних процессов завершается. PID основного процесса
удерживается до отправки сигнала группе: наблюдение через waitid/WNOWAIT
устраняет окно между освобождением PID и сигналом посторонней группе.
Это не расширяет права команды на чужие процессы.

Проверка сквозного цикла использует только httpx.MockTransport: ведущий
изменяет src/main.py, Luna читает текущий код, создаёт tests/check.py и
выполняет настоящий тест в системной изоляции, ведущий получает список
изменений и читает новый тест перед завершением. Всего девять имитированных
ответов провайдеров; платных обращений — ноль. Исходный репозиторий и его
незакоммиченные изменения не меняются. Это доказательство работы инструментов,
а не экономический эксперимент или оценка самостоятельности моделей.

этих данных требует нового подтверждения. Изменяющий веб-маршрут должен
проверять происхождение запроса и одноразовое подтверждение; модель не
управляет этими данными. После сбоя нельзя автоматически создавать новую
платную сессию. Действующие хуки нельзя вслепую повторять после API-кода:
они исполняют тесты и Git-операции, поэтому передача результата и обязательные
проверки должны сохранять новую границу доступа. Этот мост ещё не реализован.

Подтверждение Human Review → Done уже вызывает confirm_done и gate;
отдельная новая кнопка приёмки не нужна. Историческое предложение такой
кнопки уже было снято в S4-25. Доставка .deliver и отдельное разрешение
на .merge остаются существующим способом довести результат до проекта.

Поэтому реализация сохраняет доску и её жизненный цикл. Новый формат
профиля api-team-v1 выбирается для конкретной карточки, а TicketExecutor
выполняет одну API-сессию, используя общий слот, идентификатор запуска и
журнал владения. Обычные текстовые профили и Claude-этапы не переключаются.
Правки ядра необходимы для выбора исполнителя, запрета старого автоповтора
для него и добавления подтверждения/панели в существующий веб-интерфейс;
провайдеры, секреты, состояние задания и инструменты остаются в ours/.

Панель показывает состав команды и усилие, денежный потолок либо его
отсутствие, аварийные ограничения, версию/пути проекта и подтверждаемый
текст. Подтверждение связано с этими данными, карточкой, WORKFLOW и кодом.
Оно одноразовое; повтор HTTP-ответа не означает повтор работы. Обновление
коммита, задачи, настроек или кода перед стартом отменяет разрешение.
Прямого HTTP-запуска процесса нет. Новые POST-маршруты требуют локального
доступа, JSON и того же origin, включая порт; прежняя авторизация сервера
продолжает действовать. Пользовательские тексты выводятся как текст, без HTML.

После подготовки и подтверждения доверенный процесс получает ключи один
раз на провайдера, после проверки системной изоляции. Остановка запрещает
следующий платный запрос и прерывает локальную команду. Потеря владельца
отмечается по освобождённой блокировке; утрата родительского процесса
останавливает цикл перед следующим действием. Состояние запроса сохраняется
до его отправки, поэтому прерывание не превращает неизвестный расход в ноль.
Любой выход API-исполнителя, включая отмену до старта и смену конфигурации,

### Почему упали тесты в облаке

Оба отказа повторили отдельно на неизменённой версии `543d4bf` в двух коротких
запусках: [первое наблюдение](https://github.com/Serg10011/oh-my-symphony/actions/runs/42026393908)
и [проверка вывода в момент отказа](https://github.com/Serg10011/oh-my-symphony/actions/runs/42026861417).
Успех самого наблюдения означает, что журнал собран. Оба теста в нём завершились
с ошибкой, код и исходные проверки не менялись.

1. `test_running_manual_script_is_detected` проверяет защиту обновления доски,
   когда оператор уже запустил скрипт вручную. В Linux внутри упавшей проверки
   штатная команда `ps -axo pid=,args=` **показывала тот же PID**, но обрезала
   имя файла на `/boards/u`. Полный путь к `boards/update-test/test.sh` присутствовал
   в `/proc/<pid>/cmdline` и в широком выводе `ps` для этого же PID. Обычный поиск
   точного пути поэтому пропустил занятый файл. Это реальный недостаток старой
   проверки в таком Linux-окружении. Поломки на установленном Mac этот опыт не
   доказывает. Менять ширину вывода только в CI нельзя: это скрыло бы причину.
2. `test_core_bridge_and_real_controller_exchange_without_provider_access` запускает
   дочерний тестовый контроллер, который имитирует поставщиков. Подмена платформы
   в родительской фикстуре не наследуется дочерним процессом. В нём наблюдалось
   точное исключение `sandbox_platform_unsupported` при проверке, предназначенной
   для macOS. Защита сработала **до выдачи ключей или вызова модели**. Для
   переносимой фикстуры нужен тестовый двойник этой границы в дочернем процессе;
   настоящую проверку платформы в рабочем коде ослаблять нельзя.

Итог шага: бесплатный Linux подходит для поиска таких ошибок и воспроизводимого
сравнения публичных версий. Для зелёного кандидата отдельно нужны исправления
проверки работающего процесса и переносимости фикстуры, затем новый прогон
нового коммита. Исторические деревья с ошибками остаются неизменными. К исходной
проверке (коммит `92725f6`) приложены наблюдения `b805e05` и `dc6c4f1`.

Разовая диагностика не остаётся действующим workflow: её версии, полный
сценарий проверки и сборщик журналов сохранены в архиве SSD, подкаталоге
`reproduction`. Там 14 файлов, SHA-256 описи
`865a7d687489023e1af09592c4195f6159c61c7cc03443dea1447439e7ad32e4`.
В рабочей ветке остаётся обычный запуск полного набора, который сообщает
ошибку при падении тестов.

## Как карточка сверяет свой прогон — 05.11.2026

Сергей дал «Го» на привязку результата. Архитектор — Astra/max. После
завершения команды оператор может ввести номер публичного прогона в самой
карточке. Успех относится к одному коммиту, его дереву и родителю. Отдельно
показываются результат контрольной версии и ссылка на конкретную попытку.
Это промежуточный результат для человеческой приёмки. История и сверка
доступны в черновике PR №106.

В перечне файлов GitHub модуль сверяет дерево инструментов Linux и правила
экспорта Git. В проверенном сценарии разрешена подстановка только входного
коммита разработки. Контрольная версия, источник зависимостей и команды
изолированного запуска закреплены. Из метаданных задания сверяются также
стандартная Ubuntu 24.04 и группа машин GitHub, зафиксированная на реальном
прогоне. Так одноимённая метка своей машины не заменит выбранную среду.
Исход тестов берётся из шага GitHub
конкретной попытки после подготовки среды, пробы изоляции и освобождения
контейнера. Журнал тестируемого проекта может содержать произвольный текст.
Источники интерфейса GitHub — [прогоны](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run),
[шаги попытки](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt)
и [Git-объекты](https://docs.github.com/en/rest/git/trees#get-a-tree).

Карточка закрепляет профиль до подтверждения назначения. При сверке она
проверяет свой текст и дату создания, назначение, неизменность правил, базы,
рабочих файлов и собственного Git-коммита. Эти условия проверяются ещё раз
после ответа GitHub. Каждая попытка хранится отдельным файлом у журнала
карточки. При обычном открытии используются локальные данные на SSD.
Успешная ручная сверка делает пять чтений публичных метаданных GitHub.
При сетевой ошибке или временном ограничении GitHub карточка сообщает,
что результат получить не удалось. Повторное чтение выполняется по нажатию
оператора. [Лимиты чтения GitHub](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
Обновление базовой ветки делает прежнюю отметку недействительной для доставки,
как ранее было предусмотрено для старого пути в [S4-28](../tasks/TASK-S4-28.md).

На [историческом прогоне](https://github.com/Serg10011/oh-my-symphony/actions/runs/42028195681/attempts/1)
новый модуль подтвердил `b862b28` с деревом `6b966a2` и родителем `223d149`.
Историческая контрольная версия сценария — отдельный коммит `e2b1b59`.
Тот же номер с подставленным коммитом отклонён. Дополнительно на временной
доске настоящий браузер передал этот номер через рабочий HTTP-маршрут и
дочерний контроллер на GitHub. Готовый локальный кандидат имел другой коммит.
Оператор увидел «В этом запуске проверяли другую версию файлов». Карточка
осталась на рассмотрении, успешной записи в её истории не появилось.
Два ответа моделей при подготовке этой карточки были тестовыми.
