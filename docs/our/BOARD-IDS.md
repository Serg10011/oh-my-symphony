# Неповторяемые ID карточек (S4-31)

После удаления `DEMO-2` новая карточка получает `DEMO-3`. Старые запуски
остаются за `DEMO-2`. Ручное создание с использованным ID получает отказ
`ticket identifier was already issued`.

## Как хранится номер

В корне файловой доски находится `.symphony-identifiers.json`: версия
формата, выданные ID и наибольший номер каждого префикса. Создание и удаление
используют общий постоянный замок `.locks/allocator.lock`.
Сначала сохраняется резервирование ID, затем пишется или удаляется карточка.
Сбой между этими действиями оставляет пропуск; номер не возвращается.

Префиксы независимы. Для защиты от алиасов регистр букв и ведущие нули
номера не различаются: `DEMO-2`, `demo-2`, `DEMO-002` резервируют один номер.
Никогда не выдававшийся ручной ID с меньшим номером допустим; автоматическая
выдача всегда идёт выше максимума. Именованные ID без номера тоже резервируются.

Штатное PM-восстановление возвращает ту же исходную плановую карточку:
журнал хранит полный `PlanningRef` (задача, ревизия, передача и снимок).
Только полное совпадение этой идентичности допускает восстановление с прежним
ID; обычные CLI/API-создатели её не передают. Другая плановая идентичность
получает отказ. Это сохраняет существующие сценарии PM-reconcile после сбоя.

Веб-доска уже запрашивает номер у сервера. Для CLI теперь можно опустить ID:

```sh
symphony board new --workflow /path/to/WORKFLOW.md --prefix DEMO "Название задачи"
```

Прежний синтаксис с явным свободным ID сохраняется. Это команды создания
настоящей карточки; выполнять их нужно в рамках согласованного задания.

## Переход со старой доски

При создании/удалении учитываются имена существующих файлов и ID в их
front matter, а также `issue_id`/`identifier` из таблицы `runs`. История
читается через SQLite `mode=ro`, без миграции схемы и изменения запусков.
Путь берётся от WORKFLOW.md; для самостоятельного `--root` без конфигурации
ожидается `<родитель доски>/.symphony/state.db`.
Из `pm_handoff_items` также резервируются старые плановые ID; полная
идентичность восстанавливается по связанным записям задачи, передачи и снимка.
Это допускает и первую публикацию уже зарезервированной планом карточки.
Проверка хеша неизменяемого входа остаётся обязанностью PM-модуля.

При первом создании журнала также учитываются сохранившиеся `.locks/<ID>.lock`:
они помогают восстановить номера удалённых карточек, которые ещё не запускались.
Пустые старые замки могут консервативно занять номер — это безопасный пропуск.
Если журнал повреждён или историю прочитать нельзя, создание/удаление
останавливается с ошибкой. Чтение доски и изменение существующей карточки
не требуют новой выдачи ID.

Для резервной копии нужны сама доска, журнал ID, `.locks/`, история
`.symphony/state.db` и наши данные `.ours-state/`. Историю нужно снимать
согласованной копией SQLite (backup API либо остановленные записи), а не
разрозненными копиями работающих DB/WAL.
Журнал ID и постоянные замки нельзя включать в уборку временных файлов.
Если старый номер до перехода исчез из файлов, замков и всей истории,
автоматически восстановить его нельзя. Уже смешанную старую историю
изменение задним числом не разделяет.
Защита действует в штатных CLI/API/служебных создателях; прямая запись
новых Markdown-файлов в обход трекера и старые версии ядра её не соблюдают.

## Прежние создатели карточек

В служебной `tmp_workspaces/` найдены `create-eve-trial-cards.py`,
`create-e4-smoke-card.py`, `create-glossary-cards.py`, `create-s4-20-card.py`,
`create-s4-22-card.py`. Их собственный `max + 1` ненадёжен; попытка выдать
старый ID теперь получит отказ ядра. Эти исторические скрипты не запускались
и не переписывались. Для новой согласованной пробы создатель должен получать
номер через API или автоматический путь CLI, без собственного счётчика.

`ours/hooks/plan.py` задаёт подзадачам фиксированные `<задача>-<порядок>`
через CLI. После удаления такая карточка тоже остаётся зарезервированной.
В версии S4-31 при частичном провале планировщик удалял созданные файлы,
но их ID оставались занятыми; повтор требовал человека. Этот результат
сохранён как история S4-31. S4-32 добавляет отдельное продолжение **исходной**
операции, описанное ниже; обычное создание с прежним ID по-прежнему запрещено.

## Восстановление обычного плана (S4-32)

Перед первым `board new` планировщик сохраняет
`.ours-state/<ЗАДАЧА>.plan-create.json`: неизменяемый вход, его хеш,
проект/доску/исходную карточку, интеграционную ветку с исходным коммитом,
случайный ключ операции и фазу `creating` / `committed` / `done`.
Контрольная сумма обнаруживает повреждение; это не электронная подпись.
Файл и каталог синхронизируются с диском до продолжения.

В журнале ID появляется необязательный раздел `creations`: ID, ключ
создания, хеш исходной шапки/описания и исходный `created_at`.
CLI `board new --creation-key <64 hex> --json` с **явным ID** допускает
повтор лишь исходного входа. Существующий результат возвращается без
сброса состояния/описания; пропавшая карточка может восстановиться с прежним
`created_at`. Старую резервацию без квитанции принять таким ключом нельзя.
PM-путь с `PlanningRef` остаётся отдельным, объединять его с ключом нельзя.

Планировщик сначала создаёт весь набор в `Subtasks` с `--staged`:
CLI проверяет, что это неисполняемое terminal-состояние данного WORKFLOW.
`--root` вместе с явным `--workflow` той же доски сохраняет её состояния и путь к
истории; чужой `--root` не заимствует настройки другой доски. Без явного
`--workflow` сохраняется самостоятельный режим `--root`, включая работу
после удаления текущей рабочей папки завершённой задачи.
До принятия набора проверяется неизменность карточек. Затем сохраняются
родительские `Plan Accepted`/`Subtask Progress` и фаза `committed`.
`board release <ID> --creation-key <ключ> --state "In Progress"` атомарно
пишет рабочее состояние и шапку `creation_release`. Повторный release
сохраняет результаты, последующий статус и ручную паузу.

При сбое файлы не удаляются, исходная задача уходит в `needs_human`;
попытка нарезки не тратится. После устранения причины оператор в рамках
согласованного задания может продолжить **тот же** план без запуска
планирующего агента:

```sh
"<Python конвейера>" "<форк>/ours/hooks/plan.py" recover DEMO-9 --board "<папка доски>"
```

Команда возвращает исходную задачу из `needs_human` в `Subtasks` и разрешает
выполнение подзадач, поэтому это операционная команда, не проверка документации.
Код 0 — завершено/уже завершено, 1 — отказ или прерванное продолжение;
причина в выводе, карточке и `check.log`. Автоматического фонового повтора нет.
Возврат исходной карточки в `Subtasks` также позволяет `plan.py hook`
продолжить незавершённый журнал, даже если `Plan Accepted` уже записан.

Изменённый план/проект/цель/шапка, лишние карточки, чужой или повреждённый
журнал блокируют продолжение. При пропаже plan.toml продолжение использует
сохранённый снимок. До принятия набора потерянная карточка подзадачи
восстанавливается через квитанцию; **после** принятия пропавший файл требует
человека, потому что в нём могла быть работа агента. Уже выпущенные подзадачи
могут продолжать работу при сбое выпуска остальных; полный набор и записи
приёмки в этот момент уже существуют. Повтор выпуска их не перезаписывает.
Старый частичный план без журнала автоматически не усыновляется.
Удалять журнал/квитанции ради перепланирования нельзя. Общий замок задачи
защищает от двух параллельных продолжений.

## Применение и возврат

S4-31 применена через согласованный `post-merge` 01.11, `b28fe6b`.
S4-32 до отдельной приёмки и обновления доступна только в ветке разработки.
Первый штатный запрос создания/удаления создаёт журнал ID;
тестовые карточки ради миграции не нужны.

Откат кода сохраняет журнал и историю. Старый код не знает о журнале и
снова может вернуть номер в оборот; до восстановления новой защиты выдачу
новых ID нужно приостановить. Удалять журнал ради обхода отказа нельзя.
При возврате с S4-32 сохраняются также журналы создания, квитанции и отметки
выпуска в карточках. Незавершённые планы не передавать старому планировщику;
для продолжения нужен код, понимающий этот журнал. Резервная копия нужна
до применения, но не должна затирать появившуюся после неё работу.
